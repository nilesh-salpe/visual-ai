Speculative decoding in vLLM

How vLLM produces several tokens per target-model pass: proposers (n-gram, draft models, EAGLE, MTP (multi-token prediction), Medusa, suffix), verification with rejection sampling, and when it pays.

What is the problem?Decoding generates one token per forward pass and is memory-bound: the GPU (graphics processing unit) reads all weights to produce a single token per request, leaving compute idle.
Core ideaA cheap proposer guesses k tokens; the target model scores all of them in one pass; a rejection sampler accepts the longest valid prefix (plus one token of its own), so the output distribution is unchanged. In vLLM it is configured with --speculative-config, and the scheduler treats proposed tokens as more tokens to catch up.
1 · Problem

Tokens per target pass

Expected tokens produced per target forward pass as a function of acceptance rate α and the number of proposed tokens k.

2 · Limitation

Why decoding leaves the GPU idle

Memory-bound

Each step reads every weight to make one token per request.

Sequential

Token t + 1 needs token t, so steps cannot be parallelised naively.

Latency

Per-token time sets user-visible speed in chat.

5 · How it works

Worked example: expected tokens per pass

Acceptance probability α per proposed token, k proposed tokens: expected tokens per target pass = (1 − α^(k+1)) / (1 − α) (Leviathan et al., 2023).

Worked example

  1. α = 0.5, k = 4: 1.94 tokens per pass.
  2. α = 0.7, k = 4: 2.77.
  3. α = 0.9, k = 4: 4.10.
  4. Notebook 05: the n-gram proposer on a repetitive code snippet produced 16 tokens in 10 target passes (1.6 tokens/pass) with k = 3.
Speed-up depends on acceptance, which depends on the proposer and the workload; overhead must be smaller than the saving.
6 · Why it works

Why it speeds things up

Free compute

Scoring k + 1 positions costs about the same as one in a memory-bound step.

Exactness

Rejection sampling keeps outputs identical in distribution.

Fits the scheduler

Proposed tokens are just extra tokens to catch up (num_tokens_with_spec).

Workload-dependent

Repetitive or predictable text gets high acceptance; creative text less.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Speculative decoding always helps."

At large batch sizes the GPU is already compute-busy; overhead can outweigh gains.

"You need a separate draft model."

n-gram, suffix and EAGLE/MTP methods avoid a full second model.

"More proposed tokens is better."

Expected gain saturates at 1/(1 − α); extra proposals mostly get rejected.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • n-gram needs no extra model. Great for edits, quoting, code.
  • EAGLE / MTP heads. Higher acceptance on general text.
  • Watch acceptance metrics. vllm:spec_decode_num_accepted_tokens_per_pos.

⚠ Traps

  • Large k with low acceptance. Wasted verification compute.
  • Speculation at very high batch sizes. The GPU is no longer idle, so gains shrink.
  • Mismatched draft tokenizer. Draft and target must share a vocabulary.

How does the vLLM scheduler handle speculative tokens?

They count toward num_tokens_with_spec; the scheduler assigns budget so computed tokens catch up, verifying them in the same step.

When does n-gram speculation work well?

When outputs repeat or copy context: code edits, summaries quoting the source, structured data.
9 · Key takeaway

Key takeaway

vLLM speculative decoding lets a proposer (n-gram, draft, EAGLE, MTP, …) guess k tokens that the target verifies in one pass with rejection sampling: same outputs, (1 − α^(k+1))/(1 − α) tokens per pass.
Say it in 30 seconds

Decoding is memory-bound: each step reads all the weights to produce one token per request. Speculative decoding uses that idle compute. A cheap proposer, which in vLLM can be an n-gram lookup, a small draft model, EAGLE or multi-token-prediction heads, Medusa or suffix decoding, guesses a few tokens; the target model scores them all in one pass; and a rejection sampler accepts the longest valid prefix plus one token of its own, so the output distribution is unchanged. With acceptance alpha and k proposals you get one minus alpha to the k plus one, over one minus alpha, tokens per pass.
