vLLM Router: load balancing a fleet of replicas

Why LLM (large language model) traffic needs a state-aware load balancer, and how the vLLM Router does it: consistent hashing for session affinity, power of two choices, cache-aware routing, prefill/decode disaggregation, retries and circuit breakers, Kubernetes discovery, and how it compares with llm-d and a plain Kubernetes Service.

What is the problem?A fleet of vLLM replicas each holds its own KV (key-value) cache. A generic load balancer spreads a conversation's turns over different replicas, so each turn recomputes the whole history, and it cannot orchestrate prefill/decode disaggregation, where one request visits two kinds of worker.
Core ideaPut a lightweight LLM-aware router in front of the replicas. Route a session to the same replica (consistent hashing on a session or user id) or to the replica with the longest cached prefix (cache-aware), but fall back to the least-loaded replica when load is skewed. For prefill/decode disaggregation, send each request to a prefill worker, then to a decode worker that receives its KV cache. Add retries, circuit breakers, Kubernetes discovery and metrics.
1 · Problem

Replicas are not interchangeable

Each vLLM replica keeps its own KV cache and its own queue. Which replica a request reaches decides how much of its prompt must be recomputed and how long it waits.

Multi-turn chat

Every turn resends the whole conversation; only the replica that served the last turn has it cached.

Shared prefixes

System prompts and few-shot examples repeat across users; concentrating them on a few replicas raises the prefix-cache hit rate.

Two kinds of worker

With prefill/decode disaggregation a request is prefilled on one pool and decoded on another; something must coordinate the hand-off.

2 · Limitation

Why a generic load balancer falls short

Round robin ignores state

A Kubernetes Service spreads turns evenly and so scatters each conversation over replicas.

Stickiness ignores load

Pinning a session forever overloads the replica that holds a few long, busy sessions.

No P/D awareness

Treating prefill and decode pods as identical replicas sends work to the wrong pool.

C. Consistent hashing maps the same session id to the same replica every time, so each turn finds the previous turn's KV cache. Power of two balances load but ignores where the cache is.
4 · Core idea

Route on cache and load

consistent_hash

Hash a key (X-Session-ID, then X-User-ID, X-Tenant-ID, request and trace ids, or the OpenAI "user" field) onto a ring with 160 virtual nodes per worker: sticky sessions, and removing a worker only moves its own keys.

cache_aware

Keep an approximate radix tree of prefixes per worker. While load is balanced, send a request to the worker with the longest prefix match if it covers more than 50% of the prompt, else to the worker with the smallest tree; when load is imbalanced, send it to the least-loaded worker.

power_of_two

Sample two workers, pick the one with fewer pending requests: near-optimal balance with almost no coordination.

round_robin and random

Stateless spreading, for stateless or single-turn traffic.

5 · How it works

Prefill/decode routing and operations

Resilience is on by default: up to 3 retries with exponential backoff (100 ms initial, 10 s maximum, ×2, 10% jitter) on HTTP (Hypertext Transfer Protocol) 408, 429 and 5xx; a circuit breaker opens after 5 consecutive failures, half-opens after 30 s and closes after 2 successes.

5 · How it works

Worked example: a cache-aware routing decision

Defaults: cache_threshold 0.5, balance_abs_threshold 32, balance_rel_threshold 1.1. Three replicas have 40, 42 and 45 requests in flight. A prompt of 2,000 characters shares a 1,500-character prefix with something replica 2 served earlier.

Worked example

  1. Imbalance test: max − min = 45 − 40 = 5, not above 32, so the system is balanced (both conditions are required).
  2. Best match ratio: 1,500 / 2,000 = 0.75 > 0.5, so route to replica 2 and reuse its cached prefix.
  3. Later the loads are 10, 80 and 30: 80 − 10 = 70 > 32 and 80 > 1.1 × 10, so the system is imbalanced.
  4. Now the request goes to the least-loaded replica (replica 1) even though replica 2 holds the prefix; the radix tree still records it.
Cache affinity wins while load is even; load balance wins once it is not.
6 · Why it works

Why it works, and the evidence

Prefill is the expensive part to repeat

A cache hit skips recomputing the shared prefix, cutting time to first token and freeing compute.

Thresholds arbitrate

Two simple tests (absolute and relative load gaps) decide when balance overrides affinity.

Benchmarks (vLLM team, Dec 2025)

Llama 3.1 8B with 8 prefill and 8 decode pods: 25% more requests/s than llm-d and twice a round-robin Kubernetes Service, with TTFT 1,200 ms lower than llm-d. DeepSeek V3 (1 prefill and 1 decode pod, TP (tensor parallelism) 8 each): throughput close to llm-d, TTFT 2,000 ms lower than both.

One of several options

llm-d reads vLLM KV-cache events for precise prefix-aware routing and reports 3× output throughput vs round robin (Llama 3.1 70B, MI300X); the production stack bundles its own router. Pick by platform.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Sticky sessions solve LLM load balancing."

They maximise cache reuse but ignore load; hot sessions overload a replica. Cache-aware routing falls back to the least-loaded worker when load is skewed.

"The router does the inference."

It only forwards requests (or tokenised gRPC requests); the vLLM workers do all model work. Built in Rust to keep its overhead small.

"Any router works with P/D disaggregation."

P/D needs a router that knows which workers prefill and which decode and how KV transfer is configured (NIXL (NVIDIA Inference Xfer Library), NCCL (NVIDIA Collective Communications Library), Mooncake).
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Send a session header. X-Session-ID (then X-User-ID, X-Tenant-ID, …) is the consistent-hash key; without one, requests may not stick.
  • Cache-aware for shared prefixes. Repeated system prompts and few-shot examples benefit even across users.
  • Watch the router's /metrics. Per-worker latency, errors and health show hot spots and tripped circuit breakers.

⚠ Traps

  • Treating it as a mature component. It is v0.1.x, forked from the SGLang model gateway; flags may change.
  • Hash affinity without capacity. A few heavy sessions can overload one replica; consistent hashing does not look at load.
  • Comparing with a broken baseline. The blog excluded vLLM's built-in DP (data parallelism) coordinator, which then had a known throughput issue (1/8 of the others).

Why does consistent hashing use virtual nodes?

With 160 points per worker on the ring, keys spread evenly across workers, and removing one worker redistributes only its keys among all the others.

Name two resilience features of the vLLM Router.

Retries with exponential backoff and jitter on 408/429/5xx; circuit breakers that remove failing workers; health checks via Kubernetes discovery (any two).
9 · Key takeaway

Key takeaway

An LLM router sends each request to the replica that already holds its context, unless that replica is overloaded, and orchestrates prefill and decode pools.
Say it in 30 seconds

Each vLLM replica has its own KV cache, so where a request lands decides whether its prefix is reused. The vLLM Router, a Rust load balancer released in December 2025 and forked from the SGLang model gateway, offers consistent hashing on a session or user id (160 virtual nodes per worker), cache-aware routing that follows prefix matches while load is balanced and falls back to the least-loaded worker otherwise, power of two choices, and round robin. It also routes prefill/decode disaggregated deployments, retries with backoff, trips circuit breakers on failing workers, discovers pods in Kubernetes and exports Prometheus metrics. In the team's benchmark it delivered 25% more throughput than llm-d and twice a round-robin Kubernetes Service for Llama 3.1 8B.
