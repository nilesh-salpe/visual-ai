The scheduler: continuous batching and chunked prefill

How vLLM V1 decides what runs each step: one token budget shared by decodes and prefills, running requests first, chunked prefill, a long-prefill threshold, and preemption by recomputation.

What is the problem?Every step mixes requests at different stages: some decoding one token, some with long prompts to prefill, some just arrived. The scheduler must keep the GPU (graphics processing unit) full without stalling anyone.
Core ideaV1 has no prefill or decode phase. Each request has num_computed_tokens and a known token count; each step hands out a token budget (max_num_batched_tokens) so computed tokens catch up. Running requests go first, then waiting ones; long prompts are chunked. If KV (key-value) blocks run out, the newest running request is preempted and later recomputed.

Fill a step's token budget

Running requests (decoding) and waiting ones (prompts to prefill) compete for one step's budget. Change the budget and the long-prefill threshold and press "step".

2 · Limitation

What older schemes got wrong

Static batches

Wait for the whole batch to finish before admitting new requests.

Prefill-first phases

Separate prefill steps pause all decoding, causing latency spikes.

Whole prompts

One long prompt can occupy an entire step.

4 · Core idea

One budget, no phases

Token budget

max_num_scheduled_tokens per step (from max_num_batched_tokens); spent on any mix of prefill chunks and decodes.

Order

Running requests first (FCFS (first-come, first-served) policy by default, priority optional), then waiting requests while budget and KV blocks last.

Chunked prefill

On by default in V1 (enable_chunked_prefill=True); long_prefill_token_threshold caps a single request's chunk.

Preemption

If blocks run out, the newest (or lowest-priority) running request is preempted: blocks freed, computed tokens reset to 0, put back at the front of the waiting queue.

5 · How it works

From the source

The scheduler's own comment (vllm/v1/core/sched/scheduler.py, v0.31.0):

# There's no "decoding phase" nor "prefill phase" in the scheduler.
# Each request just has the num_computed_tokens and
# num_tokens_with_spec. num_tokens_with_spec =
# len(prompt_token_ids) + len(output_token_ids) + len(spec_token_ids).
# At each step, the scheduler tries to assign tokens to the requests
# so that each request's num_computed_tokens can catch up its
# num_tokens_with_spec. This is general enough to cover
# chunked prefills, prefix caching, speculative decoding, ...
5 · How it works

Worked example: one step

Notebook 03's step function (mirroring vllm/v1/core/sched/scheduler.py): budget 64 tokens; one running request decoding; one new request with a 100-token prompt.

Worked example

  1. Running first: the decoding request needs 1 token → scheduled 1. Budget left: 63.
  2. Waiting next: the new request needs 100 prompt tokens; the budget allows 63, so its prefill is chunked: 63 now, 37 next step.
  3. Blocks: 63 tokens need ⌈63/16⌉ = 4 new blocks, allocated from the pool.
  4. Defaults in v0.31.0 depend on GPU and entrypoint: on H100/H200-class GPUs, max_num_batched_tokens is 16,384 for the LLM (large language model) class and 8,192 for the server; max_num_seqs 1,024. Other GPUs: 8,192 / 2,048 and 256.
Decodes are never starved by prefills, and prefills fill whatever budget is left.
6 · Why it works

Why the unified design works

One rule covers everything

Prefill, decode, prefix-cache hits and speculative tokens are all "tokens to catch up".

Steady latency

Decodes always get their token each step; prefills absorb the rest (Sarathi-Serve's stall-free idea).

Full GPU

The budget keeps each step large enough to be efficient.

Graceful overload

Preemption by recomputation frees memory without crashing; the request resumes later.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"vLLM batches requests that arrive together."

Batches change every step: requests join and leave continuously.

"Preempted requests lose their output."

They keep generated tokens; only the KV cache is dropped and recomputed (prefix caching may make that cheap).

"Chunked prefill makes prompts slower."

Per prompt it can add a few steps, but it keeps decode latency smooth and the GPU busy.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Bigger budget = higher throughput. But longer steps, so higher inter-token latency.
  • long_prefill_token_threshold. Caps one prompt's chunk per step.
  • Watch vllm:num_preemptions. Rising → raise memory or lower concurrency.

⚠ Traps

  • Too large max_num_seqs for the memory. Constant preemption and recomputation.
  • Tiny budget with long prompts. TTFT (time to first token) grows as prompts trickle in.
  • Assuming strict FCFS. The scheduler may skip a blocked request to schedule later ones.

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

Default scheduling policy in v0.31.0?

"fcfs" (SchedulerConfig.policy).

What happens to a preempted request in V1?

Its KV blocks are freed, num_computed_tokens is reset to 0, and it is put back at the front of the waiting queue to be recomputed later.

What does long_prefill_token_threshold do?

Caps how many prompt tokens one request may be given in a single step, so one long prompt cannot monopolise the budget.
9 · Key takeaway

Key takeaway

vLLM V1 schedules with one per-step token budget and no phases: running requests first, then waiting ones in chunks, and preemption by recomputation when KV blocks run out.
Say it in 30 seconds

Every vLLM step, the scheduler hands out a token budget. There is no separate prefill or decode phase: each request simply has tokens it already computed and tokens it knows about, and the scheduler assigns tokens so it catches up. Requests already running go first, which gives every decoding request its next token, then waiting requests fill the rest, with long prompts split into chunks and optionally capped per step. If the KV cache runs out of blocks, the newest running request is preempted: its blocks are freed and it is recomputed later. Budget size trades throughput against inter-token latency.

Problem: mixed prefills and decodes every step.
Core idea: token budget; running first; chunked prefill.
Overload: preempt newest; recompute later.
