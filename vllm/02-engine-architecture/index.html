Engine architecture

How vLLM V1 splits work across processes (API (application programming interface) servers, engine cores, GPU (graphics processing unit) workers, a data-parallel coordinator), why the engine loop is isolated, and how the pieces talk.

What is the problem?Tokenising, detokenising and streaming are CPU (central processing unit) work; scheduling must run every few milliseconds; the GPU must never wait. In one Python process these compete for the interpreter.
Core ideaV1 runs an API server process (HTTP (Hypertext Transfer Protocol), tokenisation, streaming), an isolated EngineCore process per data-parallel rank (a busy loop: schedule → execute → update), and one GPU worker process per GPU. They communicate over ZMQ (and shared memory). For N GPUs: A + DP (data parallelism) + N processes, plus a coordinator if DP > 1.

2 · Limitation

Why not one process?

The GIL

One Python interpreter cannot tokenise, schedule and stream in parallel.

CPU overhead

At small per-step GPU times, CPU work between steps leaves the GPU idle.

One process per GPU

Each GPU needs its own process for its CUDA (Compute Unified Device Architecture, NVIDIA's programming platform for its graphics processors) context.

4 · Core idea

Three kinds of processes

API server

HTTP (OpenAI-compatible), input processing, detokenisation, streaming. Count defaults to DP (--api-server-count).

EngineCore

Busy loop: schedule → execute model → update outputs. Holds the scheduler and KV (key-value) cache manager. One per DP rank.

GPU worker

One per GPU: loads its shard of the model, holds its KV cache, runs forward passes (model runner, CUDA graphs).

5 · How it works

Worked example: counting processes

The vLLM architecture overview's formula: total = A + DP + N (+ 1 if DP > 1), where N = DP × PP (pipeline parallelism) × TP (tensor parallelism) GPUs and A defaults to DP.

Worked example

  1. vllm serve … -tp=4 on one node: 1 API server + 1 engine core + 4 GPU workers = 6 processes.
  2. vllm serve … -tp=2 -dp=4 on 8 GPUs: 4 API servers + 4 engine cores + 8 GPU workers + 1 DP coordinator = 17 processes.
  3. Each API server connects to every engine core via ZMQ, so any server can route a request to any data-parallel rank.
  4. In the LLM (large language model) class (offline), the engine core still runs in a background process (SyncMPClient); InprocClient keeps it in-process.
Splitting CPU-heavy I/O from the engine loop keeps the GPU fed; data parallelism replicates the engine, tensor and pipeline parallelism multiply the workers.
6 · Why it works

Why this layout works

Overlap

Tokenisation, multimodal loading and streaming run in parallel with the engine loop (V1 blog).

Simple scaling

DP adds engines; TP/PP add workers under one engine; the formulas stay simple.

Fault isolation

Front-end and engine failures are separated and observable.

Many-to-many routing

Any API server can feed any DP engine, balancing load.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"More API servers make generation faster."

They raise HTTP and tokenisation capacity; generation speed is set by the engine and GPUs.

"Each GPU runs its own scheduler."

One EngineCore schedules for all GPU workers of its DP rank; workers only execute.

"Data parallelism shares one KV cache."

Each DP rank has its own engine and KV cache; prefix-cache hits depend on routing to the right rank.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Processes = A + DP + N (+1). A defaults to DP.
  • EngineCore = scheduler + KV manager + executor. One per DP rank.
  • Executors. uniproc, multiproc (default multi-GPU on one node), Ray (multi-node).

⚠ Traps

  • Under-provisioning CPU cores. Each process needs CPU; too few cores slow the engine loop.
  • Treating DP like TP. DP replicates the whole engine; TP splits one model across GPUs.
  • Debugging only the API server logs. Scheduling issues appear in the engine core.

9 · Key takeaway

Key takeaway

vLLM V1 runs API servers (HTTP, tokenise, stream), one isolated EngineCore per data-parallel rank (schedule + KV + execute) and one worker per GPU: A + DP + N processes, +1 coordinator if DP > 1.
Say it in 30 seconds

vLLM version one splits the work across processes so the GPU never waits on Python. API server processes handle HTTP, tokenisation and streaming. Each data-parallel rank has one engine-core process running a busy loop that schedules the next step, manages the KV cache and dispatches work. Each GPU has its own worker process that runs the model. They talk over ZMQ in a many-to-many pattern. The total is the number of API servers plus data-parallel engines plus GPUs, plus a coordinator when data parallelism is on: six processes for tensor parallel four on one node, seventeen for tensor two by data four.

Problem: CPU work and scheduling compete with GPU work.
Core idea: API server / EngineCore / GPU workers over ZMQ.
Count: A + DP + N (+1 if DP > 1).
