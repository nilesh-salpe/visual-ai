What vLLM is and a request's life

The open-source LLM (large language model) inference and serving engine built around PagedAttention: what it does, the two ways to use it, and every stage a request passes through.

What is the problem?Serving an LLM well means batching many users' requests onto a GPU (graphics processing unit), managing a KV (key-value) cache that grows with every token, and streaming tokens back quickly. Writing that from scratch is a large systems project.
Core ideavLLM is a serving engine: you give it a model and requests; it handles batching (continuous, token-budget scheduling), KV memory (paged blocks with prefix caching), execution (CUDA (Compute Unified Device Architecture, NVIDIA's programming platform for its graphics processors) graphs, fused kernels, parallelism) and APIs (application programming interfaces) (a Python LLM class for offline batches and vllm serve for an OpenAI-compatible server).

2 · Limitation

Why not serve with a plain model.generate()?

One request at a time

GPUs sit mostly idle during decode without batching many users.

KV memory waste

Contiguous per-request reservations used only 20.4%–38.2% of KV memory in earlier systems (PagedAttention paper).

Everything else

Streaming, OpenAI-compatible APIs, metrics, parallelism, quantization, speculative decoding.

4 · Core idea

Four jobs of a serving engine

Batching

A unified scheduler hands out a per-step token budget across prefills and decodes (deck 04).

KV memory

Paged 16-token blocks, reference counts and automatic prefix caching (decks 03, 05).

Execution

Model runner with CUDA graphs and torch.compile; tensor, pipeline, data and expert parallelism (decks 02, 07).

Interfaces

LLM class, vllm serve (OpenAI-compatible), metrics, benchmarking tools (deck 08).

5 · How it works

The two entrypoints

# offline batch inference
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct")
outs = llm.generate(prompts, SamplingParams(temperature=0.7, max_tokens=200))

# online serving (OpenAI-compatible)
$ vllm serve meta-llama/Llama-3.1-8B-Instruct
$ curl localhost:8000/v1/chat/completions -H "Content-Type: application/json"     -d '{"model": "meta-llama/Llama-3.1-8B-Instruct", "messages": [{"role": "user", "content": "Hi"}]}'
5 · How it works

Worked example: one chat request

A client sends a 900-token prompt to vllm serve meta-llama/Llama-3.1-8B-Instruct and asks for up to 200 tokens. Checked against vLLM v0.31.0.

Worked example

  1. The API server process applies the chat template, tokenises and sends the request to the engine core over ZMQ (ZeroMQ, a messaging library).
  2. The EngineCore scheduler checks the prefix cache (a shared system prompt may already be cached), allocates 16-token KV blocks and schedules the prompt, in chunks if it exceeds the per-step token budget.
  3. The GPU worker runs the forward pass for the whole batch (this request's prefill chunk plus other users' decode tokens), samples a token, and the request joins the decode set.
  4. Each later step adds one token (or several with speculative decoding); the API server detokenises and streams them until 200 tokens or a stop condition, then the request's blocks are freed (and stay cached for reuse).
One request touches three kinds of processes and is batched with everyone else at every step.
6 · Why it works

Why vLLM became the default open engine

Memory efficiency

PagedAttention gave 2–4× throughput over FasterTransformer and Orca at the same latency (Kwon et al., 2023).

Lower CPU overhead

The V1 re-architecture isolated the engine loop and reported up to 1.7× higher throughput than V0.

Breadth

Many model families, quantization formats, hardware back ends and parallelism modes.

Standard API

OpenAI-compatible endpoints make it a drop-in back end.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"vLLM is a model."

It is an inference engine; it runs models (mostly from Hugging Face) efficiently.

"vLLM only helps big batches."

It also reduces per-request latency features (prefix caching, speculative decoding, CUDA graphs), but its biggest wins come from batching.

"PagedAttention is all vLLM does."

Scheduling, prefix caching, parallelism, quantization and the serving stack matter as much today.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Offline: LLM(model).generate(prompts). Batches everything for throughput.
  • Online: vllm serve . OpenAI-compatible /v1/chat/completions.
  • Read the Inference topic first. KV cache, batching, PagedAttention concepts.

⚠ Traps

  • Benchmarking one request at a time. vLLM's gains come from batching many.
  • Assuming V0 behaviour. V1 changed the scheduler, process layout and defaults; the V0 engine was removed entirely in v0.11.0 (October 2025).
  • Pinning advice to old versions. Defaults change between releases; check the version you run.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

Which process tokenises prompts in vLLM V1 serving?

The API server (input processing), so the engine loop stays free for scheduling.

Name the two main ways to use vLLM.

The LLM class for offline batch inference, and vllm serve for an OpenAI-compatible HTTP server.

What happens to a request's KV blocks when it finishes?

They are freed back to the pool but keep their hashes, so a later request with the same prefix can reuse them until evicted.
9 · Key takeaway

Key takeaway

vLLM is an LLM serving engine: an API server tokenises, the EngineCore schedules a token budget over paged KV blocks each step, GPU workers run the batch, and tokens stream back.
Say it in 30 seconds

vLLM is an open-source inference and serving engine. You use it offline through the LLM class, which batches a list of prompts, or online with vllm serve, an OpenAI-compatible server. Inside, an API server process tokenises requests and streams results; an engine-core process runs a loop that schedules every step, deciding how many tokens each request gets and allocating paged KV-cache blocks; GPU worker processes run the batched forward pass and sample tokens. Its origin is PagedAttention, which raised throughput two to four times by eliminating KV memory waste.

Problem: efficient multi-user LLM serving is hard.
Core idea: API server → EngineCore (schedule, KV) → GPU workers.
Use: LLM class offline; vllm serve online.

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Efficient Memory Management for Large Language Model Serving with PagedAttention
Kwon et al. · SOSP 2023

Stores the KV cache in fixed-size blocks mapped by a block table, like virtual memory pages, giving near-zero fragmentation and sharing with copy-on-write. The basis of vLLM.

Remember: 2–4× throughput vs FasterTransformer and Orca at the same latency
vLLM v0.11.0 release notes
vLLM project · GitHub releases 2025

Completes the removal of the V0 engine (AsyncLLMEngine, LLMEngine, MQLLMEngine, V0 attention backends): V1 is the only engine in the codebase.

vLLM V1: A Major Upgrade to vLLM's Core Architecture
vLLM Team · vLLM blog 2025

The V1 re-architecture: an isolated EngineCore busy loop (scheduler + executor) in its own process, a unified token-budget scheduler, zero-overhead prefix caching, torch.compile and piecewise CUDA graphs.

Remember: up to 1.7× higher throughput than V0
Architecture Overview
vLLM documentation · docs.vllm.ai 2026

Entrypoints (LLM class, OpenAI-compatible server) and the process layout: API server, one engine-core process per data-parallel rank running a busy loop, one worker process per GPU.
