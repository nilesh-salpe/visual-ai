Automatic prefix caching

How vLLM reuses KV (key-value) cache across requests that share a prefix (system prompts, few-shot examples, multi-turn chats, RAG (retrieval-augmented generation) documents): chained block hashes, cache hits, and eviction.

What is the problem?Many requests start with the same thousands of tokens. Recomputing their KV cache for every request wastes prefill compute and adds time to first token.
Core ideaHash every full KV block together with the hash of the block before it, so a block hash identifies the entire prefix up to that block. A new prompt reuses the longest run of matching block hashes and only prefills the rest. Freed blocks keep their hashes until LRU (least recently used) eviction. In V1 it is on by default (enable_prefix_caching=True, hash sha256).
1 · Problem

Which blocks hit?

Two prompts, split into 16-token blocks. Edit where the second prompt first differs from the first; blocks before that point (full blocks only) are cache hits.

2 · Limitation

Why exact-match hashing on whole prompts isn't enough

Prompts differ at the end

Whole-prompt hashes would almost never match.

Position matters

The same text at a different position has different KV (positions are encoded in K).

Memory is finite

Cached blocks must be evictable when space is needed.

3 · Your turn

Why chain the hashes?

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

Why does vLLM hash each block together with its parent block's hash?

B. KV values depend on every earlier token. Chaining ensures a hit means the entire prefix matched.
4 · Core idea

Hash, look up, touch, evict

Hash

hash((parent_hash, block_tokens, extra_keys)) for each full block (sha256 by default; xxhash options exist).

Look up

Walk the prompt's block hashes from the start; stop at the first miss.

Touch

Hit blocks get ref count +1 and leave the free queue so they cannot be evicted while in use.

Evict

Blocks with ref count 0 stay cached in the LRU free queue until reused for new data.

At a glance

Partial blocks are never cached; the last token is always recomputed to produce logits.

5 · How it works

Worked example: a shared system prompt

Notebook 02: every request = the same 70-token system prompt + a unique 30-token user message; requests processed in order with one cache.

Worked example

  1. 70 tokens = 4 full blocks (64 tokens) + 6 tokens in a partial block. Only the 4 full blocks can be cached.
  2. The first request misses; each of the next 19 reuses 64 tokens: 19 × 64 / 2,000 = 60.8% of all prompt tokens skip prefill (over 50 users: 62.7%).
  3. A 500-token shared prefix saves 91.7%; a 2,000-token one 96.6%; a 10-token one 0% (no full block).
  4. Changing the very first token changes every block hash after it: the whole prefix misses.
Long, stable prefixes put first in the prompt are where prefix caching pays off.
6 · Why it works

Why it is nearly free

Built on paging

Blocks and ref counts already exist; caching just keeps hashes on freed blocks.

Zero overhead on misses

V1 made prefix caching cheap enough to enable by default (V1 blog).

Big TTFT savings

Skipped prefill tokens directly cut time to first token.

Composable

Works with chunked prefill, preemption and speculative decoding through the same "computed tokens" counter.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Prefix caching caches responses."

It caches KV states of prompt prefixes; outputs are still generated fresh.

"Any shared substring is reused."

Only an identical prefix from the first token, in whole blocks, is reused.

"It must be enabled manually."

enable_prefix_caching defaults to True in vLLM V1 (v0.31.0).
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Put shared content first. System prompt, tools, documents, then the user turn.
  • Watch vllm:prefix_cache_hits / queries. The hit rate.
  • Route DP (data parallelism) traffic by prefix. Each data-parallel rank has its own cache.

⚠ Traps

  • Timestamps or IDs (identifiers) at the top of the prompt. Every request misses.
  • Expecting hits on partial blocks. Only full 16-token blocks are cached.
  • Assuming cached = permanent. Blocks are evicted LRU under memory pressure.

Check yourself

4 full blocks = 64.

Why is the last prompt token always recomputed?

The model needs to run at least one token through the network to produce the logits for the next token.

How should you structure prompts to maximise hits?

Put stable, shared content (system prompt, tools, documents) first and the variable part last; avoid timestamps or IDs early in the prompt.
9 · Key takeaway

Key takeaway

vLLM caches full KV blocks under chained hashes, so any request sharing an exact prefix skips its prefill; it is on by default in V1 and pays off most for long, stable prefixes.
Say it in 30 seconds

Automatic prefix caching reuses KV cache across requests. vLLM hashes each full sixteen-token block together with the hash of the block before it, so a block's hash stands for the entire prefix up to it. When a request arrives, the scheduler walks its block hashes from the start and reuses every matching block, prefilling only the rest plus the last token. Finished requests leave their blocks in a least-recently-used queue with their hashes intact until the memory is needed. In version one it is on by default. Put stable content like system prompts first.
