Deploying vLLM: from one GPU to many nodes

What a vLLM deployment physically looks like: one GPU (graphics processing unit), tensor parallelism inside a node, tensor × pipeline parallelism across nodes (Ray or multiprocessing), replicas behind a load balancer, data-parallel modes for MoE (Mixture of Experts) models, and the Kubernetes stacks (LeaderWorkerSet, production stack, llm-d) that run it.

What is the problem?A model has to fit in GPU memory with room left for the KV (key-value) cache, and then serve enough traffic. Some models fit on one GPU, some need a whole node, some need several nodes, and every choice changes how processes, networks and load balancing are laid out.
Core ideaSize one replica first: one GPU if it fits; else tensor parallelism across the GPUs of one NVLink node (or pipeline parallelism if there is no NVLink); else TP = GPUs per node, PP = number of nodes, run with Ray or --nnodes. Then add replicas for throughput: --data-parallel-size behind one endpoint, or independent servers behind a router. On Kubernetes, multi-node replicas are pod groups (LeaderWorkerSet); production stacks add routing, autoscaling and KV-cache offloading.
1 · Problem

One model, many possible layouts

The same model can be served on one GPU, eight GPUs in one server, or sixteen GPUs in two servers, and copied many times for traffic. Each layout changes the processes you run, the network you need and how requests are balanced.

Fit

Weights plus a useful KV cache must fit in the GPUs of one replica: 405B parameters in BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) are 810 GB before any cache.

Throughput

One replica serves a limited number of concurrent sequences; traffic beyond that needs more replicas.

Network

Inside a node GPUs talk over NVLink; across nodes over InfiniBand or Ethernet, roughly ten times slower.

2 · Limitation

Why the obvious setups disappoint

Tensor parallelism over TCP

TP all-reduces in every layer; across nodes without GPUDirect RDMA (remote direct memory access), NCCL (NVIDIA Collective Communications Library) falls back to sockets and throughput collapses.

One giant replica

Spreading a model that fits on one node over two adds pipeline transfers and failure points without adding much KV capacity per request.

Round-robin load balancing

Each replica has its own KV cache; spreading a conversation's turns across replicas throws away prefix reuse (Router deck).

3 · Your turn

Pick the layout

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

A model needs about 12 GPUs of memory. Each node has 8 H100s with NVLink, and nodes are connected by InfiniBand. What do the vLLM docs recommend for one replica?

B. Set TP to the GPUs per node and PP to the number of nodes: tensor parallelism's per-layer all-reduces stay on NVLink, and only pipeline activations cross the network. TP 16 also works with a fast interconnect, and data parallelism adds replicas, not memory.
4 · Core idea

Fit a replica, then copy it

Single GPU

If weights and enough KV cache fit, run one GPU per replica: no distributed overhead at all.

Single node, many GPUs

--tensor-parallel-size = GPUs needed (on NVLink). Without NVLink, or when GPUs do not divide the model evenly, use --pipeline-parallel-size instead. Multiprocessing is the default runtime.

Multi-node

TP = GPUs per node, PP = number of nodes. Start a Ray cluster (one vllm serve on any node sees all GPUs), or run vllm serve --nnodes 2 --node-rank i --master-addr … on each node, with --headless on workers.

Replicas

--data-parallel-size N runs N engines behind one endpoint (internal load balancing); --data-parallel-hybrid-lb gives each node its own endpoint; or run independent servers behind an external router. MoE models use data-parallel attention with expert-parallel MoE layers.

Networking checklist
Cross-node tensor parallelism needs InfiniBand or RoCE (remote direct memory access over Converged Ethernet) with GPUDirect RDMA: run with NCCL_DEBUG=TRACE and look for "NET/IB/GDRDMA", not "NET/Socket". Containers need host IPC (inter-process communication) or a large /dev/shm and the IPC_LOCK capability. Keep VLLM_HOST_IP on a private network: the docs warn the inter-node traffic is unencrypted and could be exploited to execute code. Pre-download the model to the same path on every node or use shared storage.

  






  

    5 · How it works
    
Worked example: Llama 3.1 405B on 8-GPU H100 nodes

    

    
80 GB per GPU, gpu_memory_utilization 0.92 (the v0.31.0 default). KV cache per token: 126 layers × 8 KV heads × 128 dims × 2 (K and V) × 2 bytes ≈ 504 KiB in BF16. Activation and CUDA-graph memory are ignored here.

    
Worked example
  1. BF16 weights: 405B × 2 bytes = 810 GB. One node offers 8 × 80 × 0.92 = 589 GB: it does not fit.
  2. Two nodes, TP 8 × PP 2: 1,178 GB usable − 810 GB = 368 GB for KV cache, about 710K tokens across the replica.
  3. FP8 (8-bit floating point) weights: 405 GB fit on one node with 184 GB left, about 355K tokens of BF16 KV (about 710K with an FP8 KV cache): TP 8, one node.
  4. Throughput: run several one-node FP8 replicas behind a router rather than one two-node BF16 replica; there is no cross-node traffic on the critical path.
Quantisation can turn a two-node replica into a one-node replica, which is simpler to run and avoids pipeline traffic between nodes.

  






  

    6 · Why it works
    
Why these layouts

    



      
Match traffic to links
Tensor parallelism all-reduces in every layer and needs NVLink; pipeline parallelism sends activations only at stage boundaries and tolerates the slower network.

      
Replicas scale linearly
Independent replicas share nothing at decode time, so throughput grows with their number; only the router has to be smart.

      
Smaller replicas are easier
A one-node replica fails, restarts and autoscales as one unit; a multi-node replica needs gang placement and fails if any node does.

      
MoE is different
Data-parallel attention with expert-parallel MoE layers keeps per-GPU KV caches independent while experts are shared; ranks must step together, so a coordinator runs dummy passes on idle ranks.

    

  






  

    7 · Misconceptions
    
Common misconceptions

    


Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.



      
"More GPUs per replica always means more throughput."

      
      
Past the point where the model and a healthy KV cache fit, extra tensor or pipeline parallelism adds communication; more replicas usually add more throughput.

    



      
"Multi-node vLLM needs Ray."

      
      
Ray is the default for multi-node, but v0.31.0 also runs multi-node with multiprocessing: --nnodes, --node-rank, --master-addr and --headless.

    



      
"A Kubernetes Service is enough to load-balance vLLM."

      
      
It works, but round-robin ignores each replica's KV cache and queue; the vLLM Router and llm-d route on cache and load (next deck).

    

  






  

    7 · Tricks and traps
    
Tricks and traps

    

    
Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

    

      
✓ Tricks
  • Read the startup log. vLLM prints "GPU KV cache size: N tokens" and "Maximum concurrency for L tokens per request: X×": add GPUs if these are too low.
  • TP inside, PP across. The documented default for multi-node: tensor_parallel_size = GPUs per node, pipeline_parallel_size = nodes.
  • No NVLink? Use PP. On PCIe-only (PCIe = Peripheral Component Interconnect Express, the standard expansion bus) GPUs (for example L40S) or uneven splits, the docs recommend pipeline parallelism instead of tensor parallelism.

      
⚠ Traps
  • Cross-node TP over TCP (Transmission Control Protocol). NCCL logs "NET/Socket" instead of "NET/IB/GDRDMA": tensor parallelism across nodes will crawl.
  • An open control network. The docs warn inter-node traffic is unencrypted and exploitable for code execution; keep VLLM_HOST_IP on a private network.
  • Counting max_num_seqs once. With data parallelism it applies per rank, while queue limits apply to the whole server.

What does --headless do in a multi-node launch?

      
      
It starts the engine and GPU workers on a node without an API (application programming interface) server; the head node (or a separate node) serves HTTP (Hypertext Transfer Protocol).

    



      
How do you check that cross-node NCCL traffic is using RDMA?

      
      
Run with NCCL_DEBUG=TRACE and look for "[send] via NET/IB/GDRDMA"; "NET/Socket" means plain TCP.

    

  






  

    9 · Key takeaway
    
Key takeaway

    

    
Fit one replica with TP inside a node and PP across nodes, then scale throughput with replicas behind a cache-aware router.

    
Say it in 30 seconds
A vLLM replica is one copy of the model. If it fits on one GPU, use one. If not, tensor-parallelise it across the GPUs of one NVLink node, or use pipeline parallelism without NVLink. If it needs several nodes, the documented default is TP = GPUs per node and PP = number of nodes, launched on a Ray cluster or with --nnodes and --headless. Throughput comes from more replicas: --data-parallel-size behind one endpoint (internal, hybrid or external load balancing), or independent servers behind a router. On Kubernetes, LeaderWorkerSet runs multi-node replicas as pod groups, and the production stack or llm-d add routing, autoscaling and KV offloading.

    
Single node: TP across NVLink GPUs; PP without NVLink
Multi-node: TP = GPUs per node, PP = nodes; Ray or --nnodes
Throughput: replicas: data parallel or a router
Kubernetes: LWS pod groups; production stack; llm-d
