Running and tuning vLLM

Serving with vllm serve: the flags that matter, the OpenAI-compatible endpoints, Prometheus metrics, benchmarking with vllm bench, and what to change when latency, throughput or preemptions look wrong.

What is the problem?Defaults are reasonable but every workload differs: long prompts or short, latency or throughput, many users or few. Tuning blind wastes GPUs (graphics processing units) or breaks latency targets.
Core ideaSize memory with --gpu-memory-utilization (0.92 by default in v0.31.0), concurrency with --max-num-seqs, step size with --max-num-batched-tokens, and context with --max-model-len. Watch /metrics (KV (key-value) usage, preemptions, queue, TTFT (time to first token), inter-token latency), and measure changes with vllm bench serve.

    5 · How it works
    
Worked example: fixing preemptions

    

    
vLLM's optimization guide: when KV cache space runs out, requests are preempted and recomputed, logging a warning and raising vllm:num_preemptions.

    
Worked example
  1. Symptom: vllm:num_preemptions climbing, vllm:kv_cache_usage_perc near 1.0, and tail latency spikes.
  2. Option 1 (from the guide): increase --gpu-memory-utilization to give the KV cache more of the GPU.
  3. Option 2: decrease --max-num-seqs or --max-num-batched-tokens to run fewer requests at once.
  4. Option 3: increase --tensor-parallel-size (weights per GPU shrink, KV room grows), or use --kv-cache-dtype fp8. Re-measure with vllm bench serve.
Preemption is a symptom of KV pressure; trade concurrency, memory share or parallelism against it, and measure.

  






  

    6 · Why it works
    
Why measure-then-tune works

    



      
Metrics name the bottleneck
KV pressure, scheduling caps and prefill load each show up in distinct metrics.

      
Built-in benchmarks
vllm bench serve replays realistic request streams against a running server.

      
Few knobs matter most
Memory share, concurrency, budget and parallelism cover most tuning.

      
Repeatable
Pin the version and flags; defaults are versioned in code.

    

  






  

    7 · Misconceptions
    
Common misconceptions

    


Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.



      
"Setting gpu_memory_utilization to 1.0 is best."

      
      
It leaves no headroom for activations spikes, other processes or fragmentation; out-of-memory errors follow.

    



      
"Higher max_num_seqs always means higher throughput."

      
      
Past the KV capacity it only causes preemption and recomputation.

    



      
"Benchmark numbers transfer between workloads."

      
      
Prompt and output length distributions change results dramatically.

    

  






  

    7 · Tricks and traps
    
Tricks and traps

    

    
Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

    

      
✓ Tricks
  • --max-model-len below the model maximum. Saves startup KV checks and memory if you never need full context.
  • vllm bench serve / throughput / latency. Built-in benchmarks.
  • Key metrics. kv_cache_usage_perc, num_requests_waiting, num_preemptions, time_to_first_token_seconds, inter_token_latency_seconds.

      
⚠ Traps
  • gpu-memory-utilization too high with other processes on the GPU. Out-of-memory at startup.
  • Tuning on a different workload. Benchmark with your real prompt/output lengths.
  • Ignoring max_num_batched_tokens. Larger raises throughput but also inter-token latency.

    9 · Key takeaway
    
Key takeaway

    

    
Run vllm serve with memory (0.92 default), concurrency, token-budget and parallelism flags; watch /metrics for KV usage, queueing and preemptions; and measure every change with vllm bench serve.

    
Say it in 30 seconds
Running vLLM well is a loop of configure, measure, adjust. The key flags set how much GPU memory vLLM may use, 0.92 by default in this version, how many requests run at once, how many tokens each step may schedule, the maximum context, parallelism, the KV-cache data type and speculative decoding. The server speaks the OpenAI API (application programming interface) and exports Prometheus metrics: KV-cache usage, running and waiting requests, preemptions, time to first token and inter-token latency. Preemptions mean KV pressure; waiting requests with free KV mean a scheduling cap. vllm bench serve measures the effect of each change.

    
Problem: one configuration does not fit every workload.
Core idea: flags → metrics → benchmark → adjust.
Defaults: mem 0.92, block 16, prefix caching and chunked prefill on.
