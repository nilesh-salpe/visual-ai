KV cache manager and PagedAttention

How vLLM stores the KV (key-value) cache: a pool of fixed-size blocks, per-request block tables, reference counts for sharing, and an LRU (least recently used) free queue, as implemented in vllm/v1/core.

What is the problem?Each request's KV cache grows token by token to an unknown final length. Reserving a contiguous maximum-length region per request wastes most of the memory.
Core ideaSplit GPU (graphics processing unit) KV memory into blocks of 16 tokens (the default block_size). Each request gets a block table mapping its logical blocks to physical ones, allocated on demand. Blocks carry reference counts so prefixes can be shared, and freed blocks enter an LRU free queue (in reverse order, tail first) so cached content survives as long as possible.

2 · Limitation

Why contiguous KV memory fails

Reservation

Unknown output lengths force reserving the maximum per request.

Fragmentation

Different reservation sizes leave unusable gaps between requests.

No sharing

Two requests with the same prefix store identical KV twice.

4 · Core idea

Blocks, tables, counts, queue

Block pool

All KV memory is pre-allocated at startup as blocks (size from CacheConfig, default 16).

Block table

Per request, the list of physical block ids for its logical blocks; kernels read KV through it.

Reference counts

A block may belong to several requests (shared prefix); it is freed when the count reaches 0.

LRU free queue

A doubly linked list of free blocks; allocation pops the front (least recently used); a request's blocks are freed in reverse order.

At a glance

PagedAttention kernels read K and V through the block table. Concept: Inference deck 05.

5 · How it works

Worked example: waste with and without paging

Notebook 01: 1,000 requests with final lengths uniform between 50 and 2,000 tokens; maximum length 2,048.

Worked example

  1. Reserving 2,048 contiguous slots per request: 49.7% of reserved KV memory is never used.
  2. Paging with 16-token blocks: only the unused tail of each request's last block is wasted: 0.75%.
  3. Block size trades waste against overhead: 8 → 0.34%, 32 → 1.53%, 128 → 5.95% waste.
  4. The PagedAttention paper measured 20.4%–38.2% of KV memory holding real token states in earlier systems, versus 96.3% in vLLM.
Paging turns KV memory from mostly reserved-but-empty into almost fully used, which directly raises batch size.
6 · Why it works

Why paging works

Allocate as you grow

Only the last block is partly empty, so waste is bounded by one block per request.

Bigger batches

Memory saved becomes room for more concurrent requests.

Sharing is cheap

A ref-count increment shares a prefix with no copying.

Eviction keeps value

LRU order with tail-first freeing keeps the most reusable prefixes longest.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"PagedAttention changes the attention math."

It computes the same attention; it only reads K and V from non-contiguous blocks.

"Smaller blocks are always better."

They waste less tail space but add table and kernel overhead; 16 is the default balance.

"Blocks are allocated for the maximum length up front."

They are allocated as tokens are scheduled; that is the point of paging.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • blocks = ⌈tokens / 16⌉. Default block_size 16 (CacheConfig.DEFAULT_BLOCK_SIZE).
  • Ref count > 1 = shared. Prefix caching and parallel sampling share blocks.
  • Watch vllm:kv_cache_usage_perc. High usage → preemptions.

⚠ Traps

  • Huge block sizes. More tail waste per request.
  • Assuming freed = gone. Freed blocks keep their hashes until evicted.
  • Ignoring per-layer cost. Each logical block exists in every layer.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

vLLM's default KV block size (CacheConfig.DEFAULT_BLOCK_SIZE)?

16 tokens.

Why free a request's blocks in reverse order?

So the tail blocks become least recently used and are evicted first, keeping the more widely shared head (prefix) blocks cached longer.

What makes sharing a prefix free?

Reference counts: a second request just points its block table at the same blocks and increments their counts.
9 · Key takeaway

Key takeaway

vLLM pages the KV cache into 16-token blocks with per-request block tables, reference counts for sharing and an LRU free queue, cutting KV waste from about half to under 1% in the notebook.
Say it in 30 seconds

The KV cache grows with every generated token to a length nobody knows in advance, so reserving contiguous space per request wastes most of it. vLLM pre-allocates all KV memory as a pool of blocks, sixteen tokens each by default, and gives every request a block table that maps its logical blocks to physical ones, allocated only as tokens are scheduled. Blocks have reference counts, so requests with the same prefix can share them, and freed blocks join a least-recently-used queue, tail first, so cached prefixes survive longest. In notebook one this cut waste from about fifty percent to under one percent.
