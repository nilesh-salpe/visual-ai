Sandboxing agents

Running agent-written code and commands safely: the threat model, the isolation spectrum from syscall filters to microVMs, and the design of a per-task sandbox with no secrets inside and network access only through a proxy.

What is the problem?Coding and computer-use agents run code they wrote a moment ago, often after reading untrusted text. Without isolation, one injected instruction can read SSH (Secure Shell) keys, delete files, mine crypto or send data anywhere, with your credentials.
Core ideaRun every task in a sandbox with two boundaries: filesystem (only the task's files) and network (egress only through a proxy that enforces an allowlist). Keep secrets outside: a proxy adds real credentials to approved requests. Pick the isolation strength to match the risk: process sandboxes (bubblewrap, Seatbelt), containers, a user-space kernel (gVisor) or a microVM (Firecracker: under 125 ms to boot, under 5 MiB overhead).

1 · Problem

Agents run untrusted code by design

Untrusted inputs

Web pages, issues and documents can carry instructions that the model may follow.

Real side effects

Shell, package installs and file writes act on whatever machine the agent runs on.

Exfiltration

Anthropic's point: without network isolation a compromised agent could send out files such as SSH keys; without filesystem isolation it could escape the sandbox and gain network access.

Approval fatigue

Asking a human before every command is slow and people stop reading; Anthropic reports sandboxing cut permission prompts by 84% in internal use.

2 · Core idea

Two boundaries, secrets outside

Filesystem

The agent sees only its working directory (and read-only system files); writes elsewhere fail.

Network

All traffic leaves through a proxy outside the sandbox that allows listed domains and asks about new ones.

Credentials

Tokens never enter the sandbox: a proxy checks a scoped credential and attaches the real token (Anthropic's git proxy for Claude Code on the web).

Resources

CPU (central processing unit), memory, disk, process count and wall-clock limits stop runaway or abusive jobs.

Isolation Mechanism Strength Start-up and cost
Syscall filter (seccomp) BPF (Berkeley Packet Filter) filter on system calls shrinks the kernel attack surface; the kernel docs say it "isn't a sandbox" alone negligible
Process sandbox (bubblewrap, Seatbelt) namespaces / OS (operating system) sandbox profiles good for a local agent on a developer machine milliseconds
Container namespaces, cgroups, shared host kernel kernel bugs can break out sub-second
User-space kernel (gVisor) Sentry services syscalls; does not pass them to the host much smaller host kernel surface slower syscall-heavy work; some incompatibilities
MicroVM (Firecracker) KVM (Kernel-based Virtual Machine) virtual machine with a minimal device model hardware-virtualisation boundary < 125 ms boot, < 5 MiB overhead, up to 150 microVMs/s per host

5 · Trade-offs

Trade-offs

Choice Benefit Cost
Stronger isolation (microVM) protects against kernel exploits more start-up time, memory and operational work
Lighter isolation (process / container) fast and cheap; good on developer machines a shared kernel is the boundary
No network no exfiltration at all cannot install packages or call APIs (application programming interfaces)
Allowlisted egress useful and contained allowlisted domains can still be abused (e.g. upload to a permitted site)
Long-lived sandboxes warm caches, faster tasks state and secrets accumulate; cross-task leakage
6 · Failure modes

Failure modes

Failure Symptom Mitigation
Secrets inside the sandbox tokens in env vars or files get exfiltrated credential proxies; short-lived scoped tokens
Exfiltration through allowed domains data posted to a permitted service narrow allowlists; inspect or block uploads; per-task policies
Escape via kernel bug container breakout gVisor or microVMs for untrusted code; patch hosts
Resource abuse crypto-mining, fork bombs, disk fill cgroups limits, timeouts, quotas
Persistence between tasks one task's files visible to the next fresh sandbox per task; wipe or snapshot-restore
7 · Challenges in production

In production

Fast start

Users wait on sandbox creation: keep warm pools and restore from snapshots.

Audit everything

Log commands, network requests and denied actions per task for incident response.

Policy per task

Different tasks need different domains and files; generate the policy from the task, not one global list.

Defence in depth

Sandboxing complements least-privilege tools, approvals for risky actions and prompt-injection defences.

Filesystem and network isolation built on Linux bubblewrap and macOS Seatbelt; egress through a proxy outside the sandbox with allowed domains; in the cloud version credentials stay outside the sandbox and a git proxy attaches the real token.

Firecracker: Lightweight Virtualization for Serverless Applications
Agache et al. · NSDI 2020

A minimal KVM-based virtual machine monitor for multi-tenant serverless workloads, used by AWS (Amazon Web Services) Lambda and Fargate.

Remember: < 125 ms boot, < 5 MiB overhead per microVM, up to 150 microVMs per second per host (firecracker-microvm.github.io)
gVisor documentation
gVisor project · gvisor.dev 2026

An application kernel in user space: the Sentry services system calls without passing them to the host kernel, a Gofer mediates file access, and runsc plugs into Docker and Kubernetes; costs some compatibility and syscall-heavy performance.

Seccomp BPF (secure computing with filters)
Linux kernel documentation · docs.kernel.org 2026

A process installs a BPF filter on system calls and their arguments to reduce the kernel attack surface; the docs note system call filtering "isn't a sandbox" by itself.
