Attention Is All You Need · 04

Queries, keys and values

How query-key compatibility produces attention weights, and how those weights combine value vectors into a context-aware output.

What is the problem?A token must decide which tokens are relevant and what to take from them. One embedding vector can't serve all three roles well: asking, being matched, and supplying content.
Core ideaProject each token three ways: a query (what I'm looking for), a key (what I can be matched on) and a value (what I contribute). Query·key gives the weights, and the weights combine the values.
1 · Problem

Searching needs a question, an index and the content itself

Think of a library. You arrive with a question, you compare it with each book's label, and you take content from the books that match. If a token's raw embedding had to be the question, the label and the content all at once, it couldn't specialize for any of those roles.

"it" should ask for an animate referent, "animal" should be findable as animate, and what "animal" passes on can be different again. These are three different jobs.
2 · Limitation

Scoring with the raw embeddings, xi·xj, doesn't work well

The simplest idea is to score each pair of tokens by the dot product of their embeddings. Below is that score matrix for the toy embeddings used in this deck.

Symmetric

xi·xj = xj·xi. If "it" looks for "animal", "animal" must look for "it" just as strongly.

Each word matches itself best

The diagonal dominates: "it" scores 1.02 with itself and only 0.10 with "animal".

One vector, three jobs

What a word is matched on and what it passes on are forced to be the same vector.

4 · Core idea

Three learned projections of the same token: q = xWQ, k = xWK, v = xWV

5 · How it works

Compatibility → weights → weighted sum of values

The query of the selected token is compared with every key by dot product. The scores are scaled by 1/√dk and passed through a softmax to give weights that sum to 1. The output is the weighted sum of the values.

Because q(it) is aligned with k(animal), "it" ends up taking most of its output from v(animal). That is the attention function from §3.2, computed live.
5 · How it works

All tokens at once, in matrix form

Stack the token vectors into X (n × dmodel). Then Q = XWQ, K = XWK and V = XWV are three matrix multiplications, and every query is matched against every key in one product, QKᵀ.

Shapes in the paper (per head): X: n × 512 · WQ, WK: 512 × 64 · WV: 512 × 64 · Q, K, V: n × 64 · QKᵀ: n × n. Deck 06 shows how 8 such heads run side by side.
5 · How it works

Worked example: sizes per head (base model)

d_model = 512, h = 8 heads, so d_k = d_v = 512 / 8 = 64. A 10-token sentence.

Worked example

  1. Per head, W_Q, W_K and W_V are each 512 × 64.
  2. Q, K, V for the sentence: [10, 64] each; scores QKᵀ: [10, 10].
  3. Parameters per head: 3 × 512 × 64 = 98,304; across 8 heads plus W_O (512 × 512): 1,048,576.
  4. Without separate projections, a token's query and key would be the same vector, forcing symmetric matches.
Separate W_Q and W_K let "what I seek" differ from "what I offer"; W_V decouples matching from content.
5 · How it works from the paper · §3.2, §3.2.1

The paper's wording

§3.2: "An attention function can be described as mapping a query and a set of key-value pairs to an output, where the query, keys, values, and output are all vectors. The output is computed as a weighted sum of the values, where the weight assigned to each value is computed by a compatibility function of the query with the corresponding key."
§3.2.1: the input is queries and keys of dimension dk and values of dimension dv. In practice the queries are packed into a matrix Q, and the keys and values into matrices K and V.
Where Q, K, V come from (§3.2.3): in self-attention, all three come from the same previous layer. In encoder-decoder attention, Q comes from the decoder while K and V come from the encoder output (deck 08).
6 · Why it works

Why separate Q, K and V work

Asymmetric matching

qi·kj ≠ qj·ki in general, so "it → animal" can be strong while "animal → it" is weak.

Specialized roles

Keys can expose the features worth matching on (animate, place). Queries can ask for exactly those features.

Content decoupled from matching

Values carry what is passed on, which can differ from what made the match.

The matching does real work

Table 3 (B): shrinking the key size dk to 16 drops dev BLEU (Bilingual Evaluation Understudy, an n-gram overlap score for translation) from 25.8 to 25.1. "Determining compatibility is not easy" (§6.2).

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Q, K and V are three different inputs."

In self-attention all three are projections of the same input X. Only in encoder-decoder attention do they come from different places (Q from the decoder, K and V from the encoder).

"Keys and values are the same thing."

They come from the same tokens but use different projections. The key decides how much weight a token gets; the value is what actually gets passed on.

"Attention picks the single best-matching value."

It outputs a weighted average of all values. Softmax gives every key some weight; in the toy, "it" still takes 15% from "street".
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • d_k = d_model / h. 64 in the base model.
  • Attention params = 4·d_model². Q, K, V and output projections, independent of h.
  • Matrix form. softmax(QKᵀ/√d_k)V for all tokens at once.

⚠ Traps

  • Thinking K and V are the same. Same input, different learned projections.
  • Using d_model for scaling. Divide by √d_k (per-head size), not √d_model.
  • Forgetting W_O. Head outputs are concatenated, then projected.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

In the base model, what is the shape of one head's WQ?

512 × 64: dmodel × dk, with dk = 512 / 8 heads (§3.2.2).

In encoder-decoder attention, which come from the encoder output?

Keys and values. Queries come from the decoder (§3.2.3).

In the toy, q(it)·k(animal) is the highest score. Why does "it" still give 15% of its weight to "street"?

Softmax never outputs exact zeros for finite scores. Every key gets some weight, in proportion to exp(score / √dk).
9 · Key takeaway

Key takeaway

Queries ask, keys answer, values deliver. softmax(q·k / √dk) decides how much of each value a token takes.
Say it in 30 seconds

Each token's vector is projected three ways by learned matrices: a query (what it is looking for), a key (what it can be matched on) and a value (what it passes on). Compatibility is the dot product of a query with each key, scaled by 1/√dk and softmaxed into weights; the output is the weighted sum of values. Separate projections make matching asymmetric and let content differ from the features used for matching.

Problem: one embedding can't play all three roles: asking, being matched, and supplying content.
Core idea: learned projections give each token a query, a key and a value. softmax(q·k / √dk) weights the values to produce the output.
