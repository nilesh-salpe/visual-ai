Attention Is All You Need · 04

Queries, keys and values

How query-key compatibility produces attention weights, and how those weights combine value vectors into a context-aware output.

What is the problem?A token must decide which tokens are relevant and what to take from them. One embedding vector can't serve all three roles well: asking, being matched, and supplying content.
Core ideaProject each token three ways: a query (what I'm looking for), a key (what I can be matched on) and a value (what I contribute). Query·key gives the weights, and the weights combine the values.
① What is the problem?

Searching needs a question, an index and the content itself

Think of a library. You arrive with a question, you compare it with each book's label, and you take content from the books that match. If a token's raw embedding had to be the question, the label and the content all at once, it couldn't specialize for any of those roles.

"it" should ask for an animate referent, "animal" should be findable as animate, and what "animal" passes on can be different again. These are three different jobs.
② Core idea

Three learned projections of the same token: q = xWQ, k = xWK, v = xWV

Every token's vector x is multiplied by three learned matrices. The toy model below has dmodel = 4 and dk = 3; the paper uses 512 and 64. All numbers are computed live. Pick a token.

Toy features of x: [animate, place, pronoun, state]. The projection weights are hand-set so the example is readable; in the paper they are learned.

② Core idea

Compatibility → weights → weighted sum of values

The query of the selected token is compared with every key by dot product. The scores are scaled by 1/√dk and passed through a softmax to give weights that sum to 1. The output is the weighted sum of the values.

Because q(it) is aligned with k(animal), "it" ends up taking most of its output from v(animal). That is the attention function from §3.2, computed live.
② Core idea

All tokens at once, in matrix form

Stack the token vectors into X (n × dmodel). Then Q = XWQ, K = XWK and V = XWV are three matrix multiplications, and every query is matched against every key in one product, QKᵀ.

Shapes in the paper (per head): X: n × 512 · WQ, WK: 512 × 64 · WV: 512 × 64 · Q, K, V: n × 64 · QKᵀ: n × n. Deck 06 shows how 8 such heads run side by side.
In the paper · §3.2, §3.2.1

The paper's wording

§3.2: "An attention function can be described as mapping a query and a set of key-value pairs to an output, where the query, keys, values, and output are all vectors. The output is computed as a weighted sum of the values, where the weight assigned to each value is computed by a compatibility function of the query with the corresponding key."
§3.2.1: the input is queries and keys of dimension dk and values of dimension dv. In practice the queries are packed into a matrix Q, and the keys and values into matrices K and V.
Where Q, K, V come from (§3.2.3): in self-attention, all three come from the same previous layer. In encoder-decoder attention, Q comes from the decoder while K and V come from the encoder output (deck 08).
Recap

Q, K, V in two lines

Problem: one embedding can't play all three roles: asking, being matched, and supplying content.
Core idea: learned projections give each token a query, a key and a value. softmax(q·k / √dk) weights the values to produce the output.
