Serving LLMs for agent workloads

Why agent traffic stresses inference servers differently from chat, and the server-side techniques that help: prefix reuse across turns, constrained decoding for tool calls, program-aware scheduling, and smaller models.

What is the problem?An agent task is a program of many dependent calls sharing a long, growing prefix, separated by tool executions, each ending in strict JSON (JavaScript Object Notation). Request-level schedulers see unrelated requests: they recompute shared prefixes, let one long program block others (head-of-line blocking) and optimise per-request latency when the user waits for the whole task.
Core ideaServe the program, not the request: reuse KV (key-value) cache across turns (SGLang's RadixAttention, up to 6.4× throughput), constrain decoding to the tool schema cheaply (XGrammar, near-zero overhead), schedule with program context (Autellix, 4-15× program throughput vs vLLM at the same latency), and use smaller or distilled models and speculative decoding where steps are easy.

1 · Problem

Agent traffic is not chat traffic

Repeated prefixes

Every turn resends system prompt, tools and history; without reuse the server prefills them again.

Strict outputs

Tool calls must parse; one malformed argument costs a full extra turn.

Dependent calls

Call n+1 waits for call n and a tool run; latency adds up across the program.

Head-of-line blocking

Autellix found programs suffer long cumulative waits, blocked at both the request and the program level.

2 · Core idea

Make the server program-aware

Prefix reuse

Keep KV blocks of earlier turns and match the longest cached prefix (vLLM automatic prefix caching; SGLang's radix tree).

Constrained decoding

Mask tokens that would break the JSON schema or grammar. XGrammar prechecks context-independent tokens and checks the rest with a persistent stack: up to 100× faster than earlier engines.

Program-level scheduling

Autellix prioritises calls using each program's completed calls; Parrot's Semantic Variables expose data flow between requests.

Right-sized models

Distilled or small models for sub-agents and easy steps; speculative decoding for latency at low batch sizes.

5 · Trade-offs

Trade-offs

Choice Benefit Cost
Keep KV during tool calls next turn is nearly free to prefill GPU (graphics processing unit) memory held by idle programs
Evict or offload KV room for more active requests recompute or transfer when the program returns
Constrained decoding tool calls always parse Let Me Speak Freely?: strict format restrictions can degrade reasoning; let the model think before the constrained part
Prefix-affinity routing high cache hit rates uneven load across replicas
Speculative decoding lower latency at small batch less benefit at high batch; draft model memory
Smaller models for sub-agents cheaper, faster steps quality risk on hard steps (route them up)
6 · Failure modes

Failure modes

Failure Symptom Mitigation
Cache thrash hit rate collapses as concurrent agents exceed KV capacity admission control, offload tiers, affinity routing
Prefix changes a timestamp or reordered tools at the top kills reuse stable prefixes; dynamic content at the end
Grammar compile stalls first request with a new schema is slow cache compiled grammars; precompile known tool schemas
Valid but wrong arguments JSON parses, values are nonsense schema enums and validation in the tool layer; constrained decoding only fixes syntax
Long programs starve short ones quick tasks wait behind huge ones program-aware fair scheduling (Autellix)
7 · Challenges in production

In production

Measure per task

Report task latency, tokens per task and prefix-cache hit rate, not just tokens per second.

Affinity

Route a session to the replica that holds its cache, with spillover when it is overloaded.

Capacity for idle KV

Size memory for programs waiting on tools, not only for active decoding.

Same engine features as hosted APIs

Self-hosting means owning prefix caching, structured outputs and tool parsing yourself (see the vLLM decks).

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

SGLang: Efficient Execution of Structured Language Model Programs
Zheng et al. · NeurIPS 2024

A runtime and frontend for multi-call LLM (large language model) programs; RadixAttention keeps KV caches in a radix tree so shared prefixes are reused across requests automatically.

Remember: up to 6.4× higher throughput
XGrammar: Flexible and Efficient Structured Generation Engine for Large Language Models
Dong et al. · MLSys 2025

Constrained decoding with context-free grammars: context-independent tokens are prechecked into masks, only context-dependent tokens are checked at runtime with a persistent stack, and mask computation overlaps GPU work.

Remember: up to 100× faster grammar execution; near-zero overhead end to end
Efficient Guided Generation for Large Language Models
Willard & Louf · arXiv 2023

Guided generation as finite-state-machine transitions with an index over the vocabulary, enforcing regular expressions and grammars (the Outlines library).

Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models
Tam et al. · EMNLP Industry 2024

Format restrictions such as forced JSON can significantly reduce reasoning performance, and stricter constraints degrade it more.

Autellix: An Efficient Serving Engine for LLM Agents as General Programs
Luo et al. · arXiv 2025

Treats agent programs as first-class units; schedulers preempt and prioritise calls using each program's completed calls to avoid head-of-line blocking.

Remember: 4-15× higher program throughput at the same latency vs vLLM
Parrot: Efficient Serving of LLM-based Applications with Semantic Variable
Lin et al. · OSDI 2024

Semantic Variables expose the data flow between an application's LLM requests so the service can schedule and share prefixes across them.

Remember: up to an order-of-magnitude end-to-end improvement
Automatic Prefix Caching (design)
vLLM documentation · docs.vllm.ai 2026

Each KV block is hashed with its tokens and the prefix before it; blocks are reference-counted, freed blocks are evicted in LRU (least recently used) order, and cache hits skip prefill.
