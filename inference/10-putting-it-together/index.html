Putting it together: diagnosing a serving system

How the techniques combine in real engines, and a symptom → cause → fix playbook for the questions you'll actually face.

2 · Limitation

Tuning without measuring goes wrong

Wrong knob

Adding GPUs when the problem is queueing, or quantizing when the problem is prefill compute.

Averages

Tuning mean latency while the p99 TPOT breaks the SLO.

One phase

Fixing TTFT by enlarging prefill iterations, which spikes everyone's TPOT.

4 · Core idea

Measure, locate, fix

Measure

TTFT and TPOT percentiles, goodput at the SLO, running batch size, queue length, KV-cache utilization, prefix-cache hit rate, GPU compute and bandwidth utilization.

Locate

Which phase (prefill or decode)? Which resource (compute, HBM (high-bandwidth memory) bandwidth, KV capacity, interconnect, scheduler)?

Fix

Apply the technique matched to that phase and resource (table on the first slide).

Verify

Re-measure goodput at the SLO, not just mean throughput.

At a glance

Diagnose by phase (prefill or decode) and resource (compute, memory bandwidth, memory capacity, network).

5 · How it works

The playbook: symptom → cause → fix

Decide the cause before revealing.

TPOT spikes whenever long prompts arrive; TTFT is fine.

Prefill interfering with decode. Use chunked prefill with a token budget (04), or disaggregate (09).

Batch size stays small although many requests are queued; KV memory is "full".

KV fragmentation or over-reservation, or KV too large. Use paged KV (05), GQA-class (GQA = grouped-query attention) models (02), FP8 (8-bit floating point) KV (07), or shorter maximum context.

Single-user latency is too slow even at batch 1; GPUs aren't compute-bound.

Memory-bound sequential decode. Use speculative decoding (06), weight quantization (07), or more TP (tensor parallelism) within NVLink (08).

Many requests share a long system prompt, and TTFT is high.

Recomputing the same prefix. Turn on prefix caching (05).

After moving to 16-way TP across two nodes, TPOT got worse.

All-reduce over the network is on the critical path. Keep TP within the NVLink domain and use pipeline or data parallelism across nodes (08).

5 · How it works

Worked example: why is the batch stuck at ~100?

Llama-3-8B in BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) on one 80 GB H100, 4,096-token contexts. The batch never grows past ~100 and GPU compute utilization is low.

Worked example

  1. Weights: 16.06 GB. Leave ~6 GB for activations and the runtime → 58 GB for KV.
  2. KV per sequence: 2 × 32 layers × 8 KV heads × 128 × 2 bytes × 4,096 = 0.50 GiB.
  3. Maximum batch ≈ 58 GB / 0.54 GB ≈ 107 sequences: memory capacity is the bottleneck, not compute.
  4. Fixes: FP8 KV halves it → ~215 sequences; paging removes fragmentation; prefix caching shares system prompts; or add GPUs.
Measure → the KV pool is full → resource = memory capacity in decode → apply KV-shrinking techniques, then re-measure TPOT and goodput.
6 · Why it works

Why a phase-and-resource view works

The physics is simple

Prefill is compute-bound and decode is bandwidth- and capacity-bound (GPU deck 02 roofline). Almost every symptom maps to one of a few resources.

Techniques compose

Continuous batching, paged KV, chunked prefill, quantization and speculative decoding stack, because each targets a different bottleneck.

Goodput keeps you honest

Measuring throughput only within the SLO stops you from "optimizing" by breaking latency.

Interviews test exactly this

"Our TTFT doubled after launch: what do you check?" is a phase-and-resource question.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"One engine or setting is best for every workload."

The right configuration depends on prompt and output lengths, sharing, SLOs, model size and interconnect. Measure goodput on your traffic.

"Higher GPU utilization means the server is healthy."

Utilization can be high while queues grow and SLOs fail. Track goodput and tail latency.

"Optimizations are independent, so stack them all."

Some trade against each other: bigger chunk budgets raise TPOT, more TP raises communication, speculative decoding uses compute that big batches also want.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Classify every symptom by phase × resource. High TTFT → prefill compute or queueing; high TPOT → decode bandwidth or interference.
  • Read utilization correctly. Low compute utilization in decode is normal; low batch with a full KV pool means capacity-bound.
  • Change one thing at a time. Many techniques interact (chunk size vs TPOT, quantization vs accuracy).

⚠ Traps

  • Tuning before measuring. Adding speculative decoding to a capacity-bound server does little.
  • Optimizing averages. Tail latency (p99) is usually what violates SLOs.
  • Benchmarking an unrealistic mix. Prompt and output length distributions decide which bottleneck you hit.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

TPOT spikes only when long prompts arrive. Which technique targets that first?

Chunked prefill (or disaggregation).

Name four metrics you'd check first on a struggling LLM (large language model) server.

TTFT and TPOT percentiles, goodput at the SLO, running batch size and queue length, and KV-cache utilization. Prefix-hit rate and GPU bandwidth utilization are good next ones.

Why might speculative decoding help less at very high batch sizes?

At large batch, decode moves toward compute-bound, so spare compute for verifying drafts shrinks. Speculative decoding exploits the memory-bound regime.
9 · Key takeaway

Key takeaway

Diagnose by phase and resource: measure TTFT, TPOT, goodput, batch, queue and KV, find whether prefill or decode is short of compute, bandwidth or memory, then apply the matching technique.
Say it in 30 seconds

Each serving technique fixes one bottleneck: KV cache for recompute, continuous batching for idle slots, chunked prefill and disaggregation for prefill-decode interference, paging and prefix caching for KV memory, speculative decoding, quantization and tensor parallelism for decode latency. In practice you measure tail TTFT and TPOT, goodput at the SLO, batch size, queue length and KV utilization; decide whether prefill or decode is limited by compute, bandwidth, memory or interconnect; then apply the matching fix and re-measure goodput.

Problem: many knobs; tuning without measurement breaks SLOs or wastes GPUs.

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Efficient Memory Management for Large Language Model Serving with PagedAttention
Kwon et al. · SOSP 2023

Stores the KV cache in fixed-size blocks mapped by a block table, like virtual memory pages, giving near-zero fragmentation and sharing with copy-on-write. The basis of vLLM.

Remember: 2–4× throughput vs FasterTransformer and Orca at the same latency
SGLang: Efficient Execution of Structured Language Model Programs
Zheng et al. · NeurIPS 2024

A runtime and frontend for multi-call LLM programs; RadixAttention keeps KV caches in a radix tree so shared prefixes are reused across requests automatically.

Remember: up to 6.4× higher throughput
Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve
Agrawal et al. · OSDI 2024

Chunked prefills plus stall-free scheduling: new requests are added without pausing ongoing decodes, so throughput rises without TPOT spikes.

Remember: 2.6× serving capacity (Mistral-7B, 1 A100) and up to 3.7× (Yi-34B, 2 A100s) vs vLLM; up to 5.6× with pipeline parallelism (Falcon-180B)
DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving
Zhong et al. · OSDI 2024

Defines serving quality as goodput, the request rate served within both TTFT and TPOT targets, and runs prefill and decode on separate GPUs so they stop interfering.

Remember: 7.4× more requests or 12.6× tighter SLO than colocated systems
