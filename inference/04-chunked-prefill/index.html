Chunked prefill

Splitting long prompts into chunks so they share each iteration with ongoing decodes instead of stalling them (Sarathi-Serve, 2024).

What is the problem?When a long prompt arrives, its prefill either stalls every running decode or waits behind them. Either throughput or latency suffers.
Core ideaGive each iteration a token budget: decodes go first (stall-free), and the rest of the budget goes to chunks of waiting prefills.
1 · Problem

Prefill and decode compete for the same iterations

Prefill

Hundreds to thousands of tokens in one pass. Compute-heavy and slow per iteration.

Decode

One token per running request. Fast, but uses little of the GPU's compute.

Naively interleaving the two makes it hard to get high throughput and low latency at the same time (Sarathi-Serve).
2 · Limitation

Two naive policies, two failure modes

Prefill-first

Run a new prompt's whole prefill as soon as it arrives. Every running decode stalls behind that long iteration, causing TPOT spikes.

Decode-first

Finish decodes before admitting prefills. New requests wait, which hurts TTFT, and decode-only batches underuse compute.

4 · Core idea

Chunked prefills + stall-free scheduling

Token budget

Each iteration processes at most B tokens in total, which bounds iteration time and therefore TPOT.

Decodes first

Every running request gets its token, so decodes never stall.

Prefill chunks fill the rest

Waiting prompts are processed in near-equal chunks. The first output token appears when the last chunk finishes.

6 · Why it works

Why it works

Predictable TPOT

Every iteration is bounded by B tokens, so no decode waits behind a huge prefill.

Better utilization

Decodes ride along with compute-heavy prefill chunks, filling the GPU's otherwise idle compute.

One knob

A smaller B means smoother TPOT but more iterations to finish a long prompt (higher TTFT), and a larger B the reverse.

Measured (vs vLLM, under latency SLOs)

Sarathi-Serve: 2.6× capacity (Mistral-7B, 1×A100), up to 3.7× (Yi-34B, 2×A100), up to 5.6× (Falcon-180B with pipeline parallelism).

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Chunking changes the model's output."

No. Attention over earlier chunks uses the KV cache, so the result is the same as a single prefill pass.

"A bigger budget is always better."

A bigger B finishes prompts sooner but allows longer iterations, which brings back TPOT spikes. It's a trade-off.

"Chunked prefill only helps long prompts."

It also raises utilization, because decode-only iterations underuse compute and the chunks fill that gap.

9 · Key takeaway

Key takeaway

Chunked prefill bounds every iteration with a token budget: decodes go first and prefill chunks fill the rest, so long prompts never stall streaming users.
Say it in 30 seconds
