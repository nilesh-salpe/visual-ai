LLM Inference & Serving · 01

The inference workload

What happens when a request hits an LLM (large language model) server: the two phases, the metrics users feel and the ones operators pay for, and why a single "tokens per second" number misleads.

What is the problem?Users care about latency, operators care about throughput, and the two pull in opposite directions.
Core ideaSeparate the work into prefill (the whole prompt at once) and decode (one token at a time). Measure TTFT (time to first token), TPOT (time per output token), and goodput: throughput that still meets latency targets.
1 · Problem

One request, two very different phases

A chat request has a prompt of P tokens and generates O output tokens. The server first processes the whole prompt in one pass, which is prefill. Then it generates output tokens one at a time, each depending on the last, which is decode.

Time to first token comes from prefill. The steady stream of tokens after that comes from decode. They are limited by different resources (see the roofline in GPU (graphics processing unit) deck 02).
2 · Limitation

Why "tokens per second" isn't enough

Throughput hides latency

A huge batch maximizes tokens/s for the server while each user waits longer per token.

Averages hide tails

A good mean latency can coexist with a p99 that breaks the product experience.

Two phases, one number

Prefill speed (prompt tokens/s) and decode speed (output tokens/s) behave differently and need different fixes.

3 · Your turn

Pick the right metric

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

Which metric captures "how much load the server handles while still meeting its latency targets"?

B. DistServe defines goodput as the request rate a system can serve while meeting its time-to-first-token and time-per-output-token targets. Peak tokens/s ignores latency, utilization can be high while users wait, and averages hide tails.
4 · Core idea

The four numbers that describe a serving system

TTFT: time to first token

Queueing plus prefill of the prompt. Grows with prompt length. Users feel it as "how long until it starts typing".

TPOT: time per output token

Time per decode step, also called inter-token latency. Users feel it as streaming speed.

Throughput

Tokens (or requests) per second across all users. This is what the operator pays for.

Goodput

Throughput counted only while TTFT and TPOT stay within their SLOs (service-level objectives). It's the metric that matters (DistServe, OSDI '24).

At a glance

Every request has one compute-heavy prefill, then many memory-heavy decode steps.

5 · How it works

5 · How it works

Worked example: latency of one request

Llama-3-8B (8.03B parameters, BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats)) on one H100 SXM (NVIDIA's socketed module form factor for data-center graphics processors). A 2,000-token prompt and a 300-token answer, at batch size 1. Spec sheet: 989 TFLOP (trillion floating-point operations)/s dense BF16, 3.35 TB/s HBM (high-bandwidth memory). Assume prefill reaches 40% of peak.

Worked example

  1. Prefill compute ≈ 2 × parameters × prompt tokens = 2 × 8.03B × 2,000 = 32.1 TFLOP.
  2. TTFT ≈ 32.1 TFLOP ÷ (0.4 × 989 TFLOP/s) ≈ 81 ms (plus any queueing).
  3. Each decode step must read all weights once: 2 bytes × 8.03B = 16.1 GB at 3.35 TB/s ≈ 4.8 ms. That is the TPOT floor at batch 1.
  4. Decode total ≈ 299 more tokens × 4.8 ms ≈ 1.43 s.
End-to-end ≈ 0.08 + 1.43 ≈ 1.51 s, and decode is 95% of it. At batch 1 the GPU does ~3 TFLOP/s during decode, a few percent of peak, which is why batching (deck 03) matters.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Tokens per second tells you how good a server is."

Not on its own. Without latency targets it rewards huge batches that make each user wait. Use goodput under SLOs.

"A bigger batch is always better."

Throughput rises, but so does TPOT. Past the SLO limit, extra batch size adds no goodput.

"TTFT and TPOT have the same bottleneck."

TTFT is mostly prefill compute plus queueing. TPOT is mostly memory bandwidth per decode step. They need different fixes.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Forward FLOPs (floating-point operations) ≈ 2 × parameters per token. Prefill cost ≈ 2·N·prompt_tokens; good to within the attention term for normal contexts.
  • Decode floor ≈ bytes read ÷ HBM bandwidth. At small batch, TPOT ≈ (weight bytes + KV bytes) / bandwidth, not FLOPs / peak.
  • Latency ≈ TTFT + (output − 1) × TPOT. Long answers are dominated by decode; long prompts by prefill.
  • Quote goodput, not throughput. Requests per second that meet both the TTFT and TPOT SLOs.

⚠ Traps

  • Comparing tokens/s across workloads. Prompt-heavy and output-heavy mixes give very different numbers on the same server.
  • Averages instead of percentiles. p99 TTFT and TPOT are what break products; means hide them.
  • Forgetting the queue. Measured TTFT includes waiting time; under load it can dominate prefill.
  • Counting prompt tokens as generated. Input tokens/s and output tokens/s are different metrics with different costs.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

Prompt 2,000 tokens at a prefill speed of 20,000 tokens/s, then 500 output tokens at 30 ms TPOT. Roughly what are TTFT and total latency?

TTFT ≈ 2,000 / 20,000 = 0.1 s. Decode ≈ 500 × 0.03 = 15 s, so the total is about 15.1 s. Decode dominates long answers.

Which definition of goodput does DistServe use?

Request rate within the latency SLOs.

Why does batching help decode throughput so much?

Each decode step must read all the weights anyway. A larger batch reuses that one read for many sequences, moving decode from memory-bound toward compute-bound.
9 · Key takeaway

Key takeaway

Serving is two workloads, a compute-bound prefill and a memory-bound decode, judged by TTFT, TPOT and goodput under SLOs.
Say it in 30 seconds

An LLM request has a prefill phase that processes the whole prompt in one pass, which sets the time to first token, and a decode phase that generates one token per step, which sets the time per output token. Throughput is what operators pay for, but bigger batches slow each step, so the right metric is goodput: the load you can serve while TTFT and TPOT stay within their SLOs. Each later technique targets one of these bottlenecks.

Problem: latency and throughput conflict, and a single tokens/s number hides that.
Core idea: separate prefill and decode, measure TTFT, TPOT and goodput, then fix each bottleneck.

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Efficiently Scaling Transformer Inference
Pope et al. · MLSys 2023

An analytical model of inference cost that picks how to partition a model across chips for a given latency target; shows prefill and decode need different strategies and that multi-query attention allows much longer contexts.

Remember: 29 ms/token on PaLM 540B with int8 weights; 76% MFU (model floating-point-operation utilization, the share of peak compute spent on the model's math) on large-batch prefill; MQA enables up to 32× longer context
DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving
Zhong et al. · OSDI 2024

Defines serving quality as goodput, the request rate served within both TTFT and TPOT targets, and runs prefill and decode on separate GPUs so they stop interfering.

Remember: 7.4× more requests or 12.6× tighter SLO than colocated systems
Splitwise: Efficient Generative LLM Inference Using Phase Splitting
Patel et al. · ISCA 2024

Characterizes prompt computation as compute-intensive and token generation as memory-intensive, and splits them onto separate machines, possibly of different GPU types.

Remember: 1.4× throughput at 20% lower cost, or 2.35× throughput at the same cost and power
