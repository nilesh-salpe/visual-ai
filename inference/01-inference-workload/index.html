LLM Inference & Serving · 01

The inference workload

What happens when a request hits an LLM server: the two phases, the metrics users feel and the ones operators pay for, and why a single "tokens per second" number misleads.

What is the problem?Users care about latency, operators care about throughput, and the two pull in opposite directions.
Core ideaSeparate the work into prefill (the whole prompt at once) and decode (one token at a time). Measure TTFT, TPOT, and goodput: throughput that still meets latency targets.
1 · Problem

One request, two very different phases

A chat request has a prompt of P tokens and generates O output tokens. The server first processes the whole prompt in one pass, which is prefill. Then it generates output tokens one at a time, each depending on the last, which is decode.

Time to first token comes from prefill. The steady stream of tokens after that comes from decode. They are limited by different resources (see the roofline in GPU deck 02).
2 · Limitation

Why "tokens per second" isn't enough

Throughput hides latency

A huge batch maximizes tokens/s for the server while each user waits longer per token.

Averages hide tails

A good mean latency can coexist with a p99 that breaks the product experience.

Two phases, one number

Prefill speed (prompt tokens/s) and decode speed (output tokens/s) behave differently and need different fixes.

3 · Your turn

Pick the right metric

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

Which metric captures "how much load the server handles while still meeting its latency targets"?

B. DistServe defines goodput as the request rate a system can serve while meeting its time-to-first-token and time-per-output-token targets. Peak tokens/s ignores latency, utilization can be high while users wait, and averages hide tails.
4 · Core idea

The four numbers that describe a serving system

TTFT: time to first token

Queueing plus prefill of the prompt. Grows with prompt length. Users feel it as "how long until it starts typing".

TPOT: time per output token

Time per decode step, also called inter-token latency. Users feel it as streaming speed.

Throughput

Tokens (or requests) per second across all users. This is what the operator pays for.

Goodput

Throughput counted only while TTFT and TPOT stay within their SLOs. It's the metric that matters (DistServe, OSDI '24).

5 · How it works

Batching trades TPOT for throughput illustrative step-time model

A decode step reads all the weights once whatever the batch size, so batching raises throughput. Each step also gets a little slower as the batch grows. Set a TPOT SLO and find the largest batch that still meets it.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Tokens per second tells you how good a server is."

Not on its own. Without latency targets it rewards huge batches that make each user wait. Use goodput under SLOs.

"A bigger batch is always better."

Throughput rises, but so does TPOT. Past the SLO limit, extra batch size adds no goodput.

"TTFT and TPOT have the same bottleneck."

TTFT is mostly prefill compute plus queueing. TPOT is mostly memory bandwidth per decode step. They need different fixes.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

Prompt 2,000 tokens at a prefill speed of 20,000 tokens/s, then 500 output tokens at 30 ms TPOT. Roughly what are TTFT and total latency?

TTFT ≈ 2,000 / 20,000 = 0.1 s. Decode ≈ 500 × 0.03 = 15 s, so the total is about 15.1 s. Decode dominates long answers.

Which definition of goodput does DistServe use?

Request rate within the latency SLOs.

Why does batching help decode throughput so much?

Each decode step must read all the weights anyway. A larger batch reuses that one read for many sequences, moving decode from memory-bound toward compute-bound.
9 · Key takeaway

Key takeaway

Serving is two workloads, a compute-bound prefill and a memory-bound decode, judged by TTFT, TPOT and goodput under SLOs.
Say it in 30 seconds

An LLM request has a prefill phase that processes the whole prompt in one pass, which sets the time to first token, and a decode phase that generates one token per step, which sets the time per output token. Throughput is what operators pay for, but bigger batches slow each step, so the right metric is goodput: the load you can serve while TTFT and TPOT stay within their SLOs. Each later technique targets one of these bottlenecks.

Problem: latency and throughput conflict, and a single tokens/s number hides that.
Core idea: separate prefill and decode, measure TTFT, TPOT and goodput, then fix each bottleneck.
