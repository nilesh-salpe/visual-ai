PagedAttention and prefix caching

Managing the KV cache like virtual memory (vLLM, SOSP 2023), and reusing the KV of shared prompt prefixes (SGLang's RadixAttention).

What is the problem?KV caches grow token by token to unknown final lengths. Reserving contiguous memory wastes most of it, and identical prompt prefixes get stored and recomputed again and again.
Core ideaStore KV in fixed-size blocks mapped by a per-sequence block table, with reference counts and copy-on-write for sharing. Index cached prefixes in a tree so later requests can reuse them.
1 · Problem

The KV cache is dynamic and unpredictable

Grows every step

Each generated token appends K and V to every layer's cache.

Unknown final length

Nobody knows in advance whether a reply will be 10 tokens or 2,000.

Lots of sharing

Parallel samples, beam search and common system prompts all start from the same prefix.

2 · Limitation

Contiguous reservations waste memory and duplicate shared data

Fragmentation

Reserving max-length buffers leaves most slots unused. Uneven sizes also leave gaps between buffers. The vLLM paper calls this waste from "fragmentation and redundant duplication", and it limits batch size.

Duplication

Each sample of the same prompt gets its own copy of identical K and V. Every request with the same system prompt recomputes it during prefill.

3 · Your turn

Borrow an idea from operating systems

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

Which operating-system idea fits the "growing, unpredictable, shareable memory" problem best?

B. PagedAttention stores each sequence's KV in fixed-size blocks (vLLM's default is 16 tokens) that need not be contiguous. A block table maps logical positions to physical blocks, and shared blocks are reference-counted and copied on write, just like OS pages.
4 · Core idea

Blocks, block tables, and copy-on-write

Fixed-size blocks

KV for B tokens per block. vLLM sets the default block size to 16, as a balance between GPU efficiency and internal fragmentation.

Block table

Per sequence: logical block i → physical block id. The attention kernel reads K and V through this table.

Share and copy on write

Forked sequences point at the same blocks (refcount > 1). The first write to a shared, partly filled block copies it.

5 · How it works

Prefix caching: reuse shared prompts

Many requests begin with the same tokens: a system prompt, few-shot examples, earlier chat turns. Keep their KV after a request finishes, index it in a tree keyed by tokens, and the next request skips prefill for the longest cached prefix. SGLang's RadixAttention uses a radix tree with LRU eviction.

6 · Why it works

Why it works

Near-zero waste

Only the last block of each sequence can be partly empty, so waste is under one block per sequence. Build-it notebook 04 measures 0.6% vs 48% for contiguous max-length reservation on random lengths.

Bigger batches

Freed memory holds more sequences. vLLM reported 2–4× throughput over FasterTransformer and Orca at the same latency.

Free sharing

Parallel sampling and beam search share prompt blocks through reference counts.

Prefix reuse

Shared prefixes skip prefill entirely. SGLang reported up to 6.4× higher throughput on structured LLM programs.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"PagedAttention makes attention compute faster."

Its main win is memory: less waste and more sharing allow bigger batches, which raises throughput. The kernel has to read through the block table.

"Bigger blocks are always better."

Larger blocks are more GPU-efficient but waste more in each sequence's last block. vLLM picked 16 as the balance.

"Prefix caching only helps identical prompts."

It reuses the longest shared prefix, so different requests with the same system prompt still benefit.

What is vLLM's default KV block size?

16 tokens.

Two samples share a prompt whose last block is half full. What happens when sample 2 generates its next token?

That block is shared (refcount 2) and partly filled, so the allocator copies it on write: sample 2 gets a fresh block, and the old block's refcount drops to 1.

What throughput gain did vLLM report over FasterTransformer and Orca at the same latency?

2–4×, with larger gains for longer sequences and larger models.
