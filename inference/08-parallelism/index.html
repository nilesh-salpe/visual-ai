Parallelism for inference

Splitting a model across GPUs (graphics processing units) to serve it: tensor parallelism for latency and fit, pipeline and data parallelism for throughput, expert parallelism for MoE (Mixture of Experts), and why the communication pattern decides where each one runs.

What is the problem?A large model may not fit in one GPU's memory, and even when it fits, one GPU's memory bandwidth limits how fast each decode step can be.
Core ideaTensor parallelism splits every matmul so each GPU reads only its share of the weights per token, at the cost of one all-reduce per block, which must stay on NVLink.
1 · Problem

Fit and speed both hit a single-GPU wall

Fit

A 70B model in BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) is about 140 GB of weights, more than one 80 GB GPU, before any KV (key-value) cache.

Speed

At batch 1, one decode step must read all the weights. At 3.35 TB/s (H100 HBM (high-bandwidth memory)), 140 GB takes at least about 42 ms per token.

2 · Limitation

Not every split helps latency

Pipeline (layers across GPUs)

Fits the model, but a single request still visits every stage in turn, so per-token latency doesn't improve.

Data parallel (replicas)

More throughput, but each replica must hold the whole model, and per-request latency is unchanged.

Naive splits

Splitting carelessly forces communication after every matmul.

3 · Your turn

Lower per-token latency

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

Which kind of parallelism reduces per-token decode latency for a single request?

B. With TP (tensor parallelism) of degree n, each GPU streams only 1/n of the weights each step, so the memory-bound step time drops roughly n× (minus communication). Pipeline and data parallelism help capacity and throughput, not one request's latency.
4 · Core idea

Megatron-style tensor parallelism

Column-parallel first

Split W₁ by output columns. Each GPU computes its slice, and GELU (Gaussian Error Linear Unit) stays local because it's elementwise.

Row-parallel second

Split W₂ by input rows to match. Each GPU holds a partial sum.

One all-reduce

Sum the partials once per MLP (and once per attention block). That's two all-reduces per layer.

At a glance

Megatron MLP: one all-reduce in the forward pass; attention splits by heads the same way.

5 · How it works

Worked example: tensor parallelism for a 70B model

70B parameters in BF16 = 140 GB of weights. H100s with 80 GB each, 3.35 TB/s HBM. 80 layers.

Worked example

  1. One GPU can't even hold the weights (140 GB > 80 GB). TP = 8: 17.5 GB per GPU.
  2. Per-token weight read: 41.8 ms if one GPU could hold it, vs 5.2 ms with TP = 8, since each GPU reads only its eighth in parallel.
  3. Communication: 2 all-reduces per layer × 80 layers = 160 all-reduces per token, each only batch × 8,192 × 2 bytes (16 KiB at batch 1).
  4. Those messages are small and latency-bound, so they need NVLink inside one server; across a network they would dominate.
TP cuts per-token latency up to ~8× here, minus communication; it is the standard way to serve models larger than one GPU at low latency.
6 · Why it works

Why TP lives inside the NVLink domain

Less to read per GPU

Decode is bound by bytes. Splitting weights n ways cuts each GPU's per-step read about n×.

Small, frequent, blocking messages

Two all-reduces per layer per step sit on the critical path, so they need NVLink-class bandwidth and latency (GPU decks 04 and 05).

Combine strategies

TP within a node; pipeline across nodes for very large models; data-parallel replicas for throughput.

MoE: expert parallelism

Experts live on different GPUs and tokens travel by all-to-all. TensorRT-LLM, for example, lists "Wide Expert Parallelism" as a runtime feature.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"More TP always means lower latency."

Weight reads shrink as 1/n, but all-reduce cost does not. Beyond the NVLink domain, communication can dominate.

"Pipeline parallelism speeds up a single request."

A request still passes through every stage in order. Pipelining helps fit and throughput, not one request's latency.

"TP needs communication after every matmul."

The column-then-row (Megatron) arrangement needs one all-reduce per MLP or attention block.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • TP lowers latency, PP (pipeline parallelism) raises throughput. TP splits every layer across GPUs; PP splits the layers into stages (pipeline parallelism).
  • Two all-reduces per transformer block. One after attention, one after the MLP (forward pass).
  • Keep TP within the NVLink domain. Typically TP ≤ GPUs per server.

⚠ Traps

  • TP across nodes. Hundreds of small all-reduces per token over a slower network erase the gain.
  • TP degree > KV heads. With 8 KV heads and TP = 16, KV heads must be replicated, wasting cache memory.
  • Expecting linear speedup. Communication and fixed per-step costs grow with TP degree.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

How many all-reduces per transformer layer does Megatron-style TP need in the forward pass?

Two: one after attention, one after the MLP.

Why is GELU between the two MLP matmuls "free" under TP?

After the column-parallel W₁ each GPU holds complete columns of the hidden activation, and GELU is elementwise, so it runs locally with no communication.

Roughly what is the minimum per-token decode time for 140 GB of weights on one H100 (3.35 TB/s), and with TP 8?

140 / 3,350 ≈ 42 ms. With TP 8 each GPU reads 17.5 GB, about 5.2 ms, plus all-reduce time.
9 · Key takeaway

Key takeaway

Tensor parallelism splits every weight matrix so each GPU reads 1/n of the weights per token, cutting latency and fitting big models, at the cost of two small all-reduces per layer that must stay on NVLink.
Say it in 30 seconds

Tensor parallelism splits each matmul Megatron-style (column-parallel then row-parallel), so each GPU reads 1/n of the weights and only one all-reduce is needed per attention or MLP block. Those all-reduces are small but on the critical path, so TP stays inside the NVLink domain. Pipeline and data parallelism add capacity and throughput, and expert parallelism spreads MoE experts across GPUs.

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism
Shoeybi et al. · arXiv 2019

Intra-layer (tensor) model parallelism that splits each attention and MLP block across GPUs with only a few all-reduce operations, implemented in plain PyTorch.

Remember: 2 all-reduces per transformer block in the forward pass; 76% scaling efficiency on 512 GPUs
Efficiently Scaling Transformer Inference
Pope et al. · MLSys 2023

An analytical model of inference cost that picks how to partition a model across chips for a given latency target; shows prefill and decode need different strategies and that multi-query attention allows much longer contexts.

Remember: 29 ms/token on PaLM 540B with int8 weights; 76% MFU (model floating-point-operation utilization, the share of peak compute spent on the model's math) on large-batch prefill; MQA enables up to 32× longer context
