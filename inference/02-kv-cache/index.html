The KV cache

Why every LLM (large language model) server stores past keys and values, how much memory that takes, and how GQA (grouped-query attention) and MLA (multi-head latent attention) shrink it.

What is the problem?Without caching, generating token t re-runs attention over all t previous tokens, so total work grows quadratically.
Core ideaStore each layer's K and V for every past token. A new token computes only its own q, k and v and attends over the cache. The result is exact, but memory grows with context × batch.
1 · Problem

Naive generation redoes almost all of its work

Generating token t needs attention between the new token and all t previous tokens. A naive loop re-runs the full forward pass over the whole prefix for every new token.

Token positions processed by the forward pass: naive = Σ (prompt + i) for i < n; cached = prompt + n.

2 · Limitation

Recomputing is pure waste

Same K and V every time

Past tokens' keys and values don't change when a new token arrives, because causal masking means earlier positions never see later ones.

Quadratic total work

Generating n tokens costs about n²/2 token-passes, so long answers get disproportionately slow.

Latency grows each step

Every step is slower than the one before it, so TPOT (time per output token) keeps rising throughout the answer.

3 · Your turn

What should be cached?

To avoid recomputation during decoding, which tensors from past tokens should be stored?

C. A new token needs its own query and everyone's keys and values. Past queries are never used again, and attention weights change with every new token.
4 · Core idea

Cache K and V per layer; compute only the new token

Prefill

Run the prompt once and store K and V for every layer and position.

Decode step

Compute q, k and v for the new token only, append k and v to the cache, then attend q over the cache.

Exact

The logits are identical to full recomputation. The cache trades compute for memory.

KV bytes = 2 × layers × kv_heads × head_dim × bytes/element × tokens × batch

At a glance

The cache turns "recompute the whole prefix" into "compute one token and read the past".

5 · How it works

Shrinking the cache: MQA, GQA and MLA

The cache scales with the number of key/value heads. Let several query heads share one KV head.

GQA (Ainslie et al., EMNLP 2023)

Between MHA (multi-head attention) and MQA (multi-query attention). Quality close to MHA at speeds comparable to MQA, and MHA checkpoints can be "uptrained" with about 5% of the original pre-training compute.

MLA (DeepSeek-V2, 2024)

Compresses K and V into a latent vector: 93.3% smaller KV cache and 5.76× max generation throughput compared with DeepSeek 67B.

5 · How it works

Worked example: how big is the cache?

Llama-3-70B: 80 layers, 8 KV (key-value) heads (GQA), head dimension 128, BF16 (2 bytes). Context 8,192 tokens, batch 32.

Worked example

  1. Per token: 2 (K and V) × 80 layers × 8 heads × 128 × 2 bytes = 327,680 bytes = 320 KiB.
  2. Per sequence at 8,192 tokens: 320 KiB × 8,192 = 2.5 GiB.
  3. Batch of 32: 80 GiB, about as much as the 70B weights in FP8 (8-bit floating point).
  4. Without GQA (64 KV heads, one per query head) it would be 8× larger: 640 GiB.
Rule: KV bytes per token = 2 × layers × KV heads × head_dim × bytes. For this model, every 1,000 tokens of context costs 0.31 GiB per sequence.
6 · Why it works

Why the KV cache shapes everything else

Compute becomes cheap

Each step does work for one token, so decode is dominated by reading weights and cache.

Memory becomes the limit

Batch size × context is capped by KV memory, so concurrency depends on the cache's size.

It drives later techniques

Paging (05), prefix sharing (05), FP8 KV (07), and moving KV between pools (09) all manage this cache.

Architecture responds

GQA, MQA and MLA are architecture changes made largely to shrink this cache.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Using a KV cache changes the model's outputs."

It is exact: logits match full recomputation, because causal attention never lets past positions see the future.

"You should cache the queries too."

Queries are needed only for the current token. Past queries are never reused.

"The KV cache is small compared with the weights."

At long context it isn't: a 70B-shaped model with GQA needs 40 GiB per sequence at 128K tokens in BF16.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • KV bytes/token = 2·L·n_kv·d_head·bytes. Use KV heads, not query heads.
  • Total = per-token × context × batch. Batch and context trade against each other for the same memory.
  • GQA saves n_heads / n_kv. Llama-3-70B: 64 query heads / 8 KV heads = 8× smaller cache.
  • Break-even with weights. Context × batch where KV = weight bytes tells you when memory, not weights, limits concurrency.

⚠ Traps

  • Using num_attention_heads. With GQA the cache scales with num_key_value_heads; using query heads overestimates by the group factor.
  • Dropping the factor 2. There are two cached tensors, K and V.
  • Caching queries. Past queries are never reused; only K and V are cached.
  • Thinking the cache changes outputs. It is exact: identical logits to recomputing everything.

Why can't you avoid the cache by just making attention faster?

Without a cache, every step reprocesses the whole prefix (quadratic total work). A faster kernel speeds up each pass but doesn't remove that redundant work.
9 · Key takeaway

Key takeaway

The KV cache stores past keys and values so each decode step computes only one new token. It is exact, but its memory (2 × layers × kv_heads × head_dim × bytes × tokens × batch) becomes the main serving constraint.

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Fast Transformer Decoding: One Write-Head is All You Need
Shazeer · arXiv 2019

Introduces multi-query attention: all heads share one key/value head, cutting the memory bandwidth of incremental decoding with only minor quality loss.

Remember: 1 K/V head instead of h
GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints
Ainslie et al. · EMNLP 2023

Grouped-query attention: an intermediate number of key/value heads, plus a recipe to convert existing multi-head checkpoints.

Remember: quality close to MHA, speed close to MQA; uptraining with 5% of the original pretraining compute
DeepSeek-V2: A Strong, Economical, and Efficient Mixture-of-Experts Language Model
DeepSeek-AI · arXiv 2024

Introduces multi-head latent attention (MLA), which compresses keys and values into a small latent vector per token, alongside a Mixture-of-Experts design.

Remember: KV cache reduced by 93.3%; maximum generation throughput 5.76× vs DeepSeek 67B
Efficiently Scaling Transformer Inference
Pope et al. · MLSys 2023

An analytical model of inference cost that picks how to partition a model across chips for a given latency target; shows prefill and decode need different strategies and that multi-query attention allows much longer contexts.

Remember: 29 ms/token on PaLM 540B with int8 weights; 76% MFU (model floating-point-operation utilization, the share of peak compute spent on the model's math) on large-batch prefill; MQA enables up to 32× longer context
