Continuous batching

Iteration-level scheduling (Orca, OSDI 2022): admit and retire requests at every decode step instead of running fixed batches to completion.

What is the problem?Decode at batch 1 wastes the GPU (graphics processing unit). Static batches, though, hold every slot until the longest request finishes, and new arrivals have to wait.
Core ideaSchedule at the granularity of one iteration: finished requests leave and waiting requests join between every decode step.
1 · Problem

One sequence at a time leaves the GPU idle

A decode step reads all the weights to produce one token per sequence. With one sequence, that read serves one token. Batching lets the same read serve many sequences, which is why servers batch.

Batching is how decode gets from memory-bound toward compute-bound (GPU deck 02, the roofline).
2 · Limitation

Static batching wastes slots and makes requests wait

Static (request-level) batching groups requests and runs the group until its longest member finishes. Short requests sit idle in their slots, and new arrivals can't join a running batch.

Finished but still occupying a slot

Requests produce different numbers of tokens. Early finishers can't be replaced until the whole batch ends.

Queueing delay

A request arriving just after a batch starts waits for the whole batch to finish.

4 · Core idea

Iteration-level scheduling + selective batching

Iteration-level scheduling

Between every decode iteration, retire finished sequences and admit new ones, up to the batch or memory limit.

Selective batching

Requests at different positions have different lengths. Orca batches the operations that don't depend on length (the linear layers) and handles attention per request.

At a glance

Scheduling happens per iteration (one decode step), not per batch.

5 · How it works

Worked example: slots wasted by static batching

Four requests start together and need 10, 20, 50, 200 output tokens.

Worked example

  1. Static batching keeps the batch together until the longest finishes: 4 slots × 200 steps = 800 slot-steps reserved.
  2. Useful work is only 10 + 20 + 50 + 200 = 280 slot-steps.
  3. Utilization = 280 / 800 = 35%; the three short requests also wait for the batch to finish before being returned.
  4. Continuous batching refills each slot the iteration after it frees, so with a queue of waiting requests the slots stay ~100% busy.
Same hardware, same model: in this example continuous batching does up to 2.9× more useful work per step, and short requests return as soon as they finish.
6 · Why it works

Why it works

No idle slots

A slot is refilled on the very next iteration, so the batch stays full whenever requests are waiting.

Less queueing

New requests start within one iteration instead of waiting for a batch to drain.

Measured

On GPT-3 175B, Orca reported a 36.9× throughput improvement over NVIDIA FasterTransformer at the same latency.

Foundation for what follows

Paged KV (05) and chunked prefill (04) both build on per-iteration scheduling.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Continuous batching just means a bigger batch."

The batch size limit can be the same. What changes is when membership changes: at every iteration rather than per batch.

"Batched requests must have the same length."

Iteration-level scheduling mixes requests at different positions. Orca's selective batching handles the length-dependent attention part.

"Batching always increases user latency."

Each step gets a little slower, but removing queueing usually lowers end-to-end latency, as the simulation shows.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Granularity = one decode step. Join and leave between iterations; never wait for the batch to drain.
  • Selective batching. Batch the matmuls across requests; run attention per request, because each has its own KV length.
  • Throughput ∝ batch while memory-bound. Adding sequences reuses the same weight read until compute becomes the limit.

⚠ Traps

  • Padding to the longest sequence. Wastes compute and memory; continuous batching with paged KV avoids it.
  • Ignoring KV memory. Batch size is capped by free KV memory, not only by a configured maximum; engines preempt when it runs out.
  • Assuming bigger batch is always better. TPOT (time per output token) rises with batch; past the SLO (service-level objective), more batch adds no goodput.

9 · Key takeaway

Key takeaway

Continuous batching re-forms the batch at every decode iteration: finished requests leave and new ones join immediately, so slots never sit idle.
Say it in 30 seconds

Decode needs batching to use the GPU, but static batching runs each batch until its longest request finishes, wasting slots and making new requests wait. Orca introduced iteration-level scheduling: the server re-decides the batch between every decode step, with selective batching for the length-dependent attention. It reported 36.9× throughput over FasterTransformer at the same latency on GPT-3 175B, and it's now standard in LLM (large language model) servers.
