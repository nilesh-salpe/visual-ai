Serving large Mixture-of-Experts models

How models like DeepSeek-V3 (671B parameters, 37B active) are served across dozens to hundreds of GPUs (graphics processing units): data-parallel attention, wide expert parallelism, all-to-all dispatch and combine, redundant experts for load balance, and overlapping communication with computation.

The questionHow would you serve a 671B-parameter MoE (Mixture of Experts) model with high throughput and low latency?
Short answerSplit by layer type. Attention runs data-parallel: each GPU serves its own requests and keeps their KV (key-value) cache. Experts are spread across many GPUs (wide expert parallelism), so each GPU stores only a few experts and each expert receives a large batch. Tokens reach their experts and return through two all-to-alls per MoE layer, hidden by overlapping two micro-batches. Copy the busiest experts to balance load, and run prefill and decode as separate units, with decode spread wider.

3 · Numbers to know

Numbers to know calculator

DeepSeek-V3 shape

256 routed experts + 1 shared per MoE layer, 8 routed chosen per token, 58 MoE layers of 61; 671B parameters, 37B active.

One expert ≈ 2.55 GB

3 × 7,168 × 2,048 weights per layer × 58 layers ≈ 2.55B parameters, 2.55 GB in FP8 (8-bit floating point). All routed experts: about 654 GB.

Tokens per expert

tokens per step × 8 ÷ expert instances. Wide EP multiplies the tokens per step: with b sequences on each of EP GPUs, each instance sees b · EP · 8 ÷ (256 + copies).

Measured throughput

DeepSeek (H800): about 73.7K input tokens/s per node in prefill and 14.8K output tokens/s per node in decode. SGLang (96 H100s): 52.3K and 22.3K per node for 2K-token inputs.

Roofline: with FP8 weights an expert matmul does about 2 FLOPs (floating-point operations) per weight byte per token, so it reaches H100 FP8 peak (1,979 TFLOP (trillion floating-point operations)/s over 3.35 TB/s) only with roughly 300 tokens per expert. Attention and communication time are not modelled.

4 · Trade-offs

Trade-offs

Choice Gains Costs
Tensor-parallel experts (vLLM's default without --enable-expert-parallel) simple; works on one node every GPU computes a slice of every expert; small matmuls and all-reduces
Expert parallelism, one node (EP 8) whole experts local; no cross-node traffic all routed experts must fit in 8 GPUs (about 654 GB for DeepSeek-V3: H200-class); few tokens per expert
Wide expert parallelism (EP 32 to 320) large batch per expert, few experts per GPU, more KV memory free all-to-all across nodes on every layer; a larger failure domain; needs RDMA (remote direct memory access) kernels (DeepEP)
Data-parallel attention each GPU keeps its requests' KV cache; no KV duplication for MLA (multi-head latent attention) ranks must step together, so idle ranks run dummy passes
Redundant experts balances hot experts; can cut cross-node traffic extra memory; re-placement moves weights
Two micro-batch overlap hides much of the all-to-all time needs enough batch to split; more complex scheduling
5 · Follow-ups

Follow-ups

Basic Why not just tensor-parallelise the experts?

Every GPU would hold a slice of every expert, so each matmul shrinks and each layer needs an all-reduce. Expert parallelism keeps whole experts local and batches all of an expert's tokens together. SGLang measured 5.2× higher decode throughput with EP 72 than a TP (tensor parallelism) 16 baseline, mostly from 4× larger batches.

Basic MoE activates only 37B of 671B parameters. Why is it still expensive to serve?

All 671B parameters must sit in GPU memory, and each step reads the weights of every expert that any token chose. Cheap compute per token does not mean cheap memory.

Deeper Why does decode use a wider expert parallelism than prefill?

A decode step produces one token per sequence, so a GPU contributes few tokens; gathering tokens from many GPUs gives each expert a useful batch. Prefill already has thousands of tokens per request. DeepSeek: EP 32 for prefill, EP 144 for decode (EP 320 in its V3 report).

Deeper One expert gets far more tokens than the rest. What happens and what do you do?

Its GPU becomes the straggler and every other GPU waits each layer. Copy hot experts onto other GPUs and re-place them from recent load statistics: DeepSeek re-places about every 10 minutes; vLLM's --enable-eplb rebalances every 3,000 engine steps over a 1,000-step window by default.

Expert How do you hide the all-to-all communication?

Split the batch into two micro-batches and alternate: one runs attention and experts while the other dispatches or combines. DeepSeek's decode splits attention into two steps for a 5-stage pipeline. Use low-latency RDMA kernels with CUDA (Compute Unified Device Architecture, NVIDIA's programming platform for its graphics processors) graphs for decode (vLLM deepep_low_latency) and high-throughput kernels for prefill (deepep_high_throughput).

Expert Why data-parallel attention for MLA models?

MLA stores one compressed latent per token shared by all heads, so splitting heads across GPUs would duplicate that cache on every GPU. Data-parallel attention keeps each request's cache on one GPU (SGLang's "DP (data parallelism) attention" removes the duplication).
6 · Wrong answers to avoid

Wrong answers to avoid

"Only 37B parameters are active, so serving costs like a 37B dense model."

Memory and weight reads cover all experts in use; DeepSeek-V3's routed experts alone are about 654 GB in FP8.

"Wider expert parallelism is always better."

Each extra node adds all-to-all traffic and another failure point. DeepSeek itself moved from EP 320 (report) to EP 144 (production write-up) for decode.

"Balanced training means balanced serving."

Real traffic routes unevenly; vLLM's docs note the token distribution across experts can be highly skewed in practice, which is why EPLB (Expert Parallelism Load Balancer) exists.

"Prefill and decode should share one layout."

They have different bottlenecks: prefill is compute-bound with large batches, decode needs many GPUs' tokens per expert, so DeepSeek runs them as separate units.
7 · In a system

In a real system

Fleet size

DeepSeek's V3 and R1 service peaked at 278 nodes (8 H800 each) and averaged 226.75 over one day, about $87K/day at an assumed $2 per GPU-hour.

Elastic capacity

At night, when traffic is low, DeepSeek shrinks inference and gives the nodes to research and training.

Precision

FP8 matmuls and FP8 dispatch, BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) for MLA attention and combine, matching training.

Open-source path

vLLM: --enable-expert-parallel with --all2all-backend deepep_low_latency or deepep_high_throughput and --enable-eplb; SGLang: DP attention, DeepEP, EPLB and two-batch overlap.

See also: Disaggregated serving for the prefill/decode split, and Expert parallelism in training.

With EP 8 on one 8-GPU node and 64 decode sequences per GPU, about how many tokens does each DeepSeek-V3 expert see per step?

B. 64 × 8 GPUs × 8 experts per token ÷ 256 experts = 16: far below the roughly 300 needed for compute-bound FP8 matmuls.

What does an expert load balancer do?

B. Redundant copies spread the hot experts' tokens so no GPU becomes the straggler.
