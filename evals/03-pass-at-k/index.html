pass@k and sampling metrics

When a model can try several times, what should the score be? pass@k, its unbiased estimator, and how to choose between pass@1 and pass@100.

What is the problem?Generation is stochastic. A model that solves a problem 1 time in 10 looks like a failure with one sample and a success with 100. A single sample per problem is also a very noisy estimate.
Core ideaSample n solutions per problem, count the c that pass, and estimate pass@k = 1 − C(n−c, k)/C(n, k): the chance that at least one of k attempts passes. Report the k that matches how the model will be used.
1 · Problem

One sample or many?

A problem the model solves with probability p per attempt. With k attempts, the chance that at least one succeeds is 1 − (1−p)k. The same model looks very different at k = 1 and k = 100.

2 · Limitation

Problems with the obvious approaches

Exactly k samples is noisy

Drawing exactly k samples per problem and checking for a pass gives a 0/1 result per problem with high variance.

Plug-in is biased

Estimating p̂ = c/n and computing 1 − (1−p̂)k underestimates pass@k, because the curve is concave in p (notebook 01 measures −0.06 at p = 0.05, n = 20, k = 10).

Text similarity isn't correctness

BLEU-style (BLEU = Bilingual Evaluation Understudy, an n-gram overlap score for translation) metrics reward code that looks like the reference. HumanEval uses unit tests: functional correctness.

4 · Core idea

The unbiased estimator

Sample n ≥ k

For each problem generate n samples (Codex used n = 200) and run the tests; c pass.

Count subsets

pass@k = 1 − C(n−c, k)/C(n, k): one minus the probability that a random size-k subset of the n samples contains no passing sample. Average over problems.

Compute stably

Binomials overflow, so use the product form 1 − ∏i=n−c+1..n(1 − k/i), as in the paper's numpy snippet. If n − c < k, the answer is 1.

At a glance

Unbiased, and it uses all n samples.

5 · How it works

Which k should you report?

pass@1: reliability

What a user gets from one attempt. Estimate it from many samples (n ≫ 1) for low variance; it equals the average per-sample pass rate.

pass@k, k large: coverage

Whether the model can solve it at all if you can verify attempts. Codex-12B: 28.8% at pass@1, and with 100 samples per problem 70.2% have at least one correct solution.

Selection matters

pass@k assumes an oracle picks a passing sample. Without one, you need a selection rule (highest likelihood, majority vote, a verifier), and the score falls between pass@1 and pass@k.

Agentic tasks

On SWE-bench-style (SWE = software engineering) tasks each attempt is expensive and long, so pass@1 with a fixed budget is usually what matters.

5 · How it works

Worked example: pass@10 from 20 samples

n = 20 samples for one problem, c = 2 pass the unit tests, k = 10.

Worked example

  1. C(18, 10) = 43,758; C(20, 10) = 184,756.
  2. pass@10 = 1 − 43,758 / 184,756 = 0.763.
  3. Plug-in estimate: 1 − (1 − 2/20)10 = 0.651, lower.
  4. pass@1 = c/n = 0.10.
Use the unbiased estimator per problem, then average over problems.
6 · Why it works

Why the estimator is right

It is exact for the sample

Given n samples with c passes, choosing k without replacement fails only if all k come from the n − c failures: probability C(n−c,k)/C(n,k). Averaging over the randomness in c gives exactly the true pass@k.

It uses every sample

All n samples contribute instead of k, which cuts variance compared with drawing exactly k.

Notebook evidence

At p = 0.05, n = 20, k = 10: unbiased error ≈ +0.004 (simulation noise), plug-in error −0.061.

Tests define "pass"

The metric is only as good as the unit tests: weak tests let wrong programs pass.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"pass@100 tells you how good the model is for users."

Users usually get one attempt. pass@100 measures what a verifier could select from 100 tries, which is a different question.

"1 − (1 − c/n)^k is a fine estimate of pass@k."

It is biased low because the function is concave. Use 1 − C(n−c,k)/C(n,k).

"pass@1 needs only one sample per problem."

One sample gives an unbiased but very noisy estimate. Many samples per problem give the same expectation with far lower variance.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • pass@1 = c/n. With many samples it is low-variance.
  • Product form. 1 − ∏ (1 − k/i) for i from n − c + 1 to n avoids overflow.
  • n − c < k ⇒ 1. Every k-subset contains a pass.

⚠ Traps

  • Plug-in 1 − (1 − c/n)^k. Biased low (concave).
  • Reporting pass@100 as user quality. Users usually get one attempt.
  • Weak tests. Wrong programs that pass weak tests count as solved.

Why is pass@k averaged over problems rather than computed from the pooled pass rate?

Problems differ in difficulty. pass@k is a per-problem probability; pooling the rate first and then applying 1 − (1−p)^k would mix easy and hard problems incorrectly (and is the biased plug-in).

When is pass@k with large k the right metric?

When you can generate many candidates and automatically verify them (unit tests, a checker), so any passing sample can be selected.
9 · Key takeaway

Key takeaway

pass@k is the chance that at least one of k attempts passes; estimate it unbiasedly from n ≥ k samples as 1 − C(n−c,k)/C(n,k), and report the k that matches real use.
Say it in 30 seconds

Code and maths models are stochastic, so the score depends on how many attempts you allow. pass@k is the probability that at least one of k samples passes the tests. The Codex paper estimates it by drawing n samples per problem, counting the c that pass, and computing one minus the number of all-failing k-subsets over all k-subsets, averaged over problems, which is unbiased and uses every sample. The tempting plug-in of c over n into one minus one minus p to the k is biased low. pass@1 measures what a user gets from one try; large k measures what a verifier could find: Codex went from 28.8 percent at one sample to 70.2 percent with 100.

Problem: stochastic generation: one sample is noisy, many samples need a definition.
Core idea: pass@k = 1 − C(n−c,k)/C(n,k), product form for stability.
Practice: pass@1 for reliability, large k only when attempts can be verified.
