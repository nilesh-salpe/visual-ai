Vector databases and ANN indexes

How similarity search over millions to billions of embeddings stays fast: inverted-file partitions, product quantization, HNSW (hierarchical navigable small world) graphs and SSD-resident (SSD = solid-state drive) graphs, plus filtering, updates and sharding.

What is the problem?Exact search compares the query with every stored vector. A billion 768-dimensional float32 vectors are about 3 TB and a full scan per query; even at a few million vectors, brute force is too slow for an agent that searches several times per task.
Core ideaApproximate nearest neighbour (ANN) indexes trade a little recall for orders of magnitude in speed and memory: partition (IVF (inverted file index): scan only the closest clusters), compress (PQ (product quantization): a vector becomes m one-byte codes), or navigate a graph (HNSW: greedy search down a layered small-world graph; DiskANN: a graph on SSD). A vector database wraps an index with storage, filters, updates and replication.

1 · Problem

Brute force does not scale

Compute

Exact top-k is one dot product per stored vector per query.

Memory

float32 embeddings cost 4 × dimensions bytes each: 3 KB for 768 dimensions, 12 KB for 3,072.

Real workloads

Searches come with filters (tenant, date, access list), and data changes continuously.

2 · Core idea

Partition, compress, or navigate

IVF

Inverted file: cluster vectors with k-means into nlist lists; at query time scan only the nprobe closest lists.

PQ

Product quantization (Jégou et al. 2011): split a vector into m sub-vectors, replace each by the id of its nearest of 256 centroids; distances come from per-query lookup tables.

HNSW

Hierarchical navigable small world graph (Malkov and Yashunin): sparse upper layers with long links, dense layer 0; greedy search from the top gives logarithmic scaling.

DiskANN

A graph on SSD with compressed vectors in RAM (random-access memory): a billion points on one workstation with 64 GB RAM, over 5,000 queries/s, under 3 ms mean latency, 95%+ 1-recall@1.

5 · Trade-offs

Trade-offs

Index Strength Weakness
Flat (exact) perfect recall, no training linear time; fine up to small collections
IVF-Flat simple, fast with good nprobe full vectors in memory; clusters drift as data changes
IVF-PQ tens of times less memory approximate distances; needs re-ranking for precision
HNSW high recall at low latency, incremental inserts graph memory on top of full vectors; deletes degrade it
DiskANN (SSD graph) billion scale on one node SSD reads per query; more complex updates
ScaNN (anisotropic quantization) strong inner-product search tuned for maximum inner product rather than general metrics
6 · Failure modes

Failure modes

Failure Symptom Mitigation
Recall silently drops no error, just worse answers measure recall@k against exact search on a sample regularly
Selective filters fewer than k results, or slow scans filter-aware indexes; partition by tenant; fall back to exact search on small filtered sets
Deletes and updates tombstones pile up; graph quality decays compaction and periodic rebuilds
Metric mismatch cosine model indexed with L2 on unnormalised vectors normalise vectors or use the metric the model was trained for
Memory blow-up HNSW over RAM, swapping capacity planning (above); PQ or DiskANN for large sets
7 · Challenges in production

In production

Tune on a curve

Plot recall@k against p95 latency for several efSearch or nprobe values; pick the knee.

Hybrid search

Combine with BM25 (Okapi Best Matching 25 ranking function) for exact terms; many databases fuse both in one query.

Multi-tenancy

A partition or namespace per tenant keeps filters cheap and data separated.

Library vs database

Faiss is a library of indexes; a database adds durability, replication, filtering and access control around one.

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs
Malkov & Yashunin · IEEE TPAMI 2018

A multi-layer proximity graph: each element's top layer is drawn from an exponentially decaying distribution (mL = 1/ln M), search descends greedily from the top layer, and layer 0 keeps up to 2M links per element; logarithmic complexity scaling.

Product Quantization for Nearest Neighbor Search
Jégou, Douze & Schmid · IEEE TPAMI 2011

Split each vector into m subvectors and quantize each with its own small codebook, so a vector is stored as m short codes; distances are estimated from per-query lookup tables (asymmetric distance computation), combined with an inverted file (IVFADC).

DiskANN: Fast Accurate Billion-point Nearest Neighbor Search on a Single Node
Subramanya et al. · NeurIPS 2019

A graph index (Vamana) stored on SSD with compressed vectors in RAM serves a billion-point index from one workstation.

Remember: 1B points, 64 GB RAM, >5,000 queries/s, <3 ms mean latency, 95%+ 1-recall@1 on 16 cores
The Faiss library
Douze et al. · arXiv 2024

The vector-search toolkit behind many vector databases: flat, IVF, PQ and graph indexes, and the trade-off space between accuracy, speed, memory and build time.

Accelerating Large-Scale Inference with Anisotropic Vector Quantization
Guo et al. · ICML 2020

ScaNN: a quantization loss that penalises the error parallel to the data point more than the orthogonal error, which suits maximum inner product search.
