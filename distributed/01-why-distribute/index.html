Distributed Training · 01

Why training must be distributed

The two walls a single GPU (graphics processing unit) hits when training a large model, memory and time, and the four ways of splitting the work across thousands of GPUs.

What is the problem?A 70B-parameter model needs over a terabyte just for weights, gradients and optimizer state, and training it on one GPU would take centuries.
Core ideaSplit the work along four axes: data (different examples per GPU), tensor (split each matrix), pipeline (split the layers) and context (split the sequence), plus expert parallelism for MoE (Mixture of Experts) models.

2 · Limitation

Why a bigger GPU is not the answer

Memory grows with the model

Weights, gradients and optimizer state alone take 16 bytes per parameter; the largest GPUs hold 80–192 GB.

Compute grows with model × data

Compute-optimal training scales tokens with parameters, so FLOPs grow roughly with the square of model size.

One chip improves slowly

A new GPU generation every ~2 years gives a few × more FLOPs; model training compute grew far faster.

Plain data parallelism copies the whole model to every GPU. What does it reduce?

B. Each GPU processes a slice of the batch, so the step finishes sooner, but every GPU still holds the full model, gradients and optimizer state. Fitting the model needs sharding (ZeRO (Zero Redundancy Optimizer)/FSDP (Fully Sharded Data Parallel)), tensor or pipeline parallelism.
4 · Core idea

Four axes of parallelism

Data (DP)

Each GPU gets different examples; gradients are averaged with an all-reduce. Sharded variants (ZeRO, FSDP) also split the model states.

Tensor (TP)

Split every weight matrix across GPUs; partial results are combined with all-reduces in every layer. Needs NVLink-class bandwidth.

Pipeline (PP)

Give each GPU a contiguous block of layers; activations flow stage to stage. Costs pipeline "bubbles".

Context (CP)

Split a long sequence across GPUs; attention exchanges keys and values. MoE models add expert parallelism (EP).

At a glance

Real runs combine all of them (deck 10).

5 · How it works

All the axes, side by side animation

Pick an axis. The animation shows four GPUs and what moves between them; the panel says what it splits, its pros and cons, and who uses it.

Data parallelism (DDP)

Every GPU holds a full copy of the model and processes different examples. After the backward pass, gradients are averaged with one all-reduce, so all copies stay identical.

Pros
  • Simplest: no change to the model code
  • Throughput scales almost linearly with GPUs
  • The gradient all-reduce overlaps with the backward pass
Cons
  • Does not help the model fit: every GPU keeps all 16 bytes per parameter
  • The global batch grows with the number of GPUs
  • Every step all-reduces every gradient

In production: Every large run uses a data axis, usually outermost, across nodes. On its own it is enough only for models that fit on one GPU.

Sharded data parallelism (ZeRO, FSDP)

Data parallelism where each GPU stores only a 1/N shard of the parameters, gradients and optimizer state. A layer's full weights are all-gathered just before it runs and freed after; gradients are reduce-scattered.

Pros
  • Model states shrink N-fold, so much larger models fit
  • Same programming model as data parallelism
  • Communication can be prefetched and overlapped
Cons
  • About 1.5× the traffic of plain data parallelism
  • Needs enough compute per GPU to hide the all-gathers
  • At the largest scale it still has to be combined with other axes

In production: Llama 3 405B uses FSDP as its data axis (64 to 128 ways). DeepSeek-V3 uses ZeRO-1 (only optimizer state sharded). PyTorch FSDP2 is the standard implementation.

Tensor parallelism (TP)

Every weight matrix is split across GPUs (by columns, then by rows). All GPUs see the same input; each computes part of every layer, and partial results are summed with all-reduces inside each layer.

Pros
  • Splits both weights and compute of every layer
  • No pipeline bubble; works at any batch size
  • Also cuts activation memory when combined with sequence parallelism
Cons
  • Two all-reduces per layer in the forward pass (two more in backward), on the critical path
  • Needs NVLink-class bandwidth, so it rarely goes beyond one 8-GPU node
  • Matmuls get smaller and less efficient as the TP (tensor parallelism) degree grows

In production: Inside a node. Llama 3 405B: TP 8. DeepSeek-V3 trained without tensor parallelism by saving memory elsewhere.

Pipeline parallelism (PP)

The layers are split into stages, one per GPU group. Each batch is cut into micro-batches that flow stage to stage; only the activations at stage boundaries move between GPUs.

Pros
  • Only point-to-point transfers at stage boundaries, so slower inter-node links are fine
  • Splits the weights by layers
  • Scales to many nodes for the largest dense models
Cons
  • Pipeline bubble: idle time of about (p − 1)/m of the ideal step time
  • Needs many micro-batches, which constrains the batch size
  • Stages must be balanced (embedding and loss layers are uneven); schedules (1F1B, interleaved, DualPipe) are complex

In production: Llama 3 405B: PP (pipeline parallelism) 16. DeepSeek-V3: 16-way PP with its DualPipe schedule, which overlaps communication with compute.

Context parallelism (CP)

The sequence is split into chunks, one per GPU. Everything except attention is local; for attention, keys and values are exchanged (in a ring or by all-gather) so each GPU's queries see the whole context.

Pros
  • Splits activations along the sequence, enabling 100K+ token training
  • Attention compute is split too
  • Can be combined with all other axes
Cons
  • Keys and values exchanged in every attention layer
  • Causal masks need load balancing across chunks
  • Only worth it for long sequences

In production: Llama 3 405B: CP (context parallelism) 16 for its 131,072-token long-context stage, CP 1 (off) for the 8,192-token stage.

Expert parallelism (EP)

For Mixture of Experts models: experts are spread over GPUs. A router sends each token to its experts on other GPUs (all-to-all dispatch), the experts run, and results come back (all-to-all combine).

Pros
  • Total parameters grow without growing compute per token
  • Each expert sees a larger batch, so its matmuls stay efficient
  • Combines with data parallelism for the non-expert layers
Cons
  • Two all-to-alls per MoE layer in the forward pass, two more in backward, often across nodes
  • Load imbalance: popular experts become stragglers
  • Communication can equal compute (DeepSeek-V3 reports about 1:1), so overlap is essential

In production: DeepSeek-V3: 64-way EP spanning 8 nodes. Needed by every large MoE model.

Dense models

Tensor parallelism inside the node, pipeline across nodes, sharded data parallelism outermost; add context parallelism only for long-context training.

MoE models

Expert parallelism replaces most of the need for tensor parallelism; DeepSeek-V3 used pipeline + expert + ZeRO-1 data parallelism.

Smaller models

If the model fits with sharding, FSDP alone is simplest and is what most fine-tuning and sub-70B runs use.

Pick by bottleneck

Doesn't fit: shard (FSDP), then TP or PP. Too slow: add data parallel replicas. Sequence too long: CP. MoE: EP.

Hardware context

Bandwidth falls about 10× per step away from the GPU (HBM (high-bandwidth memory) 3,350 · NVLink 450 · network 50 GB/s per direction on H100 systems). The chattiest parallelism goes on the fastest links. See GPU deck 05 for the network and collectives.

5 · How it works

Worked example: one GPU vs a 70B model

70B parameters, 15T training tokens, mixed-precision Adam (16 bytes per parameter), H100 at 989 TFLOP (trillion floating-point operations)/s with 40% MFU (model FLOPs utilization).

Worked example

  1. Model states: 16 × 70B = 1.12 TB, versus 80 GB of HBM (high-bandwidth memory) on one GPU: 14× too much.
  2. Compute: 6 × N × D = 6 × 70B × 15T = 6.3e+24 FLOPs.
  3. On one GPU: 6.3e+24 ÷ (989 TFLOP/s × 0.4) ≈ 505 GPU-years.
  4. On 16,384 GPUs at the same efficiency: ≈ 11 days.
Memory forces the model to be split; time forces thousands of GPUs. Both must happen without wasting the GPUs on communication.
6 · Why it works

Why combining axes works

Each axis has a different cost

TP communicates most and needs NVLink; DP communicates least per FLOP and tolerates the network; PP sits in between.

Memory and speed are separate knobs

Sharding and TP/PP make it fit; DP and CP add throughput; recomputation trades compute for memory.

Overlap hides traffic

Gradient all-reduce overlaps the backward pass; pipeline sends overlap compute; ring attention overlaps K/V passing.

Real systems prove it

Llama 3 405B trained on 16,384 H100s with TP, CP, PP and FSDP-style DP at 38–43% MFU.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Just use more GPUs with data parallelism."

DP alone keeps a full copy of the model on every GPU; past ~1–2B parameters it no longer fits without sharding or model parallelism.

"Model parallelism is always slower."

It costs communication, but it is the only way large models fit, and with good placement (TP on NVLink) the overhead is moderate.

"Linear scaling is the default."

Communication, bubbles and stragglers grow with scale; 40% MFU at 16K GPUs is considered very good.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Training FLOPs ≈ 6·N·D. Forward 2, backward 4 per parameter per token.
  • Model states ≈ 16 bytes per parameter. BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) weights and grads + FP32 (32-bit floating point) master, m and v.
  • Activations are the third bill. They scale with batch × sequence × layers (deck 08).

⚠ Traps

  • Thinking more GPUs only add speed. Many techniques exist mainly to make the model fit.
  • Ignoring communication. Every split adds traffic; the art is hiding it behind compute.
  • Counting peak FLOPs. Plan with realistic MFU (~40% for large runs).

Which parallelism axes reduce memory per GPU, and which mainly add throughput?

Memory: sharded DP (ZeRO/FSDP), TP, PP, CP (activations). Throughput: plain DP (more examples in parallel) and CP for long sequences.

Why is tensor parallelism usually kept inside one node?

It all-reduces activations in every layer, many times per step; only NVLink-class bandwidth makes that cheap.
9 · Key takeaway

Key takeaway

Large-model training is distributed because the model does not fit and one GPU is far too slow; four axes (data, tensor, pipeline, context) plus experts split the work.
Say it in 30 seconds

A 70 billion parameter model needs about 1.1 terabytes for weights, gradients and Adam state and would take decades of GPU time on one H100. So training is split. Data parallelism gives each GPU different examples and averages gradients; sharded data parallelism also splits the model states. Tensor parallelism splits each matrix and needs fast NVLink. Pipeline parallelism splits the layers into stages. Context parallelism splits long sequences, and MoE models add expert parallelism. Real runs combine them so that the chattiest communication rides the fastest links.

Problem: memory (16 B/param) and time (6·N·D) both exceed one GPU by orders of magnitude.
Core idea: split along data, tensor, pipeline, context (and expert) axes.
Practice: combine axes; put the chattiest on NVLink; overlap communication with compute.
