Distributed Training · 02

Data parallelism

The simplest way to use many GPUs (graphics processing units): copy the model, split the batch, average the gradients. How the all-reduce works and how PyTorch hides it behind the backward pass.

What is the problem?One GPU processes the batch too slowly. Giving each GPU part of the batch is easy, but every GPU must end each step with the same, averaged gradient.
Core ideaEach GPU runs forward and backward on its own micro-batch, then a ring all-reduce averages the gradients (each GPU sends ≈ 2× the gradient size). Bucketing starts all-reducing gradients as soon as they are ready, so communication overlaps the backward pass.
1 · Problem

Copy the model, split the batch

Four GPUs each process a quarter of the batch. Their gradients differ; before the optimizer step they must be averaged so every copy stays identical. Press play to see one step.

Illustrative timeline: backward produces gradients layer by layer from the last layer; buckets of gradients can be all-reduced while earlier layers are still computing.

2 · Limitation

What makes naive data parallelism slow

Wait, then talk

All-reducing after the backward pass finishes leaves the network idle during compute and the GPUs idle during communication.

Many tiny messages

All-reducing every parameter tensor separately pays per-message latency thousands of times.

Full copies everywhere

Every GPU stores the full model, gradients and optimizer state; DP (data parallelism) adds no memory headroom.

3 · Your turn

How much does each GPU send?

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

Ring all-reduce over N GPUs on a gradient of S bytes. Roughly how many bytes does each GPU send?

C. Reduce-scatter sends (N−1)/N·S and all-gather another (N−1)/N·S: about 2·S per GPU, nearly independent of N. That is why the bandwidth cost of DP stays flat as you add GPUs.
4 · Core idea

Average gradients with a ring, overlap it with backward

Ring all-reduce

Reduce-scatter (each GPU ends up owning one summed chunk) then all-gather (everyone receives every chunk). Built into NCCL (NVIDIA Collective Communications Library).

Bucketing

Group gradients into buckets of a few tens of MB and launch each bucket's all-reduce as soon as it is complete in the backward pass.

Exact

The averaged gradient equals the full-batch gradient, so DP gives the same model as one big GPU would.

At a glance

Mathematically identical to one GPU on the whole batch.

5 · How it works

Ring all-reduce, step by step

Four GPUs, each with a gradient split into four chunks. Step through reduce-scatter (sum as you go) and all-gather (copy the finished chunks). Notebook 01 implements exactly this.

5 · How it works

Worked example: is the all-reduce hidden?

An 8B model (16 GB of BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) gradients), 8 GPUs in a ring over 400 Gb/s network cards (50 GB/s), 8,192 tokens per GPU per step, H100 at 40% MFU (model floating-point-operation utilization, the share of peak compute spent on the model's math).

Worked example

  1. Bytes each GPU sends: 2 × (N − 1)/N × 16 GB = 28 GB.
  2. Time at 50 GB/s: 0.56 s (bandwidth only).
  3. Compute per step: 6 × 8B × 8,192 tokens ÷ (989 TFLOP (trillion floating-point operations)/s × 0.4) = 0.99 s, of which the backward pass is about two thirds (0.66 s).
  4. With bucketing, most of the all-reduce runs during the backward pass; without it, the GPUs would idle for the whole all-reduce after every step.
Communication (0.56 s) is comparable to compute (0.99 s): overlapping it decides whether DP scales.
6 · Why it works

Why data parallelism scales so well

Flat bandwidth cost

Each GPU sends ≈ 2·S per step regardless of N, so adding GPUs adds compute without adding per-GPU traffic.

Communication can hide

Backward pass compute is long; bucketed all-reduce runs underneath it. PyTorch DDP (distributed data parallel) reports near-linear scaling on 256 GPUs.

Limits

Latency grows with N (2(N−1) steps); the global batch grows with GPUs; and memory per GPU never shrinks.

Where it lives

In large runs DP is the outermost axis, across nodes, usually sharded (deck 03).

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Data parallelism makes the model fit."

Every GPU holds the full model, gradients and optimizer state. Only sharding (ZeRO (Zero Redundancy Optimizer)/FSDP (Fully Sharded Data Parallel)) or model parallelism reduces memory.

"All-reduce cost grows with the number of GPUs."

Bandwidth per GPU stays ≈ 2·S; only the latency term grows.

"DP changes the result."

Averaging per-GPU gradients is exactly the full-batch gradient (the same model, up to floating-point order).
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Ring all-reduce sends ≈ 2·S per GPU. Independent of the number of GPUs.
  • Average, not sum. Divide by world size (or scale the loss) so the learning rate stays valid.
  • Gradient accumulation. Skip synchronization on all but the last micro-batch.

⚠ Traps

  • Global batch grows with GPUs. Adding GPUs at a fixed per-GPU batch changes the optimization; retune learning rate.
  • Unbucketed all-reduce. Waiting until backward finishes leaves the network idle during compute and the GPUs idle during communication.
  • Non-deterministic data order. Each rank must read a different shard; duplicated data silently halves effective data.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

Which two collectives make up a ring all-reduce?

Reduce-scatter + all-gather.

What does gradient bucketing buy?

It lets all-reduce start during the backward pass (overlap) and amortizes per-message latency over tens of MB.

Why might you skip gradient synchronization on some micro-batches?

With gradient accumulation, only the last micro-batch's gradients need averaging; syncing every micro-batch wastes bandwidth.
9 · Key takeaway

Key takeaway

Data parallelism copies the model, splits the batch and averages gradients with a ring all-reduce (≈ 2·S per GPU), overlapped with the backward pass.
Say it in 30 seconds

Data parallelism is the simplest way to use many GPUs: each holds the full model, processes its own slice of the batch, and the gradients are averaged before the update so every copy stays identical. The average is computed with a ring all-reduce, a reduce-scatter followed by an all-gather, in which each GPU sends about twice the gradient size regardless of how many GPUs there are. Frameworks like PyTorch DDP group gradients into buckets and start all-reducing them while the backward pass is still running, which hides most of the communication. It does nothing for memory, which is the job of sharding.

Problem: one GPU is too slow; replicas must agree on the gradient.
Core idea: ring all-reduce (≈ 2·S per GPU), bucketed and overlapped with backward.
Limit: full model copy per GPU; global batch grows with GPU count.
