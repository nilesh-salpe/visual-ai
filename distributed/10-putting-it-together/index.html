Putting it together: 4D layouts

How real training runs combine tensor, context, pipeline and data parallelism, and how to reason about a layout from first principles: Llama 3 405B as the worked case.

What is the problem?Each parallelism axis has a different communication pattern, memory effect and scaling limit. Choosing the product TP (tensor parallelism) × CP (context parallelism) × PP (pipeline parallelism) × DP for a cluster is a constrained puzzle.
Core ideaNest the axes by bandwidth need: TP inside the node (NVLink), CP when sequences are long, PP across nodes for memory, DP (sharded) outermost for throughput. Check memory fits, the pipeline bubble is small and the batch is large enough.

2 · Limitation

Why one axis is never enough

TP is capped by the node

Beyond 8 GPUs (HGX) its per-layer all-reduces leave NVLink.

PP is capped by the batch

More stages need more micro-batches to keep the bubble small.

DP is capped by the batch too

The global batch grows with DP; past a point it hurts convergence.

CP is only for long context

It adds K/V traffic that only pays off when sequences are long.

3 · Your turn

Where should TP go?

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

You have 8 GPUs per node with NVLink, and a 400 Gb/s network between nodes. Which degree of tensor parallelism is safest?

B. TP all-reduces activations in every layer, so it must stay within the NVLink domain: TP = 8 on an 8-GPU node, which is what Llama 3 used.
4 · Core idea

Nest the axes by bandwidth

TP innermost

Most frequent, latency-sensitive communication: keep it on NVLink.

CP next

K/V exchange for long sequences; often within or across a few nodes.

PP across nodes

Point-to-point activations only at stage boundaries.

DP outermost

One gradient reduction per step, overlapped with backward; sharded (FSDP/ZeRO (Zero Redundancy Optimizer)) for memory.

At a glance

Llama 3 orders GPU groups as [TP, CP, PP, DP], fastest-changing first, so TP neighbours share a node.

5 · How it works

Worked example: Llama 3 405B on 16,384 H100s

126 layers, d = 16,384. Reported 8K-sequence layout: TP 8, CP 1, PP 16, DP 128 (43% → 41% MFU from 8,192 to 16,384 GPUs; 38% at 131K context with CP 16).

Worked example

  1. GPUs: 8 × 1 × 16 × 128 = 16,384.
  2. Parameters per GPU after TP and PP: 405B / (8 × 16) ≈ 3.16B → 6.3 GB of BF16 weights.
  3. Model states with FSDP over DP 128 on top: 16 × 405B / 16,384 ≈ 0.4 GB per GPU (activations extra).
  4. At 131K context: CP = 16 and DP = 8 instead (8 × 16 × 16 × 8 = 16,384), trading data parallelism for sequence capacity.
TP stays within the 8-GPU NVLink node, PP spreads memory across 16 nodes, CP appears only for long context, and DP supplies the rest of the scale.
6 · Why it works

Why this layout logic works

Communication matches links

The heaviest traffic uses the fastest links, so exposed communication stays small.

Memory is spread multiplicatively

TP × PP divides weights per GPU; FSDP divides model states further; CP and TP+SP (sequence parallelism) divide activations.

Scale comes from DP

Once the model fits, DP adds throughput with flat per-GPU bandwidth.

Efficiency still drops

Llama 3: 43% at 8K GPUs, 41% at 16K; long context 38%. Bubbles, stragglers and exposed communication grow with scale.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"There is one optimal layout."

It depends on model size, sequence length, batch size, cluster topology and memory; Llama 3 changed its layout for long-context training.

"More model parallelism is always safer."

Every model-parallel axis adds communication; use as little as needed to fit, and DP for the rest.

"MFU should be near 100%."

Large runs report 38–55%; the rest is bubbles, communication, recomputation and stragglers.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Order axes by bandwidth. TP innermost, DP outermost.
  • Product = GPUs. TP × CP × PP × DP must equal the cluster (or job) size.
  • Check three numbers. Memory per GPU, bubble (p−1)/(v·m), and global batch.

⚠ Traps

  • TP across nodes. Per-layer all-reduces over the network collapse MFU.
  • Too much PP for the batch. Few micro-batches per pipeline → large bubbles.
  • Ignoring stragglers. At 16K GPUs one slow GPU slows every synchronous step (deck 11).

Llama 3 405B's 16K-GPU 8K-sequence layout?

TP 8 · CP 1 · PP 16 · DP 128. The 128K-context layout used CP 16 and DP 8.

In what order should the axes be nested, from innermost?

TP (NVLink), then CP, then PP, with DP outermost, matching communication volume to link bandwidth.

Name three numbers you check before launching a layout.

Memory per GPU (states + activations), pipeline bubble, and global batch size; also that TP stays within the NVLink domain.
9 · Key takeaway

Key takeaway

Real runs nest TP (NVLink) inside CP, PP and sharded DP, choosing degrees so memory fits, bubbles stay small and the batch stays sensible, as Llama 3 405B did on 16,384 GPUs.
Say it in 30 seconds

No single parallelism axis scales a frontier run, so they are combined. Tensor parallelism has the heaviest, most frequent communication and stays inside a node on NVLink. Context parallelism is added for long sequences. Pipeline parallelism spreads layers across nodes with only point-to-point traffic. Sharded data parallelism is outermost and supplies the remaining scale. Llama 3 405B used tensor 8, pipeline 16 and data 128 on 16,384 H100s at about 41 percent utilization, and switched to context 16 with data 8 for 128K-token training. Before launching, check memory per GPU, the bubble and the batch size.
