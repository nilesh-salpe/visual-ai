Distributing model weights to a large GPU fleet

Getting a 1 TB checkpoint onto 1,000+ GPUs (graphics processing units) quickly: why reading from the object store is slow, chain vs tree vs peer-to-peer swarm, shard-aware fetching, integrity and versioning, and the last hop into GPU memory.

What is the problem?A new 1 TB model version must reach 128 nodes (1,024 GPUs) for a deploy or an urgent scale-out. How do you move the bytes fast and safely?
Core ideaSplit the checkpoint into content-addressed chunks; seed a few nodes from the object store, then let nodes exchange chunks peer-to-peer so upload capacity grows with the fleet. Fetch only the shards each node serves, verify every hash, stream into GPU memory, and switch versions in waves with instant rollback.

1 · Clarify requirements

Clarify before you design

Ask first

Does every node need the whole model or only its shards? Planned deploy or emergency scale-out? What other traffic shares the network? How often do versions change?

Functional

Publish a version; every target node ends up with verified copies of the bytes it needs; switch serving to it and back.

Non-functional (targets)

All nodes ready within about a minute; never use an unverified byte; never overload the object store or the network core.

Scale (assumptions)

1 TB checkpoint; 128 nodes × 8 GPUs; 25 GB/s per node to storage; object store egress 200 GB/s in total.

5 · Deep dive

Deep dive: store, chain, tree or swarm animation

Fan-out is limited by the store's shared egress. A chain is nearly optimal but stalls behind one slow node. A tree uploads to two children, halving each node's send rate. A swarm pulls chunks from many peers at once and routes around slow ones; Uber's Kraken distributes 20,000 blobs of 100 MB–1 GB in under 30 seconds this way.

5 · Deep dive

Deep dive: shards, the last hop and integrity

Shard-aware fetching

A replica with tensor parallelism 8 × pipeline parallelism 2 spans 2 nodes: each node needs only half the layers, each GPU one-eighth of those. The manifest maps chunks to shards.

Into GPU memory

From RAM (random-access memory), a 62.5 GB shard crosses PCIe (Peripheral Component Interconnect Express, the standard expansion bus) Gen5 (64 GB/s) in about a second; from one NVMe (Non-Volatile Memory Express, the fast interface for flash storage) drive (about 7 GB/s) 500 GB takes over a minute. Stream tensors concurrently (vLLM supports the Run:ai Model Streamer, even straight from S3). ServerlessLLM reports 3.6–8.2× faster checkpoint loading.

Urgent scale-out

BlitzScale loads parameters from GPUs that already hold them over the compute network and serves layer by layer before loading finishes: up to 94% lower tail latency than ServerlessLLM.

Integrity and versions

SHA-256 (SHA = Secure Hash Algorithm) per chunk, verified before use; a version is ready only when all needed chunks verify; switch by flipping a pointer in waves, so rollback is instant.

6 · Bottlenecks and scaling

Bottlenecks and scaling

Bottleneck Fix
Object store egress seed a few nodes, then peer-to-peer
Core network links rack-aware peer selection: prefer peers on the same switch
Tracker load shard by version; agents gossip chunk availability
Disk write speed write to RAM first; stripe across NVMe drives
Frequent new versions chunk-level dedupe: only changed chunks move
7 · Failures, monitoring, cost

Failures, monitoring and cost

Failure Handling
Peer dies mid-transfer re-request the chunk elsewhere; discard partial chunks
Corrupt chunk hash mismatch → discard, refetch from another peer, report the source
Bad model version waves with health and quality checks; automatic rollback by pointer flip
Late-joining node fetch from the whole swarm, or load from running GPUs for urgent scale-out

Watch bytes from store vs peers, the completion curve across nodes, the slowest 1%, hash failures and time to serving. Idle GPUs are the real cost: 1,024 GPUs waiting 10 minutes is about 170 GPU-hours per deploy.

8 · Wrap-up

Wrap-up

Decisions

Content-addressed chunks; seed then peer-to-peer swarm; shard-aware fetching; hash verification; versioned waves with pointer-flip rollback.

Trade-offs

A chain is fastest on paper but fragile; a tree is simple but halves send rate; a swarm is robust at the cost of a tracker and more connections.

Next steps

Measure completion curves on real deploys; add rack awareness; keep the previous version cached for instant rollback.

Risks

Transfers competing with live traffic (rate-limit them); tracker as a dependency; disk and RAM for cached versions.

Kraken: P2P Docker registry capable of distributing TBs of data in seconds
Uber · GitHub 2026

Peer-to-peer registry with origins, a tracker and agents; content-addressed blobs; in production at Uber since 2018.

Remember: 20K blobs of 100 MB–1 GB in under 30 s at peak; >1M blobs a day
ServerlessLLM: Low-Latency Serverless Inference for Large Language Models
Fu et al. · OSDI 2024

Loading-optimised checkpoint format and multi-tier (SSD (solid-state drive), DRAM (dynamic random-access memory), GPU) loading, live migration and locality-aware scheduling for serverless LLM inference.

Remember: 3.6–8.2× faster checkpoint loading; 10–200× lower latency in serverless scenarios
BlitzScale: Fast and Live Large Model Autoscaling with O(1) Host Caching
Zhang et al. · OSDI 2025

Loads parameters over the GPU compute network with multicast and serves layer by layer while loading, instead of caching weights on every host.

Remember: up to 94% lower tail latency than ServerlessLLM; 49% less GPU time than non-autoscaling serving (DistServe, vLLM) at the same SLA (service-level agreement)
Loading models with Run:ai Model Streamer (vLLM documentation)
vLLM project · vLLM docs 2026

Reads Safetensors tensors concurrently while streaming them to GPU memory; supports local disk, S3, GCS (Google Cloud Storage) and Azure Blob Storage; sharded loading.
