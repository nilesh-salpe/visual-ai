Multi-tenant LLM API platform

The backend of a public LLM (large language model) API or a ChatGPT-style product: rate limits by tokens, fair scheduling across tenants, priority tiers, routing to model pools and LoRA (Low-Rank Adaptation) adapters, a discounted batch tier, metering, and the cost model behind it all.

What is the problem?Thousands of organisations call several models over one API. Keep time to first token low, stop any tenant from taking all the GPUs (graphics processing units), cap free-user cost, and bill accurately.
Core ideaPut a stateless API gateway in front of model pools. Limit each organisation with token buckets on requests, input tokens and output tokens; admit by priority class, then by fair share of tokens; route to the right pool and to the replica that caches the prompt prefix; fill idle capacity with a discounted batch tier; meter every token for billing.

1 · Clarify requirements

Clarify before you design

Ask first

How many models and sizes? Streaming? Is conversation state on the server (here: no, clients send history)? How skewed are tenants? What does fair mean: equal, or weighted by tier?

Functional

Create a response (streaming or not), choose a model, system prompts, prompt caching, batch jobs, usage reporting, limits per key and per organisation.

Non-functional (targets)

Time to first token p95 under 1 s for paid tiers; 40+ tokens/s per stream; 99.9% monthly availability; isolation: a tenant within its limits keeps its latency target.

Scale (assumptions)

10,000 organisations; peak 5,000 requests/s; 2,000 input tokens (40% cached) and 400 output tokens per request.

5 · Deep dive

Deep dive: who runs next when the GPUs are busy animation

Rate limits cap each tenant, but inside the limits first-come-first-served lets a bulk tenant delay everyone. The Virtual Token Counter (VTC) serves the backlogged tenant that has used the fewest tokens: isolation like a limit, but no idle GPUs while anyone waits. Priority classes (enterprise > paid > free > batch) sit above it.

5 · Deep dive

Deep dive: rate limits, routing and the batch tier

Token buckets

Three per organisation, as on the Claude API: requests, input tokens and output tokens per minute, refilled continuously. Reserve max_tokens at admission, refund the rest. Cache reads can be exempt from the input limit, rewarding prompt caching. Gateways hold local allowances so most checks need no network call.

Routing

Model pool from the request (optionally a router sends easy prompts to the small model); fine-tunes as LoRA adapters on shared base models (S-LoRA, Punica); replica by prefix hash with a load cap, so repeated system prompts hit the prefix cache.

Free-user caps

Daily token budget, small model by default, lower max_tokens, lowest priority, admitted only into capacity paid tiers are not using.

Batch tier

Asynchronous jobs at the lowest priority soak up idle GPUs. The Claude API: up to 100,000 requests or 256 MB per batch, done within 24 hours (most within an hour), 50% cheaper.

GPU capacity at the daily peak time to first token rises autoscale on queue depth and KV-cache (KV = key-value) use; scheduled pre-scaling; shift work to batch
One very large tenant its share starves others weighted fair share; a dedicated pool with reserved capacity
Rate-limit service hot shard for a big org local allowances at gateways; shard by org
Long prompts prefills stall decoding chunked prefill; prefill/decode disaggregation
Thousands of fine-tunes GPU memory for weights LoRA adapters on shared bases; cache adapters by popularity
Single region latency and outages stateless API in several regions; route by latency and capacity
7 · Failures, monitoring, cost

Failures, monitoring and cost

Failure Detection Handling
Replica dies mid-stream stream error, health check client retries with the same request id; billing deduplicated by id
Overload queue depth, admission rejects 429 with retry-after; shed batch then free tiers first; never drop admitted streams
Rate-limit service down error rate fail open with local caps for paid tiers; fail closed for free
Bad deploy canary SLOs (service-level objectives), eval regressions automatic rollback; tenants can pin model versions

Monitor per tenant and model: tokens (input, cached, output), time to first token, inter-token latency, 429s by limit, queue time, cost. Cost per million output tokens ≈ GPU $/hour × GPUs per replica ÷ (tokens/s × 3,600 ÷ 10⁶) ÷ utilisation.

8 · Wrap-up

Wrap-up

Decisions

Token-based limits and fairness (requests differ by 1,000× in cost); stateless API; prefix-aware routing; LoRA for fine-tunes; batch tier for utilisation.

Trade-offs

Dedicated pools give the strongest isolation at lower utilisation; shared pools with fair scheduling give utilisation with weaker guarantees.

Next steps

Load-test replica throughput per model; enable fair scheduling in log-only mode first; publish limits and 429 semantics before enforcing.

Risks and open questions

Pricing of cached tokens; how much capacity to reserve; forecasting throughput of new models. (The Claude API's Priority Tier commitments are no longer sold: offers like this change.)

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Rate limits
Anthropic documentation · platform.claude.com 2026

Limits in requests, input tokens and output tokens per minute (RPM, ITPM, OTPM) per model class, enforced with a token bucket; 429 errors with retry-after; for most models cached input tokens do not count toward ITPM.

Remember: 2M ITPM with an 80% cache hit rate ≈ 10M total input tokens per minute
Batch processing (Claude documentation)
Anthropic · Claude platform docs 2026

Message Batches API: asynchronous processing of large request volumes at lower cost; results within 24 hours, most within an hour.

Remember: 50% cheaper; up to 100,000 requests or 256 MB per batch
Fairness in Serving Large Language Models
Sheng et al. · arXiv 2024

Defines LLM serving fairness by weighted input and output tokens and introduces the Virtual Token Counter scheduler on top of continuous batching; work-conserving.

Remember: provable 2× tight bound on service difference between backlogged clients
S-LoRA: Serving Thousands of Concurrent LoRA Adapters
Sheng et al. · MLSys 2024

Keeps adapters in host memory, pages them into a unified GPU memory pool and batches requests for different adapters together.

Remember: up to 4× throughput vs Hugging Face PEFT (parameter-efficient fine-tuning) and naive vLLM LoRA
Punica: Multi-Tenant LoRA Serving
Chen et al. · MLSys 2024

A CUDA (Compute Unified Device Architecture, NVIDIA's programming platform for its graphics processors) kernel (SGMV (segmented gather matrix-vector multiplication)) that batches requests for many different LoRA adapters through one shared base model.

Remember: 12× throughput, +2 ms latency per token
Efficient Memory Management for Large Language Model Serving with PagedAttention
Kwon et al. · SOSP 2023

Stores the KV cache in fixed-size blocks mapped by a block table, like virtual memory pages, giving near-zero fragmentation and sharing with copy-on-write. The basis of vLLM.

Remember: 2–4× throughput vs FasterTransformer and Orca at the same latency
vLLM Router: A High-Performance and Prefill/Decode Aware Load Balancer for Large-scale Serving
vLLM Team · vLLM blog 2025

Rust load balancer forked from the SGLang model gateway: consistent hashing, power of two, round robin and random; native P/D routing (NIXL (NVIDIA Inference Xfer Library), NCCL (NVIDIA Collective Communications Library)); retries, circuit breakers, Kubernetes discovery, Prometheus metrics.

Remember: Llama 3.1 8B (8P/8D): +25% throughput vs llm-d, 2× a round-robin K8s Service
RouteLLM: Learning to Route LLMs with Preference Data
Ong et al. · ICLR 2025

Routers trained on human preference data (with augmentation) choose between a strong and a weak model per query; they transfer when the model pair changes.

Remember: costs cut by over 2× in some cases without lowering response quality
