Serving a chat assistant to a million daily users

A capacity-driven design for an LLM (large language model) chat product: requirements and service-level objectives, back-of-envelope sizing of GPUs (graphics processing units) and KV (key-value) cache, the serving architecture, and how it scales and fails.

What is the problem?Design the backend for a chat assistant used by 1 million people a day, answering with a 70B-class model, streaming responses with low latency, within a GPU budget.
Core ideaSize the fleet from peak concurrency × KV cache per sequence and from output tokens per second, whichever is larger. Serve with continuous batching, a paged KV cache and prefix caching for the shared system prompt, route with cache affinity, stream tokens, and protect the fleet with quotas, admission control and autoscaling.

1 · Requirements

What the system must do

Functional

Multi-turn chat with history, streaming responses, a system prompt per product, per-user quotas, conversation storage.

Scale (assumption)

1M daily active users × 20 requests each = 20M requests a day; peak traffic 3× the daily average.

Latency targets (assumption)

Time to first token p95 under 1 s; steady streaming of about 40 tokens per second per user.

Constraints

A 70B-class open model on 8-GPU H100 nodes; cost per request matters; safety checks on input and output.

Prompt shape (assumption): about 1,500 input tokens (a 1,000-token shared system prompt plus history) and 300 output tokens per request.

4 · Walkthrough

Life of one message

Prefix caching

The shared system prompt is computed once per replica and reused; vLLM v0.31.0 enables automatic prefix caching by default.

Continuous batching

Requests join and leave the running batch at every step (Orca), keeping GPUs busy.

Chunked prefill

Long prompts are split so they do not stall decodes (Sarathi-Serve).

5 · Deep dive

Deep dive: the KV cache is the budget

Memory, not FLOPs

At the default assumptions about 5,000 sequences are active at peak, needing about 3 TB of KV cache: more than all the weights in the fleet.

Shared prefixes

With prefix caching the 1,000-token system prompt is stored once per replica, not per sequence: unique KV per sequence drops from 1,800 to about 800 tokens.

Paged allocation

PagedAttention allocates KV in fixed blocks (16 tokens by default in vLLM), so fragmentation stays small and memory can be shared.

Levers

FP8 (8-bit floating point) KV halves memory; grouped-query attention (8 KV heads instead of 64) already cut it 8×; shorter retained history and summarisation cut it further.

6 · Scaling

What breaks at 10×

Bottleneck Symptom Response
KV cache full requests queue or get preempted and recomputed more replicas, FP8 KV, shorter history, prefix-aware routing
Prefill spikes time to first token jumps when long prompts arrive chunked prefill; separate prefill and decode pools (DistServe)
Router hot spots affinity sends popular sessions to the same replica consistent hashing with spill-over to the least-loaded replica
GPU supply cannot add replicas fast enough for the peak scheduled pre-scaling, a smaller model tier for overflow, quotas
Conversation store history reads dominate latency cache recent turns next to the gateway
7 · Failures and operations

Failures and operations

Replica failure

Health checks remove a replica; in-flight streams are retried on another replica from the stored history (the client sees a short pause).

Overload

Admission control and per-user quotas; return 429 with retry-after rather than letting latency collapse for everyone.

Bad deploy

Canary new model or prompt versions on a small share of traffic with automatic rollback on latency or quality regressions.

Observe

Time to first token, inter-token latency, KV utilisation, preemptions, tokens and cost per request, safety-filter rates.

8 · Trade-offs

Trade-offs and alternatives

Decision Chosen Alternative Why
Model one 70B-class model router across small and large models simpler first; add routing when cost matters more than consistency
Serving self-hosted vLLM hosted model API (application programming interface) control and unit cost at high volume vs no operations at low volume
Parallelism tensor parallel 8 per node TP (tensor parallelism) 4 with FP8 weights more KV memory per replica vs fewer GPUs per replica
Prefill/decode colocated with chunked prefill disaggregated pools simpler; disaggregate when prefill and decode SLOs (service-level objectives) conflict
Streaming server-sent events WebSockets one-way token streams need nothing more
9 · Summary

Summary

Size from KV and tokens/s

Concurrency × KV per sequence, and output tokens per second: take the larger.

Cache the shared prefix

Prefix caching plus cache-affinity routing makes the system prompt almost free.

Protect the fleet

Quotas, admission control and pre-scaling keep latency stable at peak.

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

Efficient Memory Management for Large Language Model Serving with PagedAttention
Kwon et al. · SOSP 2023

Stores the KV cache in fixed-size blocks mapped by a block table, like virtual memory pages, giving near-zero fragmentation and sharing with copy-on-write. The basis of vLLM.

Remember: 2–4× throughput vs FasterTransformer and Orca at the same latency
Automatic Prefix Caching (design)
vLLM documentation · docs.vllm.ai 2026

Each KV block is hashed with its tokens and the prefix before it; blocks are reference-counted, freed blocks are evicted in LRU (least recently used) order, and cache hits skip prefill.

Orca: A Distributed Serving System for Transformer-Based Generative Models
Yu et al. · OSDI 2022

Iteration-level scheduling (requests join and leave the batch after every decode step) plus selective batching (batch the matmuls, run attention per request).

Remember: 36.9× throughput over FasterTransformer at the same latency (GPT-3 175B)
Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve
Agrawal et al. · OSDI 2024

Chunked prefills plus stall-free scheduling: new requests are added without pausing ongoing decodes, so throughput rises without TPOT (time per output token) spikes.

Remember: 2.6× serving capacity (Mistral-7B, 1 A100) and up to 3.7× (Yi-34B, 2 A100s) vs vLLM; up to 5.6× with pipeline parallelism (Falcon-180B)
DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving
Zhong et al. · OSDI 2024

Defines serving quality as goodput, the request rate served within both TTFT (time to first token) and TPOT targets, and runs prefill and decode on separate GPUs so they stop interfering.

Remember: 7.4× more requests or 12.6× tighter SLO than colocated systems
The Llama 3 Herd of Models
Llama Team, AI (artificial intelligence) @ Meta · arXiv 2024

Dense Transformer with GQA (8 KV heads), RoPE (rotary position embedding) base 500,000, a 128K vocabulary and a document mask; staged long-context pretraining to 128K; post-training with SFT (supervised fine-tuning), rejection sampling and DPO (Direct Preference Optimization) in six rounds.

Remember: 128K context after six stages over ~800B tokens
Rate limits
Anthropic documentation · platform.claude.com 2026

Limits in requests, input tokens and output tokens per minute (RPM (requests per minute), ITPM (input tokens per minute), OTPM) per model class, enforced with a token bucket; 429 errors with retry-after; for most models cached input tokens do not count toward ITPM.

Remember: 2M ITPM with an 80% cache hit rate ≈ 10M total input tokens per minute
