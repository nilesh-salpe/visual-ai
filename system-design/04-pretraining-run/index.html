Planning a pretraining run

Turning a training budget into a plan: compute and time estimates, the data pipeline, the parallelism layout, checkpointing against measured failure rates, cluster operations and the evaluations that decide what to change.

What is the problem?Plan the pretraining of a 70B-parameter model on 15 trillion tokens with 4,096 H100 GPUs (graphics processing units): how long will it take, how do you lay it out, and how do you keep it running?
Core ideaEstimate compute with 6 × parameters × tokens and time with an assumed MFU (model floating-point-operation utilization, the share of peak compute spent on the model's math); lay out tensor parallelism inside nodes, pipeline parallelism across nodes and sharded data parallelism for the rest; set the checkpoint interval from the failure rate (Young/Daly); automate detect → drain → restart; de-risk choices with small-scale ablations first.

1 · Requirements

What the run must deliver

Target (assumption)

A 70B dense transformer trained on 15T tokens of a curated mixture, then handed to post-training.

Resources (assumption)

4,096 H100 GPUs (512 nodes of 8) with a high-bandwidth network, a parallel file system for data and checkpoints.

Constraints

A fixed calendar budget; failures are routine at this scale; every decision about data and architecture is hard to undo mid-run.

Success

Hit the planned loss and evals on schedule, with fully reproducible data and code.

4 · Walkthrough

Laying out the model

Tensor parallel 8, inside a node

Splits each layer's matrices across the 8 GPUs joined by NVLink, where the frequent all-reduces are cheap.

Pipeline parallel, across nodes

Splits layers into stages; micro-batches keep stages busy; interleaved schedules shrink the bubble.

Sharded data parallel for the rest

FSDP (Fully Sharded Data Parallel) / ZeRO (Zero Redundancy Optimizer) shards parameters, gradients and optimizer state across data-parallel ranks: e.g. 4,096 / (8 × 4) = 128 replicas with 4 pipeline stages.

Context parallel for long context

For long-sequence phases split the sequence across GPUs too; Llama 3 405B moved to context parallel 16 for its long-context stage.

5 · Deep dive

Deep dive: checkpointing against failures

Failures are the norm

Llama 3 405B pretraining: 466 interruptions in 54 days, 419 unexpected; only 3 needed significant manual intervention because recovery was automated.

Interval from the failure rate

Young/Daly: τ* ≈ √(2 δ M) for save time δ and mean time between failures M. At the Llama 3 rate a 4,096-GPU job fails about every 12 hours: with 5-minute saves, checkpoint roughly every 86 minutes.

Make saves cheap

Asynchronous, sharded checkpoints written in the background shrink δ, which shortens the interval and the work lost.

Resume exactly

Checkpoint the optimizer state, RNG (random number generator) state and data-loader position too, so a resumed run is the same run.

6 · Scaling

What breaks at larger scale

Bottleneck Symptom Response
Failure rate more interruptions as GPUs grow automated detect → drain → requeue, hot spares, faster checkpoints
Stragglers one slow GPU slows every synchronous step per-rank step-time monitoring, drain slow nodes
Network collectives dominate step time topology-aware placement, overlap communication with compute
Storage checkpoint writes stall training asynchronous sharded writes, staged to local NVMe (Non-Volatile Memory Express, the fast interface for flash storage) first
Loss spikes divergence late in the run monitor gradient norms; roll back and skip data; stability measures from the start
7 · Failures and operations

Failures and operations

Automated recovery

Health checks and job watchdogs detect failures; the scheduler drains bad nodes, requeues the job and resumes from the latest checkpoint on spares.

Silent data corruption

Bad numerics without a crash: compare loss and gradient statistics across ranks, test suspect GPUs (GPU failures deck).

Data problems

A bad shard or mixture bug shows up as loss anomalies: versioned shards make rollback precise.

Observe

Tokens per second, MFU, step time per rank, loss and gradient norm, interruptions by cause, time lost per interruption.

8 · Trade-offs

Trade-offs and alternatives

Decision Chosen Alternative Why
Data decisions ablate at small scale first decide at full scale DataDecide: 150M-parameter rankings predicted ~80% of 1B comparisons, far cheaper
Parallelism TP (tensor parallelism) 8 + PP (pipeline parallelism) + FSDP FSDP only a 70B model with long sequences needs model parallelism to fit and to scale
Checkpoints asynchronous, sharded, every ~1.5 h synchronous, rare cheaper saves allow more frequent ones and lose less work
Scheduling dedicated reservation with spares shared queue restarts must not wait behind other jobs
Precision BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) with selective FP8 (8-bit floating point) FP8 everywhere FP8 speeds GEMMs (general matrix multiplications) but adds stability risk; validate at small scale

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

The Llama 3 Herd of Models
Llama Team, AI (artificial intelligence) @ Meta · arXiv 2024

Dense Transformer with GQA (8 KV (key-value) heads), RoPE (rotary position embedding) base 500,000, a 128K vocabulary and a document mask; staged long-context pretraining to 128K; post-training with SFT (supervised fine-tuning), rejection sampling and DPO (Direct Preference Optimization) in six rounds.

Remember: 128K context after six stages over ~800B tokens
Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism
Shoeybi et al. · arXiv 2019

Intra-layer (tensor) model parallelism that splits each attention and MLP (multilayer perceptron) block across GPUs with only a few all-reduce operations, implemented in plain PyTorch.

Remember: 2 all-reduces per transformer block in the forward pass; 76% scaling efficiency on 512 GPUs
ZeRO: Memory Optimizations Toward Training Trillion Parameter Models
Rajbhandari et al. · SC 2020

Partitions optimizer states, gradients and parameters across data-parallel workers instead of replicating them.

Remember: 100B+ parameters on 400 GPUs at 15 PFLOP (quadrillion floating-point operations)/s; 8× larger models than prior state of the art
PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel
Zhao et al. · VLDB 2023

PyTorch's ZeRO-3-style fully sharded data parallelism, with flattened parameter units, prefetching and hybrid sharding.

Remember: comparable to DDP (distributed data parallel) speed while supporting much larger models
The FineWeb Datasets: Decanting the Web for the Finest Text Data at Scale
Penedo et al. · NeurIPS Datasets and Benchmarks 2024

15T tokens from 96 Common Crawl snapshots with fully ablated choices: WARC (Web ARChive format) + trafilatura over WET (plain text extracted from Web ARChive records), per-snapshot (not global) MinHash dedup, selected C4 filters; FineWeb-Edu uses an LLM-annotated educational-quality classifier.

Remember: 15T tokens; FineWeb-Edu 1.3T
DataDecide: How to Predict Best Pretraining Data with Small Experiments
Magnusson et al. · arXiv 2025

Controlled pretraining over 25 corpora, up to 100B tokens and 1B parameters, 3 seeds: rankings at a single small scale are a strong baseline; no scaling-law method among 8 baselines beats it for the same compute; continuous likelihood metrics make benchmarks highly predictable.

Remember: 150M rankings predict ~80% of 1B comparisons; >80% predictable with 0.01% of the compute
MegaScale: Scaling Large Language Model Training to More Than 10,000 GPUs
Jiang et al. · NSDI 2024

Production training system at ByteDance: algorithm-system co-design plus diagnosis tools for stragglers and failures at 10,000+ GPU scale.

Remember: 55.2% MFU on 12,288 GPUs (175B model), 1.34× Megatron-LM
