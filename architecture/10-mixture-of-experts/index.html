Mixture of Experts (MoE)

Replace the dense FFN (feed-forward network) with many expert FFNs and a router that sends each token to a few of them: more parameters without more compute per token, and the balancing problems that come with it.

What is the problem?In a dense model every token uses every parameter, so adding parameters (more knowledge) adds FLOPs (floating-point operations) to every token in training and serving.
Core ideaSwap the FFN for N experts plus a router. Each token is processed by its top-k experts, weighted by the router. Parameters scale with N; compute scales with k. An auxiliary loss keeps the experts evenly used.
1 · Problem

Parameters vs compute per token

Total parameters (what must be stored) vs active parameters per token (roughly what each token computes with), from the papers. In a dense model they are equal; in an MoE (Mixture of Experts) they come apart.

Mixtral 8x7B: 47B total, 13B active. DeepSeek-V2: 236B total, 21B active. Llama 3 70B: dense, so total = active.

2 · Limitation

Why not just make the dense model bigger?

Every FLOP is paid by every token

Doubling a dense model roughly doubles the training and inference compute per token, even for easy tokens.

Knowledge needs parameters

Many capabilities improve with parameter count, but most tokens only need a small part of the model's knowledge at a time.

Serving cost scales with active compute

Decode time per token is driven by the weights each token touches. Fewer active parameters means cheaper tokens, though the memory to hold all experts remains.

4 · Core idea

Router + experts

Experts

N independent FFNs (SwiGLU (Swish-gated linear unit) in Mixtral) replace the single FFN in each layer. Attention stays shared and dense.

Router

A linear layer gives each token a logit per expert. Mixtral: G(x) = Softmax(TopK(x·W_g)), keeping the top 2 logits and softmaxing over just those. Switch Transformer routes to one expert (k = 1).

Combine

y = Σ over the top-k experts of G(x)ᵢ · Eᵢ(x). Different tokens, even in the same sequence, use different experts, and the choice can change at every layer.

DeepSeekMoE: many small experts plus shared ones

DeepSeek-V2 splits experts more finely and isolates some as shared experts that every token uses: each MoE layer has 2 shared + 160 routed experts, with 6 routed experts active per token (236B total, 21B active). Fine-grained experts give the router more combinations to choose from; shared experts hold common knowledge so routed ones don't each have to duplicate it.

At a glance

Parameters scale with N; compute per token scales with k.

5 · How it works

Load balancing and capacity

4,096 tokens, 8 experts, top-1 routing. Increase the router's skew towards some experts and watch three things: each expert's share of tokens, the Switch auxiliary loss, and the tokens dropped when each expert has a fixed capacity of 1.25 × (tokens / experts).

busiest expert's share
tokens dropped

The Switch Transformer loss

loss = α · N · Σᵢ fᵢ · Pᵢ, where fᵢ is the fraction of tokens whose top-1 expert is i and Pᵢ is the average router probability for expert i. Both should be 1/N, and the loss is minimized under uniform routing. The paper uses α = 10⁻²: "sufficiently large to ensure load balancing while small enough to not to overwhelm the primary cross-entropy objective". Expert capacity = (tokens per batch / number of experts) × capacity factor; overflow tokens skip the expert through the residual connection.

5 · How it works

Worked example: Mixtral and expert capacity

Mixtral: 8 experts, top-2. A batch of 4,096 tokens with capacity factor 1.25.

Worked example

  1. Parameters: 47B in total, about 13B active per token (attention and embeddings are shared; 2 of 8 FFNs run).
  2. Expert capacity = tokens / experts × capacity factor = 4,096 / 8 × 1.25 = 640 token slots per expert (counting top-1 assignments).
  3. If routing sends 30% of tokens to one expert, that is 1,228 tokens for 640 slots: 588 are dropped from that expert.
  4. Switch auxiliary loss α·N·Σfᵢ·Pᵢ equals α = 0.01 when perfectly balanced and α·N = 0.08 when collapsed onto one expert.
MoE cuts FLOPs per token but not memory, and only works if routing stays balanced.
6 · Why it works

Why MoE works, and what it costs

Parameters without FLOPs

Switch Transformer reports up to 7× faster pre-training than T5-Base/Large at the same compute, and a 4× speedup over T5-XXL with its trillion-parameter model.

Experts specialize, just not by topic

Mixtral's analysis: expert choice "appears to be more aligned with the syntax rather than the domain", especially in the first and last layers. Don't expect a "math expert".

Memory and communication

All experts must be in memory. Spread across GPUs (expert parallelism), every MoE layer needs an all-to-all exchange to send tokens to their experts and back.

Balance and stability

Without a balancing loss the router collapses onto a few experts. Fixed capacity drops tokens when routing is uneven, and Switch needed extra tricks to train stably in bfloat16.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"Each expert is a domain specialist: one for code, one for maths."

Mixtral's routing analysis found no obvious topic-based assignment. Routing follows syntax and token-level patterns more than domains.

"A 47B MoE with 13B active parameters runs like a 13B model."

Compute per token is close to 13B, but memory must hold all 47B, and expert routing adds communication. On memory-bound hardware it does not behave like a 13B model.

"MoE replaces the whole Transformer layer."

Usually only the FFN becomes experts. Attention, norms and embeddings stay dense and shared.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Active ≈ shared + k × expert size. Mixtral: ~13B of 47B per token.
  • Capacity = tokens/N × capacity factor. Overflow tokens skip the expert via the residual.
  • Aux loss minimum = α. At uniform routing fᵢ = Pᵢ = 1/N.

⚠ Traps

  • "Runs like a 13B model." Memory must hold all 47B; expert parallelism adds all-to-all traffic.
  • Expecting topic experts. Mixtral's routing follows syntax more than domain.
  • Ignoring drops. Imbalanced routing silently skips tokens at fixed capacity.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

In Mixtral, how are the gate weights computed?

Softmax over the top-2 logits: G(x) = Softmax(TopK(x·W_g)).

What value does the Switch auxiliary loss take under perfectly uniform routing, and under total collapse onto one expert?

Uniform: fᵢ = Pᵢ = 1/N, so the loss = α·N·N·(1/N²) = α. Collapse: f = P = 1 for one expert, so the loss = α·N.

Why do MoE models drop tokens, and what happens to a dropped token?

Each expert has a fixed buffer (capacity = tokens/experts × capacity factor) so shapes stay static. Tokens routed to a full expert are dropped from that layer's FFN and carried forward by the residual connection.
9 · Key takeaway

Key takeaway

MoE swaps the FFN for many experts and a top-k router: parameters grow with the number of experts, compute with k, and a balancing loss keeps the experts evenly used.
Say it in 30 seconds
