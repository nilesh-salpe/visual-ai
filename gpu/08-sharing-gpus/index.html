Sharing GPUs:
from time-slices to multi-tenant serving

An idle H100 still costs money. This deck covers the ways to share one GPU (time-slicing, MPS (NVIDIA Multi-Process Service), MIG (Multi-Instance GPU, hardware partitioning of one GPU)), the ways to share a model across users (continuous batching, multi-LoRA), and the ways to share a cluster (gang scheduling, quotas, preemption).

01 · Why share

Most small workloads use a fraction of a GPU

Notebooks, small inference services, embedding models and CI (confidence interval) jobs often use 5–30% of a GPU. If each gets a whole H100, most of the fleet sits idle. Choose the workloads and compare how many GPUs they need with and without packing.

03 · One GPU

Time-slicing vs MPS: taking turns vs running side by side

With time-slicing, processes take turns owning the whole GPU, and there is a context-switch cost at each turn. With MPS, one shared server context lets kernels from different processes run on different SMs at the same time.

SM utilization
each process's slowdown vs running alone
memory

Model: each process launches kernels that need the given share of SMs. Time-slicing runs them one at a time with about 5% switch overhead. MPS packs them onto SMs until the GPU is full.

Time-slicing never makes a GPU busier than one process can make it; it only shares its time. MPS improves utilization when each process is too small to fill the GPU, but a fatal fault in one client can affect the others.
04 · One GPU

MIG: split an H100 into as many as 7 hardware-isolated GPUs

Multi-Instance GPU divides the chip into 7 compute slices and 8 memory slices (10 GB each). Each instance gets its own SMs, L2 cache slice and memory controllers. Add profiles to build a layout.

H100 80 GB profiles: 1g.10gb · 1g.20gb · 2g.20gb · 3g.40gb · 4g.40gb · 7g.80gb. Click an instance to remove it. Simplified: real MIG also has placement rules about which slice positions each profile may start at.

MIG is the only option that gives guaranteed QoS and fault isolation, so it suits multi-tenant inference, embeddings and small models. The cost is coarse fixed sizes, a GPU that has to be drained to repartition, and no NVLink peer-to-peer between instances.
NVIDIA MIG User Guide (H100 supported profiles).
05 · One model

Continuous batching: one model, many users, no waiting for the slowest

With static batching, a batch of 4 requests holds its slots until its longest output finishes. Continuous (in-flight) batching schedules at every decode step: when one request finishes, the next one takes its slot straight away.

Continuous batching combined with paged KV (deck 03) is what made vLLM, TGI (Hugging Face's Text Generation Inference server), SGLang and TensorRT-LLM several times faster than naive serving. It is the default way a single model is shared among many users.
Yu et al., "Orca: A Distributed Serving System for Transformer-Based Generative Models" (OSDI 2022).
06 · One model

Multi-LoRA: hundreds of fine-tuned variants sharing one base model

A LoRA (Low-Rank Adaptation) adapter for a 70B model is only a few hundred MB. Keep one copy of the base weights and load adapters as needed. Requests for different adapters can still go in the same batch, using custom kernels (Punica's SGMV (segmented gather matrix-vector multiplication), S-LoRA).

one adapter (BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats))
H100s for full copies
H100s with multi-LoRA

Llama-3-70B shapes. LoRA is applied to all attention and MLP (multilayer perceptron) projections: r × (d_in + d_out) parameters per matrix × 7 matrices × 80 layers. GPU count covers weights only; add KV cache on top.

For SaaS-style (SaaS = software as a service) per-customer fine-tunes, multi-LoRA changes the cost from roughly N × (a whole deployment) to one deployment plus small adapters. The trade-off is some kernel overhead and adapter-swap latency for adapters that are rarely used.
Worked example

Worked example: one H100 for seven small services

Seven internal services each need ~8 GB of memory and a small share of compute.

Worked example

  1. Time-slicing: all seven take turns on the whole GPU; a busy service delays the others, and memory isn't isolated.
  2. MIG: seven 1g.10gb instances, each with its own SMs, L2 slice and ~10 GB of memory: guaranteed isolation and QoS.
  3. MPS: processes share SMs concurrently with soft limits: better utilization, weaker isolation.
  4. If all seven are LoRA variants of one base model, multi-LoRA serving keeps one copy of the base and batches them together (Punica: 12× throughput).
Use MIG when tenants need isolation, MPS for cooperating processes, and model-level sharing (batching, multi-LoRA) when they share a model.
07 · One cluster

Sharing a cluster: gang scheduling, fragmentation and preemption

A distributed training job needs all of its GPUs at once (gang scheduling), preferably on whole nodes within one network pod. Small jobs scattered across nodes leave free GPUs that a large job can't use.

Gang / all-or-nothing

Kueue, Volcano, Slurm: either all N pods start or none do, so a half-placed job never holds GPUs while it waits.

Topology-aware placement

Place by node, then rail or pod. Fill nodes completely before spilling over, so large jobs keep contiguous blocks.

Quotas and preemption

Teams get guaranteed quotas and can borrow idle capacity. Borrowed, low-priority work is preempted (after a checkpoint) when the owner needs it back.

Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • MIG ≤ 7 instances on H100. Fixed profiles; reconfigure only when idle.
  • Share the model, not just the GPU. Continuous batching and multi-LoRA beat partitioning for same-model traffic.
  • Gang scheduling. Distributed jobs need all their GPUs at once.

⚠ Traps

  • Time-slicing for latency-sensitive work. Turns add unpredictable delay.
  • Fragmentation. Leftover GPUs that no job can use idle a cluster.
  • Assuming MPS isolates faults. A crashing client can affect others.
08 · Test yourself

Questions to test your understanding

MIG vs MPS vs time-slicing: when would you use each?
MIG: untrusted multi-tenant or SLO-bound inference (hardware partitioning of memory, cache and SMs, fault isolation), with fixed profile sizes, up to 7 instances. MPS: cooperating processes from one team that each underuse the GPU, such as several small inference workers. It gives real concurrency but weak fault isolation. Time-slicing: dev, notebooks and CI, where convenience matters and performance or isolation guarantees don't. You can combine them, for example MPS inside a MIG instance.
How would you serve 200 customer fine-tunes of a 70B model?
Train them as LoRA adapters and serve with a multi-LoRA server (vLLM, S-LoRA, LoRAX): one copy of the base weights, with adapters in GPU memory or paged in from host memory based on popularity. Mixed-adapter batches use segmented-GEMM kernels, alongside continuous batching and paged KV. Route by adapter for cache locality. Capacity plan: base model ≈ 140 GB plus about 0.4 GB per rank-16 adapter, plus KV. Full fine-tunes would need about 200 separate deployments.
Why can't a 64-GPU job start when the cluster shows 100 free GPUs?
Fragmentation plus gang and topology constraints. The free GPUs are scattered across partly used nodes and pods, and the job needs whole nodes, ideally in one pod, all at the same time. Fixes: bin-packing placement for small jobs, reserving or draining nodes for large jobs, backfill of short jobs that finish in time, priority preemption, and placing small inference and dev work on separate pools (or MIG).
What's continuous batching and why is it a big win?
Scheduling happens at each decode step rather than per request. Finished sequences leave and waiting ones join immediately, so slots aren't held by padding until the longest output ends. Throughput goes up several times and queueing latency goes down. It pairs with chunked prefill (splitting long prompts so decode steps aren't blocked) and paged KV (no per-request contiguous allocation).
09 · Take it with you

Four things to remember

Time-slicing shares time, MPS shares SMs, and MIG partitions the hardware. Isolation goes up in that order and flexibility goes down.
MIG on an H100: 7 compute slices × 8 memory slices of 10 GB, giving profiles 1g.10gb up to 7g.80gb.
To share one model: continuous batching and paged KV for many users, multi-LoRA for many fine-tunes.
To share a cluster: gang scheduling, topology-aware packing, quotas with borrowing, and preemption after checkpoint.

Remember: 12× throughput, +2 ms latency per token
