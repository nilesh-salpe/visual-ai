GPU for GenAI · 01

What a GPU is,
and how it thinks

A CPU (central processing unit) is built to finish one task quickly. A GPU (graphics processing unit) is built to finish a huge number of tasks at once. This deck covers the chip, its execution model, and the details that matter in practice: warps, occupancy, Tensor Cores and wave quantization.

01 · Two philosophies

Same silicon budget, spent on opposite goals

A CPU spends most of its area on making a single thread fast: big caches, branch predictors and out-of-order logic. A GPU spends it on arithmetic units, and keeps just enough control logic to feed them.

Hover or tap a block to see what it does.

Schematic, not to scale. An H100 has 132 active SMs (streaming multiprocessors), each with 128 FP32 (32-bit floating point) lanes and 4 Tensor Cores, which comes to roughly 17,000 FP32 lanes. A server CPU has a few dozen cores, each with a 16-lane SIMD (single instruction, multiple data) unit.

A CPU minimizes latency: one thread finishes as fast as possible. A GPU maximizes throughput: the most total work per second, even if each thread is slow.

At a glance

You write one thread; the hardware runs thousands at once in warps of 32 across 132 SMs (streaming multiprocessors).

02 · Two philosophies

Small jobs go to the CPU. Big parallel jobs go to the GPU.

Every GPU launch has a fixed overhead before any math starts. Drag the slider to change the size of the job and watch where the crossover happens.

Illustrative model: CPU at about 4 TFLOPS (trillion floating-point operations per second) of FP32 with no launch cost. GPU at about 60 TFLOPS of FP32 (no Tensor Cores) plus about 10 µs of launch and sync overhead. With Tensor Cores the GPU side gets about 15× faster still.

This is why small kernels hurt. A transformer step that runs thousands of tiny kernels is limited by launch overhead, not math. CUDA (Compute Unified Device Architecture, NVIDIA's programming platform for its graphics processors) Graphs and torch.compile fusion exist to fix exactly that.
03 · Anatomy

Inside an H100: GPCs, SMs, L2, and HBM

The basic building block is the Streaming Multiprocessor (SM). SMs are grouped into GPCs (graphics processing clusters), they share one L2 cache, and they read from HBM (high-bandwidth memory) stacks placed next to the die. Click any part.

Full GH100 die: 8 GPCs × 9 TPCs (texture processing clusters) × 2 SMs = 144 SMs. The H100 SXM (NVIDIA's socketed module form factor for data-center graphics processors) product enables 132; the rest are fused off to improve manufacturing yield (shown greyed out).
NVIDIA H100 Tensor Core GPU Architecture whitepaper (2022). Which SMs are disabled varies from chip to chip; the pattern here is illustrative.

05 · Programming model

SIMT: one instruction, 32 lanes, and the cost of if

A warp issues one instruction at a time to all 32 lanes. When lanes take different branches, the warp runs each path in turn with the inactive lanes masked off. This is called divergence.

Dense linear algebra rarely branches, which is one reason it suits GPUs so well. Data-dependent control flow, such as MoE (Mixture of Experts) routing, sampling or sparse ops, is where divergence and imbalance show up.
06 · Programming model

GPUs hide memory latency by switching warps

A load from HBM takes hundreds of cycles. A CPU covers that wait with big caches and out-of-order execution. A GPU covers it by switching to another warp that is ready to run, which costs no cycles. That only works if enough warps are resident, which is called occupancy.

issuing mathwaiting on memoryscheduler busy

Model: each warp computes for 40 cycles, then waits L cycles for a load. You need about (40 + L) / 40 warps to keep the scheduler busy. Occupancy is capped by registers (64K 32-bit registers per SM), shared memory per block, and a hard limit of 64 warps per SM.

"Why does my kernel use 255 registers per thread and run slowly?" Too many registers per thread means fewer resident warps, and with fewer warps the memory stalls are no longer hidden.
07 · Tensor Cores

Tensor Cores: hardware that does a matrix multiply in one step

A CUDA core does one fused multiply-add per lane per cycle. A Tensor Core does a whole small matrix multiply-accumulate, D = A·B + C, on a tile in a single operation. Almost all of an H100's headline FLOPs (floating-point operations) come from Tensor Cores.

Each partition of an SM has one Tensor Core; a warp issues an MMA instruction (Hopper adds wgmma across 4 warps) and the tile math happens in hardware.

H100 SXM peak throughput in TFLOPS (TOPS (trillion operations per second) for INT8 (8-bit integer)). Log scale.

If your work isn't a matmul in BF16 (bfloat16, a 16-bit floating-point format with the exponent range of 32-bit floats) or FP8 (8-bit floating point), you are using about 7% of the chip. That's why everything in a transformer is arranged around GEMMs (general matrix multiplications).
NVIDIA H100 datasheet (SXM5): FP64 34, FP64 Tensor 67, FP32 67, TF32 Tensor 495, BF16 Tensor 989, FP8 Tensor 1,979, INT8 Tensor 1,979 (dense). The 2:4 structured sparsity numbers are twice these.
08 · Tensor Cores

A matmul is split into tiles, and the tiles run in waves across 132 SMs

A GEMM kernel cuts the output matrix into tiles and gives each tile to one SM (one thread block). If the tile count doesn't divide evenly by 132, the last wave leaves most SMs idle.

Try M = N = 1536: that gives 144 tiles, which is 132 + 12, so the chip runs 2 waves and the second one has 120 SMs idle. Choosing dimensions that are multiples of 64 or 128 and fit the SM count can give speedups of 10–40%.
Worked example

Worked example: wave quantization

An H100 SXM has 132 SMs. A matmul is split into 128 × 128 output tiles, and each SM runs one tile at a time.

Worked example

  1. Output 1,408 × 1,536 → 11 × 12 = 132 tiles → exactly 1 wave: every SM busy, 100% use.
  2. Output 1,536 × 1,536 → 12 × 12 = 144 tiles → ⌈144/132⌉ = 2 waves; the second wave has only 12 tiles.
  3. Efficiency = 144 tiles / (2 waves × 132 SMs) = 55%: 9% more work takes about twice as long.
  4. Fixes: choose shapes whose tile count fills whole waves, use smaller tiles, or split K (split-K) to create more tiles.
GPU time is quantized in waves of 132 tiles; matrix sizes just above a wave boundary are the most wasteful.

Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Warp = 32 threads. Branches inside a warp run one after another (divergence).
  • Occupancy hides latency. Enough resident warps per SM let the scheduler switch while others wait on memory.
  • Count waves. tiles ÷ SMs, rounded up, sets the runtime.

⚠ Traps

  • Counting CUDA cores as speed. For AI (artificial intelligence), Tensor Core throughput and memory bandwidth matter far more.
  • Divergent branches. A warp with an if/else pays for both paths.
  • Shapes just past a wave. A slightly larger matrix can take ~2× the time.
10 · Test yourself

Questions to test your understanding

Why does a GPU need tens of thousands of threads in flight?
To hide latency. An HBM access takes hundreds of cycles, and a GPU core has no large caches or out-of-order engine to cover that. Instead, every cycle the warp scheduler picks a warp that is ready to run. With too few resident warps (low occupancy), the units sit idle waiting on memory. By Little's law, the parallelism you need equals latency × throughput.
What is a warp, and why does divergence hurt?
A warp is a group of 32 threads that execute one instruction together (SIMT (single instruction, multiple threads)). When threads in a warp take different branches, the paths run one after another with lanes masked off, so utilization drops by the number of distinct paths. Fixes: arrange data so the threads in a warp take the same branch, or use branch-free arithmetic.
A 1536×1536 GEMM gets fewer TFLOPS than a 2048×2048 one. Why?
Wave quantization. With 128×128 tiles there are 144 output tiles. On 132 SMs that means 2 waves, and the second runs only 12 tiles, so about 45% of SM time is wasted. The 2048 case gives 256 tiles, also 2 waves but much better filled. Small matrices also have low arithmetic intensity. Fixes: pad dimensions, use split-K or stream-K kernels, or choose a different tile size.
What's the difference between CUDA cores and Tensor Cores?
CUDA cores are scalar FP32/INT (integer) lanes, each doing one FMA (fused multiply-add) per cycle. Tensor Cores are dedicated matrix-multiply-accumulate units working in BF16, FP16 (16-bit floating point), TF32 (TensorFloat-32), FP8 and, on Blackwell, FP4 (4-bit floating point). On an H100, BF16 Tensor Core throughput (989 TFLOPS dense) is about 15× the FP32 CUDA-core peak. Softmax, layernorm and activation functions run on CUDA cores. That's why fusing them, or overlapping them with GEMMs as FlashAttention-3 does, matters so much.
What limits occupancy, and is higher occupancy always better?
Three things limit it: registers per thread (64K registers per SM, so 128 registers per thread allows at most 512 threads, or 16 warps), shared memory per block (up to 228 KB per SM on H100), and the cap on threads and blocks per SM (64 warps). Higher occupancy is not always better. Well-tuned GEMM and attention kernels often run at low occupancy with big tiles held in registers, and hide latency through instruction-level parallelism and asynchronous copies (TMA (Tensor Memory Accelerator)) instead.
11 · Take it with you

Four things to remember

A GPU trades per-thread latency for throughput. It has thousands of simple lanes, little cache, and hides latency by switching warps.
The hierarchy is grid → block (on one SM) → warp (32 threads in lockstep) → thread. Block sizes should be multiples of 32, and divergence is serialized.
Tensor Cores provide nearly all the FLOPs. The work has to be expressed as BF16 or FP8 matmuls to use them.
Tile counts and SM counts interact. Wave quantization and launch overhead are the most common causes of "the GPU isn't busy".
