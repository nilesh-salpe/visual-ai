GPU for GenAI · 02

Why GPUs for AI:
FLOPs, bytes, and the roofline

Neural networks are almost all matrix multiplications, and GPUs (graphics processing units) are built to do those. To reason about performance, keep track of FLOPs (floating-point operations), bytes moved, and the ratio between the two. This deck shows how to do that.

Press → or Space to begin.

01 · The workload

A transformer forward pass is mostly matmuls: about 2 FLOPs per parameter per token

Every weight is used in one multiply-add per token, which gives roughly 2·N FLOPs per token for N parameters. Attention adds work that grows with context length. Pick a model and drag the context slider to see when attention starts to matter.

Per-token forward FLOPs. Linear layers (QKV (query, key and value), output projection, MLP (multilayer perceptron)): about 2·N. Attention scores and weighted sum: about 4·L·ctx·d. Training costs about 3× the forward pass (forward + backward), which is where 6·N·D comes from.

At typical context lengths more than 80% of the FLOPs are dense GEMMs (general matrix multiplications), which is exactly the operation Tensor Cores accelerate. Attention FLOPs take over only at very long context.

03 · Roofline

Arithmetic intensity: FLOPs done per byte moved

An H100 can do about 989 TFLOPS (trillion floating-point operations per second) but only read about 3.35 TB/s from HBM (high-bandwidth memory). To keep the Tensor Cores busy, a kernel has to do roughly 295 FLOPs for every byte it loads. That number is the ridge point.

For an n×n matmul the intensity is about n/3: it does O(n³) work on O(n²) data. Elementwise ops do about one FLOP per several bytes, so they are always memory-bound. That is why fusing them into neighbouring kernels matters.
04 · Roofline

The roofline: bandwidth limits the left side, compute limits the right

Attainable FLOPS = min(peak, bandwidth × intensity). Points to the left of the ridge are memory-bound and points to the right are compute-bound. Drag the batch slider to move LLM (large language model) decode along the slope.

Peak dense BF16 / HBM bandwidth: A100 SXM 312 TF / 2.04 TB/s · H100 SXM 989 TF / 3.35 TB/s · B200 (HGX) ~2,250 TF / 8 TB/s. Points use BF16 and d = 8192.
05 · Inference

Prefill is limited by compute; decode is limited by memory bandwidth

Prefill runs all prompt tokens through the model at once, which is one big GEMM. Decode generates one token per step, and each step has to read every weight plus the whole KV (key-value) cache from HBM. Example: Llama 3 70B in BF16 on 8×H100 with tensor parallelism (TP=8), batch 1.

Model: prefill FLOPs ≈ 2·N·P at 60% of 8 × 989 TFLOPS. Decode step ≈ (140 GB weights + KV) ÷ (8 × 3.35 TB/s × 80%). At batch 1 the Tensor Cores sit almost idle during decode.

TTFT depends on compute (prompt length × FLOPs). TPOT depends on bandwidth (bytes ÷ HBM bandwidth). Every discussion of LLM serving uses these two metrics.
06 · Inference

Batching shares one read of the weights across many users

Each decode step reads 140 GB of weights no matter how many sequences are in the batch, so a bigger batch gets more tokens out of each read. KV-cache reads still grow with the batch, and eventually the cache doesn't fit in memory.

Llama 3 70B BF16 on 8×H100 (640 GB). KV cache = 320 KB per token (80 layers × 8 KV heads × 128 dims × 2 (K and V) × 2 bytes).

Batching trades per-user latency for total throughput. At long context, KV-cache reads dominate and decode stays memory-bound at any batch size, which is why GQA (grouped-query attention), MLA (multi-head latent attention), KV quantization and paged KV matter.
07 · Precision

Fewer bits per number: twice the FLOPs and half the bytes each time you halve the width

BF16 keeps FP32 (32-bit floating point)'s exponent range, so training is stable without loss scaling. FP8 (8-bit floating point) and FP4 (4-bit floating point) need scaling factors per tensor or per block (for example the MX (microscaling, block-scaled number formats) formats) because their range is so small.
08 · Utilization

MFU: the percentage of peak FLOPs that does useful model work

MFU = (6·N · tokens/s) ÷ (peak FLOPS × #GPUs). Peak is never reached in practice. Each slider below is one source of lost throughput; they multiply together.

MFU counts only the model's FLOPs. HFU (hardware floating-point-operation utilization, which also counts recomputed work) (hardware FLOPs utilization) also counts recomputation from activation checkpointing, so HFU ≥ MFU.

Large dense pretraining runs typically report about 35–45% MFU. Llama 3 405B reported 38–43% BF16 MFU on 16K H100s.
Llama 3 paper, Table 4; Chowdhery et al., "PaLM" (2022), which introduced MFU.
Worked example

Worked example: estimate a training run on a whiteboard

Llama 3 405B: N = 405B parameters, D = 15.6T tokens, H100 at 989 TFLOP (trillion floating-point operations)/s dense BF16, assume 40% MFU (model FLOPs utilization).

Worked example

  1. Total compute ≈ 6 · N · D = 6 × 405B × 15.6T = 3.79e+25 FLOPs.
  2. GPU-hours = 3.79e+25 ÷ (989 TFLOP/s × 0.4) ÷ 3,600 ≈ 26.6M (Meta reported 30.84M including restarts and other overheads).
  3. On 16,384 GPUs: 26.6M ÷ 16,384 ÷ 24 ≈ 68 days.
  4. Ridge point of H100: 989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOPs per byte; below that, a kernel is memory-bound.
Four numbers (N, D, peak FLOP/s, MFU) give a training budget in 30 seconds.
Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Training ≈ 6·N·D, inference ≈ 2·N per token. Forward 2, backward 4.
  • Ridge point = peak ÷ bandwidth. ≈ 295 FLOPs/byte on H100 in BF16.
  • Decode intensity ≈ batch size. Each weight read serves one token per sequence in the batch.

⚠ Traps

  • Using sparse peak numbers. Datasheet 2:4-sparsity figures are 2× the dense ones.
  • Assuming 100% MFU. Real large runs reach ~40% (Llama 3: 38–43%).
  • Calling decode compute-bound. At small batch it is limited by bandwidth.
09 · Test yourself

Questions to test your understanding

Estimate the max decode speed of a 70B model on one H100, batch 1.
BF16 weights are 140 GB, which doesn't fit in 80 GB. In FP8 they are about 70 GB, which barely fits. Each token has to read all the weights: 70 GB ÷ 3.35 TB/s ≈ 21 ms per token, so at most about 48 tokens/s, and less in practice once KV-cache reads and imperfect bandwidth are included. Compute is nowhere near the limit: 2 × 70e9 FLOPs per token is only about 0.14 ms of H100 compute.
Why is prefill compute-bound but decode memory-bound?
Prefill multiplies a [P × d] activation matrix by every weight matrix, so each weight byte is reused P times and the intensity is about P. Decode uses each weight once per sequence in the batch, so the intensity is about the batch size, far below the ~300 FLOPs/byte ridge. Attention in decode is worse still: every sequence reads its own KV cache, so batching doesn't help it.
How long does it take to train a 70B model on 15T tokens with 4,096 H100s?
6 × 70e9 × 15e12 = 6.3e24 FLOPs. Effective throughput is 4,096 × 989e12 × 0.4 ≈ 1.6e18 FLOPs/s, which gives about 3.9e6 s ≈ 45 days. Then mention what this leaves out: failures and restarts, data loading, and evaluation pauses.
How would you find out whether a kernel is memory-bound or compute-bound?
Work out its arithmetic intensity (FLOPs ÷ bytes) and compare it with the GPU's ridge point (peak FLOPS ÷ bandwidth). Then confirm with a profiler such as Nsight Compute: if achieved DRAM (dynamic random-access memory) bandwidth is close to peak, it's memory-bound; if Tensor Core utilization is close to peak, it's compute-bound. If neither is high, it's limited by latency or launch overhead.
Why are FP8 and FP4 harder to use than BF16?
Their range is tiny: E4M3 tops out at 448 and E2M1 at 6. Outliers in activations overflow, and small gradients round to zero. So you need scaling factors (per tensor, per channel, or per block of 16–32 values as in MXFP8 (8-bit microscaling floating point) and NVFP4 (NVIDIA's block-scaled 4-bit floating point)), higher-precision accumulators, and usually a few sensitive layers (embeddings, the LM (language model) head, normalization) kept in BF16.
10 · Take it with you

Four things to remember

Use 2N FLOPs per token for inference and 6ND for training. Divide by peak × MFU to get time.
Ridge point = peak FLOPS ÷ bandwidth, about 300 FLOPs/byte on an H100. Below it you are limited by memory bandwidth.
Prefill is compute-bound (TTFT); decode is bandwidth-bound (TPOT). Batching amortizes the weight reads but not the KV-cache reads.
Lower precision doubles throughput and halves bytes each step, provided you handle range with scaling factors.
