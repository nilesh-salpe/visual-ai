GPU for GenAI · 05

Cluster topology:
wiring 16,000 GPUs together

Above about 8 GPUs, the network is the computer. This deck covers scale-up vs scale-out, fat trees and rails, the collective operations, why ring all-reduce works, and how TP, PP, DP and EP are placed onto the network.

Press → or Space to begin.

01 · Two tiers

Scale-up inside a node, scale-out between nodes

Each node is a fast NVLink island (450 GB/s per GPU per direction). The islands are connected by a network (about 50 GB/s per GPU). Pick a parallelism type to see which links its traffic uses.

The rule of thumb: the chattiest parallelism goes on the fastest links. TP is synchronous on every layer, so it stays in the node. PP sends activations point-to-point between stages. DP all-reduces gradients once per step and can overlap that with the backward pass.
02 · Network shape

Leaf-spine (fat tree): every endpoint is a few hops from every other

NICs connect to leaf switches, and every leaf connects to every spine. If uplink capacity equals downlink capacity, the network is non-blocking: any half of the cluster can talk to the other half at full rate. Click two endpoints, then reduce the uplinks.

Real clusters add a third tier (leaf → spine → core) above roughly 2–4K GPUs. Meta's Llama 3 RoCE cluster used full bisection bandwidth inside each 3,072-GPU pod and 1:7 oversubscription between pods. Jobs were placed so that the heavy traffic stayed inside a pod.

03 · Network shape

Rail-optimized: GPU i of every node shares one leaf switch

With a top-of-rack layout, all of a node's NICs go to the same leaf. In a rail layout, NIC i of every node goes to leaf i. Data-parallel peers (same local rank on different nodes) are then one switch apart.

NCCL's PXN (PCIe × NVLink) uses this: to reach rail 3 on another node, GPU 0 first moves its data over NVLink to local GPU 3, which then sends it out on its own rail. The NVLink hop is nearly free, and the expensive spine hop is avoided.
04 · Collectives

The five collectives that distributed training is built from

All-reduce = reduce-scatter + all-gather. FSDP and ZeRO-3 split this in two: they all-gather the weights before each layer and reduce-scatter the gradients after it, so each GPU only keeps its own shard.
05 · Collectives

Ring all-reduce, step by step

Split the buffer into N chunks. In each step, every GPU sends one chunk to its right-hand neighbour and adds the chunk it receives. After N−1 steps each GPU holds one fully reduced chunk (reduce-scatter). Another N−1 steps circulate those chunks (all-gather).

Each GPU sends 2·(N−1)/N × the buffer size in total, which is nearly independent of N. Every link is busy in every step. That's why ring all-reduce makes full use of bandwidth.

06 · Collectives

Ring is limited by bandwidth; tree is limited by latency

T_ring ≈ 2(N−1)·α + 2(N−1)/N · S/B. The bandwidth term stays flat as N grows, but the latency term grows linearly. Trees grow only with log N. Change the message size to see which one wins.

ringtree (pipelined, approx.)
For large gradient buckets (hundreds of MB), ring is near optimal. For small, latency-sensitive collectives such as MoE dispatch, decode-time TP all-reduce or many-node all-reduce, trees or in-network reduction (SHARP) win. NCCL picks the algorithm automatically based on size and topology.

09 · Mapping

Expert parallelism means all-to-all, and the busiest GPU sets the pace

In MoE layers each token goes to the GPUs that host its top-k experts (dispatch) and comes back (combine). If the router sends a skewed share of tokens to one expert, that GPU receives more data and every other GPU waits for it.

MoE systems fight this with load-balancing losses (or the auxiliary-loss-free bias used in DeepSeek-V3), capacity limits, node-limited routing (each token goes to at most M nodes), and by putting EP inside the largest available NVLink domain.
10 · Interview

Questions you'll get

You have 1,024 H100s and a 70B model. How do you lay out the parallelism?
Start with TP=8 inside each node on NVLink, which is enough to shard the layers and keep the GEMMs efficient. Add PP of 2–4 across nodes only if memory or activations require it, and run enough micro-batches to keep the bubble small. Put the rest into DP with FSDP or ZeRO-1: 1024 / (8 × 2) = 64 replicas. Check memory per GPU, the global batch size (DP × micro-batch × grad accumulation must stay within a good batch size), and that DP communication overlaps with backward. Then say what you would measure: MFU, exposed communication time, and bubble fraction.
Why is ring all-reduce bandwidth-optimal, and when is it a bad choice?
Every GPU sends and receives 2(N−1)/N × S, which is the lower bound for all-reduce, and all links are used in every step. But it takes 2(N−1) sequential steps, so the latency term grows linearly. At thousands of GPUs, or for small messages, that dominates. Hierarchical schemes (reduce inside the node, then a ring or tree across nodes), double binary trees, and in-network reduction (SHARP) handle that case.
What does "rail-optimized" mean, and why do labs build networks that way?
NIC i of every node connects to leaf (rail) i, so same-rank GPUs across nodes, which are exactly the DP and PP peers, are one switch hop apart. Most training traffic stays inside a rail and never touches the spine. Fewer spine ports are needed and tail latency is lower. Cross-rail traffic is routed over NVLink first (NCCL PXN).
InfiniBand vs RoCE: what's the trade-off?
InfiniBand has lossless credit-based flow control, adaptive routing, SHARP in-network reduction and mature NCCL support, and it is a single-vendor ecosystem. RoCE v2 runs RDMA over Ethernet, which is cheaper and more widely available, but it needs PFC/ECN tuning and congestion control, and ECMP hash collisions on large flows hurt it. Meta trained Llama 3 on RoCE and other labs use IB, so both work at scale. The newer Ultra Ethernet specification aims to close the gap.
What is an MoE all-to-all bottleneck, and how do you reduce it?
Dispatch and combine move every token's hidden state to its experts' GPUs and back, which is bandwidth-heavy and latency-sensitive, and router skew creates hot GPUs. Mitigations: keep EP within the NVLink domain (8, or 72 on NVL72), limit how many nodes each token can be sent to, add load-balancing terms to the router, overlap communication with computation (for example micro-batch interleaving and DeepEP-style kernels), and compress the dispatch data to FP8.
11 · Take it with you

Four things to remember

There are two tiers: the NVLink island (fast and small) and the network (about 9× slower, very large). Map TP → node, PP and DP → network.
Fat tree plus rails: non-blocking inside a pod, oversubscribed above it. Same-rank GPUs share a leaf.
All-reduce = reduce-scatter + all-gather. Ring is bandwidth-optimal at 2(N−1)/N · S, but its latency grows with N.
MoE all-to-all is limited by the busiest GPU. Keep EP in the NVLink domain and balance the router.
