Tokenization quirks in LLMs

Letter counting, arithmetic, leading spaces, prompts that end mid-token, and glitch tokens: many odd LLM behaviours become obvious once you look at the tokens.

What is the problem?LLMs show surprising failures on tasks that look trivial to people, such as spelling, counting letters, adding numbers, or continuing a prompt that ends in a colon.
Core ideaThe model sees token ids, not characters. Character-level facts must be learned indirectly, and unusual token boundaries put inputs outside what the model was trained on.
1 · Problem

Trivial for people, surprisingly hard for models

Spelling and counting letters

"How many r's are in strawberry?"

Arithmetic

Multi-digit numbers arrive in irregular chunks.

Prompt endings

A trailing space or a cut-off "http:" changes the completion.

2 · Limitation

The model never sees letters

After tokenization, " strawberry" is a single id. Nothing in that integer says which letters it contains. Any knowledge of its spelling has to be learned indirectly from training data.

4 · Core idea

Look at the tokens first

When an LLM fails on something character-level, number-level or boundary-sensitive, check how the input was tokenized before blaming "reasoning".

Ids hide characters

Spelling, rhyme, letter counts and character edits all need knowledge the ids don't carry.

Boundaries carry meaning

Training text was tokenized greedily, so an unusual split tells the model something it rarely saw, and that something is misleading.

5 · How it works

Token healing: fixing prompt boundaries

The prompt-boundary problem, from the Guidance project's notebook: in training data URLs are tokenized as http + ://. A prompt ending in http: ends with a lone : token, which the model almost never saw followed by //. Their example model then produced http: //www…, an invalid URL with a space.

guidance-ai/guidance, "Prompt boundaries and token healing" notebook. Token healing "automatically backs up the generation process by one token before the end of the prompt", then constrains the first generated token to start with the removed text.
6 · Why it works

Why each quirk happens

Spelling

The ids are opaque, so character knowledge exists only to the extent the model learned each token's spelling.

Arithmetic

Digits come in irregular chunks (gpt2: 123|45|678; cl100k: 123|456|78), so place value isn't aligned across numbers. Llama 1/2 split every digit, and cl100k/o200k cap groups at 3.

Spaces and case

"hello", " hello" and "Hello" are different ids with separately learned embeddings. Whitespace is part of the token.

Glitch tokens

The tokenizer is trained separately from the model, so some vocabulary tokens barely appear in model training. Their embeddings stay under-trained and inputs containing them can trigger strange outputs (Land & Bartolo, 2024).

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"LLMs read text letter by letter."

They read token ids. In cl100k_base, " strawberry" is a single id.

"A trailing space in a prompt is harmless."

In GPT-style tokenizers a space usually starts the next token. A trailing space leaves the model with an unusual lone-space token, which changes what it predicts.

"Every token in the vocabulary was well trained."

Some tokens are under-trained: present in the vocabulary but nearly absent from model training. " SolidGoldMagikarp" is the famous example, a single token in GPT-2's tokenizer.

How does cl100k_base tokenize "12345678"?

123|456|78: its pre-tokenizer splits numbers into groups of at most 3 digits.

What does token healing do?

It backs up one token and constrains generation to start with the removed text, so the model can produce its natural token (e.g. "://").

Why do under-trained ("glitch") tokens exist at all?

The tokenizer is built separately from model training, on different data, so some vocabulary entries are rare or absent in the model's training data and their embeddings are barely trained (Land & Bartolo, 2024).
9 · Key takeaway

Key takeaway

LLMs see token ids, not characters. Spelling, arithmetic, spacing and prompt-boundary quirks, and glitch tokens, all follow from how text was tokenized.
Say it in 30 seconds

A model receives token ids, so character-level facts like spelling or letter counts are hidden inside opaque tokens: in cl100k_base, " strawberry" is one id. Numbers are chunked irregularly, leading spaces and capitalization change ids, and a prompt that ends mid-token (like "http:") puts the model at a boundary it rarely saw, which token healing fixes by backing up a token and constraining the next. Some tokens, such as GPT-2's " SolidGoldMagikarp", are under-trained because the tokenizer was built on different data from the model.
