Visual Agents · Operations · 01

Evaluating agents

Measuring agents that take many stochastic steps in changing environments: execution-based end-state checks, reliability over repeated trials (pass^k), trajectory review, and the benchmarks that set the bar.

What is the problem?Agents are multi-step and random: the same task can succeed once and fail the next time, many different paths can be correct, and grading by comparing text to a reference answer misses what actually happened.
Core ideaGrade outcomes in the environment (tests pass, database in the goal state, file exists), run each task several times and report pass^k (all k trials succeed) alongside success rate, and review trajectories for how it got there. Build realistic, sandboxed, reproducible environments.

1 · Problem

Why agent evaluation is hard

Stochastic

The same agent and task can succeed and fail on different runs.

Many correct paths

Comparing to one reference trajectory punishes valid alternatives.

Real environments

Websites, APIs (application programming interfaces) and OS (operating system) state change; results must be reproducible.

2 · Core idea

Grade outcomes, measure consistency

Execution-based grading

SWE-bench (SWE = software engineering) runs tests; OSWorld runs per-task evaluation scripts; τ-bench compares the final database state to the goal.

Reliability: pass^k

τ-bench's metric: the chance that all k trials succeed. gpt-4o succeeded on < 50% of tasks and pass^8 was < 25% in retail.

Human baselines

GAIA: humans 92% vs 15% for GPT-4 with plugins; OSWorld and WebArena report similar gaps at release.

Trajectory review

Inspect how the agent succeeded: policy violations, wasted steps, risky actions.

7 · Challenges in production

In production

Regression suites from real traces

Turn production failures into test tasks.

Online monitoring

Track success signals, escalations, cost and latency per task live.

Human review sampling

Regularly read trajectories; metrics miss surprising behaviour.

Gate releases

Prompt, model or tool changes must pass the eval suite before rollout.

Further reading

Key papers

The primary sources behind this deck, each with what it contributed. Links go to the paper (arXiv or the conference page).

τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains
Yao et al. · arXiv 2024

Simulated users, domain APIs and policies; grades the final database state and introduces pass^k to measure consistency across trials.

Remember: gpt-4o < 50% success; pass^8 < 25% in retail
SWE-bench: Can Language Models Resolve Real-World GitHub Issues?
Jimenez et al. · ICLR 2024

Real GitHub issues: the model edits the repository and the project's own tests decide success.

Remember: 2,294 issues; Claude 2 solved 1.96% at release
GAIA: a benchmark for General AI (artificial intelligence) Assistants
Mialon et al. · ICLR 2024

466 real-world questions that are simple for humans but need reasoning, browsing, multimodality and tool use.

Remember: humans 92% vs 15% for GPT-4 with plugins
OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments
Xie et al. · NeurIPS 2024

369 real desktop and web tasks across operating systems with execution-based evaluation scripts.

Remember: humans 72.36% vs best model 12.24% (at release)
AgentBench: Evaluating LLMs as Agents
Liu et al. · ICLR 2024

Eight interactive environments for LLM agents; poor long-term reasoning, decision-making and instruction following are the main failure causes.
