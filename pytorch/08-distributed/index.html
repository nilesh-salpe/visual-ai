Distributed training in PyTorch

The PyTorch APIs (application programming interfaces) behind data parallelism: torchrun, process groups and collectives, DistributedDataParallel and FSDP2's fully_shard, with their key settings.

What is the problem?You know the theory of data and sharded parallelism (Distributed topic). Now the code: how processes start, find each other, average gradients and shard a model, with as few changes as possible.
Core ideatorchrun starts one process per GPU (graphics processing unit) and sets RANK, LOCAL_RANK, WORLD_SIZE; init_process_group("nccl") connects them. DDP (distributed data parallel) wraps the model and all-reduces gradients in buckets during backward. FSDP2 calls fully_shard on each block and then the root, sharding parameters as DTensors.

2 · Limitation

What multi-process training needs

Discovery

Processes on many machines must find each other and agree on ranks.

Identical replicas

Every rank must start from the same weights and stay in sync.

Different data

Each rank needs its own shard of each batch.

3 · Your turn

What does LOCAL_RANK index?

Pick an answer before moving on. Committing to a guess, even a wrong one, makes the real answer stick.

On a 2-node × 8-GPU job, what is LOCAL_RANK for global rank 11?

3: rank 11 is the fourth GPU (index 3) on node 1. LOCAL_RANK picks the GPU within a node; RANK is global.
4 · Core idea

Launch, connect, wrap

torchrun

Spawns processes, sets RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT; can restart on failure.

Process group

init_process_group("nccl") on GPUs ("gloo" on CPU (central processing unit)); collectives: all_reduce, all_gather, reduce_scatter, broadcast.

DDP or FSDP2

DDP(model) for replicated models; fully_shard per block for sharded ones.

5 · How it works

FSDP2 in a few lines

from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for block in model.blocks:
    fully_shard(block, mp_policy=mp)       # each block: all-gather before use, reduce-scatter grads
fully_shard(model, mp_policy=mp)           # the root (embeddings, head)
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)   # optimizer sees sharded DTensor params

Mapping from FSDP1

The official FSDP2 tutorial states that FSDP1 (FullyShardedDataParallel) Legacy is deprecated; new code should use fully_shard (FSDP2) Current practice. The tutorial maps FULL_SHARD to reshard_after_forward=True (ZeRO-3-like (ZeRO = Zero Redundancy Optimizer)), SHARD_GRAD_OP to reshard_after_forward=False (ZeRO-2-like), and HYBRID_SHARD to a 2-D device mesh.

5 · How it works

Worked example: what DDP does for you

Notebook 08: two CPU processes launched with torchrun and the gloo backend; each holds half of a 16-example batch.

Worked example

  1. Manual version: after backward, for every parameter call dist.all_reduce(p.grad, SUM) and divide by the world size.
  2. Result: identical to the gradient of the full 16-example batch on one process (checked to 10⁻⁶).
  3. DDP version: wrap the model in DistributedDataParallel and run the same forward/backward: same gradients, with all-reduce launched in buckets during backward.
  4. PyTorch 2.14.1 DDP bucket size defaults to 25 MB (the first bucket is 1 MiB, so communication can start early).
DDP is exactly "average the gradients", overlapped with the backward pass and bucketed for efficiency.
6 · Why it works

Why the APIs look like this

Same model code

DDP and FSDP2 wrap modules; the model itself is unchanged.

Overlap

Hooks launch communication during backward (DDP buckets, FSDP (Fully Sharded Data Parallel) prefetch).

Per-block sharding

Wrapping each block bounds peak memory to one block's full parameters at a time.

Elastic launch

torchrun can restart failed workers and re-form the group.

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"DDP sums gradients."

It averages them across ranks, so the learning rate means the same as on one GPU with the global batch.

"FSDP needs a different model definition."

fully_shard wraps existing modules; parameters become sharded DTensors.

"Each process sees all GPUs and picks one."

Each process should set its device from LOCAL_RANK; otherwise all processes default to GPU 0.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • torchrun --nproc_per_node=8 train.py. Single node, 8 GPUs.
  • torch.cuda.set_device(LOCAL_RANK). Before creating the model.
  • FSDP2: shard blocks, then the root. for b in model.blocks: fully_shard(b); fully_shard(model).

⚠ Traps

  • Same data on every rank. Use DistributedSampler (and call set_epoch).
  • Saving from every rank. Save on rank 0 (DDP) or use distributed checkpoints (FSDP).
  • Mismatched collectives. If ranks call collectives in different orders, the job hangs.

9 · Key takeaway

Key takeaway

torchrun starts one process per GPU, init_process_group connects them, and DDP (bucketed gradient all-reduce) or FSDP2 (fully_shard per block) turns the same model code into distributed training.
Say it in 30 seconds

Distributed PyTorch starts with torchrun, which launches one process per GPU and sets each one's global rank, local rank and world size. Each process calls init process group with the nccl backend on GPUs or gloo on CPUs, sets its device from the local rank and reads its own shard of the data. Wrapping the model in DistributedDataParallel averages gradients across ranks with bucketed all-reduces during the backward pass; notebook eight shows this equals the full-batch gradient. For models that do not fit, FSDP2's fully shard is applied to each block and then the root, sharding parameters and gradients.

Problem: launch, connect and sync many processes.
Core idea: torchrun → process group → DDP or fully_shard.
Defaults: DDP buckets 25 MB; nccl on GPUs.

PyTorch Distributed: Experiences on Accelerating Data Parallel Training
Li et al. · VLDB 2020

PyTorch's DistributedDataParallel design: gradient bucketing, overlapping all-reduce with the backward pass, and skipping synchronization during gradient accumulation.

Remember: near-linear scaling on 256 GPUs
torchrun (Elastic Launch)
PyTorch documentation · docs.pytorch.org 2026

Launches one process per device and sets RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR and MASTER_PORT; supports multi-node and elastic restarts.

Getting Started with Fully Sharded Data Parallel (FSDP2)
PyTorch documentation · docs.pytorch.org 2026

fully_shard applied to each transformer block and then the root; parameters become DTensors sharded on dim 0; all-gather before use, reduce-scatter after backward.

PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel
Zhao et al. · VLDB 2023

PyTorch's ZeRO-3-style fully sharded data parallelism, with flattened parameter units, prefetching and hybrid sharding.

Remember: comparable to DDP speed while supporting much larger models
