The training loop

The handful of lines every PyTorch training script shares: zero_grad, forward, loss, backward, clipping, optimizer and scheduler steps, parameter groups for weight decay, and checkpoints that resume exactly.

What is the problem?Training runs for days, must be stable, and will be interrupted. The loop has to apply the right update every step and resume after a crash as if nothing happened.
Core ideaEach step: opt.zero_grad(set_to_none=True) → loss = … → loss.backward() → clip_grad_norm_(…, 1.0) → opt.step() → sched.step(). Put biases and norm gains in a no-decay parameter group. A checkpoint stores model, optimizer and scheduler state (plus RNG (random number generator) and data position).
1 · Problem

What does a checkpoint weigh?

Model, gradients and AdamW state for a given size and precision. The checkpoint you save is model + optimizer (gradients are recomputed).

2 · Limitation

What goes wrong in naive loops

Stale gradients

Forgetting zero_grad adds last step's gradients to this one.

Loss spikes

One huge gradient can wreck a run without clipping.

Non-resumable runs

Restarting from weights alone changes the optimisation trajectory.

4 · Core idea

Six lines, in order

zero_grad

Reset .grad (set_to_none=True frees the memory).

forward, loss, backward

Compute the loss and fill gradients.

clip, step, schedule

Clip the global norm, update weights, advance the learning rate.

5 · How it works

The loop in code

decay    = [p for p in model.parameters() if p.dim() >= 2]
no_decay = [p for p in model.parameters() if p.dim() < 2]
opt = torch.optim.AdamW([{"params": decay, "weight_decay": 0.1},
                         {"params": no_decay, "weight_decay": 0.0}], lr=3e-4, betas=(0.9, 0.95))
sched = torch.optim.lr_scheduler.LambdaLR(opt, warmup_then_cosine)

for step, (x, y) in enumerate(loader):
    opt.zero_grad(set_to_none=True)
    logits, loss = model(x, y)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step(); sched.step()
    if step % 1000 == 0:
        torch.save({"model": model.state_dict(), "opt": opt.state_dict(),
                    "sched": sched.state_dict(), "step": step}, "ckpt.pt")
5 · How it works

Worked example: what a checkpoint must contain

Notebook 04: train 40 steps straight, versus 20 steps → checkpoint → reload into fresh objects → 20 more steps.

Worked example

  1. Saving model + optimizer + scheduler state_dicts and loading all three: the final weights match the uninterrupted run exactly (max difference 0).
  2. Saving only the model weights: Adam's moment estimates and the scheduler position are lost; warmup restarts and the weights end up different (max difference ≈ 0.4 in the notebook).
  3. For a 7B model, AdamW's m and v in FP32 (32-bit floating point) are 8 bytes × 7B = 56 GB, twice the FP32 weights themselves.
  4. PyTorch's AdamW defaults: lr 10⁻³, betas (0.9, 0.999), eps 10⁻⁸, weight_decay 0.01 (LLM (large language model) recipes often use 0.1 and β₂ 0.95).
The optimizer state is part of the model's training state; resume with all of it or the run changes.
6 · Why it works

Why each line is there

zero_grad

Gradients accumulate by design (deck 02).

Clipping

Bounds the update size when a rare batch produces a huge gradient.

No decay on norms and biases

Shrinking gains toward 0 fights normalisation for no benefit.

Full checkpoints

Exact resumption after hardware failures (Distributed deck 11).

7 · Misconceptions

Common misconceptions

Each statement below is a mental model people often get wrong. Decide why it is wrong, then reveal.

"model.state_dict() is a complete checkpoint."

Without optimizer and scheduler state, resuming changes the run (notebook 04).

"AdamW's default weight decay is 0."

In PyTorch it is 0.01; Adam's default is 0.

"Gradient clipping changes the gradient direction."

Norm clipping rescales all gradients by one factor; the direction is preserved.
7 · Tricks and traps

Tricks and traps

Rules of thumb that make this topic quick to reason about, and the mistakes people most often make with it.

✓ Tricks

  • Parameter groups. decay = p.dim() ≥ 2; no decay for biases and norms.
  • LambdaLR(opt, fn). fn(step) multiplies the base learning rate.
  • torch.save a dict of state_dicts. model, opt, sched, step, RNG.

⚠ Traps

  • sched.step() before opt.step(). PyTorch warns and the first LR value is skipped.
  • Saving the whole model object. Pickles code paths; save state_dicts instead.
  • Clipping after opt.step(). Too late; clip between backward and step.
8 · Check yourself

Check yourself

Answer from memory. If you can't, revisit the slide named in the answer.

FP32 bytes of AdamW m + v for a 1B-parameter model?

2 × 4 bytes × 1B = 8 GB.

Why exclude LayerNorm/RMSNorm (root-mean-square normalization) weights from weight decay?

They are scale parameters; decaying them toward zero fights the normalisation and does not regularise usefully.

What should a resumable checkpoint store?

Model, optimizer and scheduler state dicts, the step count, RNG states and the data loader position.
9 · Key takeaway

Key takeaway

Every step is zero_grad → forward → loss → backward → clip → optimizer step → scheduler step; decay only matrices, and checkpoint model + optimizer + scheduler to resume exactly.
Say it in 30 seconds

PyTorch training loops share six lines: zero the gradients, run the forward pass and loss, call backward, clip the gradient norm, step the optimizer and step the learning-rate scheduler. AdamW is usually given two parameter groups so weight decay applies only to weight matrices, not biases or normalisation gains, and a LambdaLR scheduler implements warmup plus cosine decay. A checkpoint must contain the model, optimizer and scheduler states: notebook four shows that resuming from weights alone changes the run, because Adam's moment estimates and the schedule position are lost.

Problem: stable, resumable multi-day training.
Core idea: six lines in a fixed order; decay groups.
Checkpoint: model + optimizer + scheduler + step + RNG.

Loshchilov & Hutter · ICLR 2019

L2 regularization and weight decay differ for adaptive optimizers; applying decay directly to the weights (AdamW) decouples it from the learning rate and improves generalization.

PyTorch's design: eager, Pythonic execution ("code as a model") with efficient C++/CUDA (Compute Unified Device Architecture, NVIDIA's programming platform for its graphics processors) kernels, a caching allocator and reverse-mode autograd.

A minimal, readable GPT training codebase in PyTorch (model.py + train.py) using SDPA (scaled dot-product attention), AdamW with weight-decay groups, cosine schedule, DDP (distributed data parallel) and torch.compile.
